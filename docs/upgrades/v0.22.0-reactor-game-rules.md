# v0.22.0 reactor game rules: documentation handoff

This is the player-facing rule handoff for `structs-ai` and interface authors.
It describes the replacement candidate; deployment remains a separate step.
The [client reference](v0.22.0-economy-client-reference.md) supplies the query and
event contracts. No upstream documentation repository has been modified.

## Base power and diversity

Eligible bonded, unjailed reactors convert fuel into power at 1:1 before the
existing commission split. At the default 4% commission, 1,000,000 ualpha gives
the owner 960,000 units of base power and the reactor 40,000. The owner can earn
additional power by distributing its post-commission shares across reactors.
That bonus creates capacity, not tokens, and incurs no second commission.

Group all addresses belonging to an owner by reactor before measuring the
distribution. Player and guild portfolios are separate: joining a guild does
not pool the player's stake into the guild's bonus. Generators and incoming
allocations do not count toward reactor diversity.

For equally weighted portfolios, the default bonus is:

| Eligible reactors | Bonus on owner reactor base power |
| --- | --- |
| 1 | 0% |
| 2 | Approximately 5.56% |
| 3 | Approximately 11.11% |
| 5 | Approximately 22.22% |
| 10 or more | 50% |

Unequal holdings earn less. The effective reactor count is `(sum(power))² /
sum(power²)`, and the bonus fraction is `50% × min(1, (effective count − 1) / 9)`.
The chain uses exact integer arithmetic and floors the final bonus once.
Displayed percentages are explanatory; use the returned applied bonus for
actual power. At the integer capacity ceiling, only the bonus that fits is applied.

**Adding stake to a concentrated reactor can reduce total power**, even after
including the new base power. Show the projected portfolio and capacity change
before confirmation. The chain permits this change. Lower capacity can cause a
brownout, resize automated allocations, and trigger ordinary GridCascade and
agreement settlement. Recovery guidance must account for the portfolio effect;
“infuse more into the same reactor” does not always increase power.

Dust spread across reactors provides little benefit. Reactor identities do not
prove independent operators. Splitting holdings between owners can sometimes
increase their combined bonus; the chain does not add identity tracking to
prevent that outcome.

## Stake admission and guild joining

The default cap activates once ten validators are bonded and stays active if
that count later falls. It rejects new stake inflows that leave the target above
30% of its defined denominator: bonded-pool tokens, plus the target's own tokens
when the target is not bonded. Existing concentration is not forcibly removed.
Outflows remain possible subject to ordinary staking rules. Passive validator-set
changes can put an existing position above the cap.

Delegation, migration into a reactor, validator self-bond and cancellation of an
unbonding all count as inflows. Native, authz, ICA and Structs staking paths share
the cap. Query headroom is a current estimate; it does not guarantee admission
despite balance, jail, authorization or intervening state changes.

A guild join requiring stake migration fails atomically when that migration
cannot complete, including a capped destination. Membership, rank and message-side
stake/payment changes roll back. A separately enabled join-by-rank-purchase path
moves no stake; it is available only when the guild enables and prices it.

## Outages, recovery and interfaces

Missing, jailed and unbonded validators supply no usable reactor power. Losing
a reactor also changes the owner's diversity bonus. Stored rows may take several
blocks to reconcile through bounded work, while readiness conservatively discounts
stale power. Query clients must distinguish stored capacity from usable capacity
and an incomplete inventory from a proven zero bonus. The existing 2,048-row
inventory limits remain relevant to large portfolios.

After recovery, only live backed positions are restored. A database restart or
genesis import does not award an extra copy of the bonus. The maximum bonus and
curve target are fixed between coordinated upgrades; cap parameters can change
through authorized parameter updates.
