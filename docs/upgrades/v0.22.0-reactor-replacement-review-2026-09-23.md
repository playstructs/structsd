# Review: v0.22.0 Reactor Efficiency Replacement Plan

Reviewed September 23, 2026 against `118b-reactors`, HEAD `ae08f243`, including
the current uncommitted economy and security changes.

**Recommendation: proceed with the direction, but revise the plan before implementation.**
Flat 1:1 power removes historical-rate accounting. The cap is a contained
admission rule; the diversity bonus remains a substantial current-state
accounting feature. Preserve their separation during implementation so removal
of efficiency does not become removal of unrelated security behavior.

## Findings that must change the implementation plan

### R1 — High: the removal rule would discard unrelated release changes

**Plan sections:** Removal scope; “Strip back to HEAD”; final no-trace grep.

“If it is not in v0.21.0, it is deleted” is not a safe feature boundary. The
uncommitted work also contains vaults, guild economics, permission changes, and
security fixes. HEAD is a comparison point, not a restore target for mixed files.

For example, current hooks contain the failed-reconciliation retry, and infusion
caches contain owner-index accounting. Neither should disappear because it was
developed alongside efficiency.

**Required revision:** inventory exact functions, fields, branches, keys, and
tests as remove, retain, or adapt. Delete only efficiency-owned behavior. Extract
shared validation before deleting its container file. Preserve both released
schema contracts and unrelated new fields; avoid unnecessary field renumbering.

Replace the blanket `reserved`/`efficiency` grep with an inventory of retired
feature identifiers in shipped code and interfaces. Ordinary reservations,
performance terminology, and dated review evidence are not removal targets.

**Acceptance:** the reviewable diff accounts for every mixed-file deletion, and
vault, guild, permission, billing, generator, and inherited security regressions
remain present and passing.

### R2 — High: commission and repair safety are not efficiency-only features

**Plan sections:** Decision 6; deletion of commission revision and repair snapshot files.

The [current source gate](/Users/abstract/Documents/Structs/Code/structs/x/structs/keeper/reactor_energy.go:30)
checks commission repair completion as well as validator health. Allocation
[creation](/Users/abstract/Documents/Structs/Code/structs/x/structs/keeper/allocation_cache.go:173)
and [increases](/Users/abstract/Documents/Structs/Code/structs/x/structs/keeper/allocation_cache.go:228)
use that gate. A slash can leave a validator bonded and unjailed while stored
commission capacity still awaits bounded repair. Flat power does not remove this
window.

The [repair snapshot](/Users/abstract/Documents/Structs/Code/structs/x/structs/keeper/reactor_repair_snapshot.go:14)
also establishes a finite insertion interval. Its completion boundary is a
separate concern from historical efficiency weights.

**Required revision:** retain these safeguards initially. Simplify their
implementation only when a replacement proves that stale commission cannot
authorize new allocations, permissionless restart cannot disable a healthy
source, and a bounded repair can finish despite new positions and later slashes.
Current repair metadata is not a historical billing journal.

**Acceptance:** preserve or adapt slash-liveness and commission-supply tests;
exercise a partial slash that does not jail the validator, unfinished repair,
continuous position insertion, and a second slash before repair completes.

### R3 — High: bonus updates need read consistency and grid propagation

**Plan section:** Diversity bonus → Incremental accounting, step 5.

Recalculating only at the top of `CommitAll` leaves earlier capacity checks in
the same operation observing the old bonus. Changing the capacity attribute alone
also misses automated allocation resizing and cascade scheduling. The current
[owner-capacity helper](/Users/abstract/Documents/Structs/Code/structs/x/structs/keeper/infusion_cache.go:175)
explicitly performs both.

**Required revision:** define one bonus refresh operation invoked before any
dependent capacity read and before commit. Route bonus deltas through the
established propagation behavior without feeding the bonus itself back into
reactor position totals. Specify which reads flush dirty totals and prevent
recursive refresh. Commit remaining dirty owners in sorted order.

Update `S2` using the old and new **aggregate power on that reactor**, not merely
the changed infusion's square. Multiple addresses on the same reactor represent
one diversity position.

**Acceptance:** mutate stake and query/use capacity in one context; resize an
automated allocation through a bonus-only change; trigger normal cascade on bonus
loss; and compare incremental totals with an independent grouped recomputation.

### R4 — High: the proposed nested-cache fix repairs only one symptom

**Plan section:** Open review items → InfusionCache.Commit.

Reading the stored previous owner during
[Commit](/Users/abstract/Documents/Structs/Code/structs/x/structs/keeper/infusion_cache.go:32)
can improve index deletion, but does not make the outer cached infusion current.
It can still overwrite a newer owner, and previously computed capacity/diversity
deltas can remain wrong. Using CurrentContext for all reads is not sufficient
when two contexts overlap and one commits behind the other.

**Required revision:** finish hook-driven changes before loading dependent outer
caches, or explicitly refresh/rebase them at the known boundary. Solve this
before adding diversity accounting to that lifecycle.

**Acceptance:** a real nested-hook regression checks the canonical infusion,
owner index, both owners' capacities, and both diversity summaries together. An
index-only assertion is insufficient.

### R5 — High: activation removal has unproven migration/genesis consequences

**Plan sections:** Decision 7; Phase 1's “no behaviour change” exit gate.

The new binary executes the upgrade handler; it does not begin running only after
that handler finishes. The [current handler](/Users/abstract/Documents/Structs/Code/structs/app/upgrades/v0_22_0/upgrades.go:30)
moves assets and rebuilds indexes before enabling the economy. In genesis,
staking/genutil hooks run before Structs installs its parameters, as documented
in the [current initialization code](/Users/abstract/Documents/Structs/Code/structs/x/structs/module/genesis.go:85).

**Required revision:** classify every flag-dependent behavior and establish the
initialization order required by its replacement. Remove the old flag when safe;
do not preserve historical efficiency merely to retain unrelated initialization
behavior. A narrowly scoped initialization control is acceptable if necessary.

**Acceptance:** fresh genesis with non-default parameters, gentx, the complete
upgrade handler, injected late migration failure, normal export/import, and
native restart. Removing a gate is not a behavior-neutral refactor by assertion.

### R6 — Medium: the cap can switch off after a temporary validator-set reduction

**Plan sections:** Decision 3; Stake-share cap → Exemptions.

Under the written rule, ten validators enables enforcement, nine disables it,
and returning to ten preserves concentration acquired during the disabled period.
This weakens the intended inflow limit. It is a policy consequence of the
proposed exemption, not an implemented exploit reproduced in this review.

**Required revision:** choose between persistent activation after reaching the
threshold (recommended), intentionally reversible enforcement, or an explicit
activation setting. Persist/export activation if it is historical state.

Define the validator-set boundary used by the rule.
[GetLastValidators](/Users/abstract/Documents/Structs/Code/structs/third_party/cosmos-sdk/x/staking/keeper/validator.go:411)
reads the last validator set and loads each validator; it is not an O(1), live
count. Avoid doing this full read for every delegation.

Also specify per-pair snapshot lifecycle, multiple-message overwrite/consumption,
rollback, and intentional genesis exceptions. “Missing snapshot means no-op”
needs tests proving ordinary inflows cannot reach that exception. Test the exact
post-operation denominator for native delegation, cancellation, and both
redelegation source statuses. Include actual ICA execution in the test matrix.

**Acceptance:** bootstrap, ten-to-nine-to-ten transitions, restart, and cap
boundaries; no cap error on slashing or stake reductions; exact typed errors and
rollback for rejected inflows.

### R7 — Medium: configurable bonuses lack a parameter-change lifecycle

**Plan sections:** Decisions 1–2; diversity totals.

If only dirty owners are recalculated, changing slope or maximum leaves untouched
owners at their old stored bonus indefinitely. Live readiness can deny stale
power, but cannot by itself complete stored grid accounting and propagation.

**Required revision:** for simplicity, make these parameters configurable at
genesis/upgrade and require a coordinated recalculation when they change. If
ordinary runtime changes are essential, budget and specify that extra lifecycle
explicitly. “Tighten later through params” is not yet an implementation design,
and changing bonus parameters cannot reduce the 1:1 base rate itself.

**Acceptance:** no mixed old/new pricing persists after the defined update;
bonus increases and decreases propagate correctly, including restart mid-work
if a deferred implementation is chosen.

### R8 — Medium: preserving a cursor does not completely solve repair starvation

**Plan section:** Open review items → failed reconcile re-snapshots from row zero.

The reset in [EnqueueReactorSlashReconcile](/Users/abstract/Documents/Structs/Code/structs/x/structs/keeper/reactor_slash_queue.go:33)
can repeat earlier work. However, replacing it with the existing restart behavior
can miss a new failure behind the current cursor. Independently, the worker
[resumes at the first failed position](/Users/abstract/Documents/Structs/Code/structs/x/structs/keeper/reactor_slash_queue.go:231),
so a persistent early failure can repeatedly consume a batch and prevent later
positions beyond it from being reached.

**Required revision:** separate forward progress from bounded retry obligations.
Keep failures discoverable without continually resetting the main pass. A newer
slash still needs to cover previously visited positions. Choose the smallest
representation that proves both progress and eventual repair.

**Acceptance:** failure behind the cursor, persistent failure at the start,
repeated enqueue, multiple reactors, later slash, recovery after removing the
failure, and no premature certification.

## Additional conclusions and corrections

### Guild joining: implement the confirmed rejection policy

Delete skip-and-continue from the plan. Propagate a required migration error and
let the normal message transaction roll back the join. No optional-migration
subtransaction is needed for that policy.

The SDK [unbonds the source before delegating to the destination](/Users/abstract/Documents/Structs/Code/structs/third_party/cosmos-sdk/x/staking/keeper/delegation.go:1268),
so test a destination rejection after that mutation, and a later rejection after
an earlier required migration succeeded. Membership, rank, staking, message-side
payments, and success events must all roll back. Do not claim ordinary ante
effects roll back with failed message execution.

### Genesis can be simpler than my earlier recommendation

The export [includes grid records](/Users/abstract/Documents/Structs/Code/structs/x/structs/module/genesis.go:496),
but import only accepts selected non-derived attributes through
[isGenesisGridImportable](/Users/abstract/Documents/Structs/Code/structs/x/structs/module/genesis.go:531).
Capacity and load are deliberately excluded and rebuilt from objects.

Therefore, exporting capacity does **not** by itself require exporting a separate
applied-bonus component to subtract on import. My earlier implementation plan's
recommendation was too broad on this point.

Prefer rebuilding diversity totals and applying the bonus once to reconstructed
capacity. Ensure hook-created and imported reactor contributions are not counted
twice. Only introduce extra exported accounting state if the final import design
actually needs it. Test pending repair and both normal/zero-height exports; native
database restart is a separate persistence path.

### The alternate-account claim needs narrowing

One reactor per alternate account earns no bonus. Other portfolio splits can
increase the total. With the proposed formula, one owner at
`[1000,10,10,10,10]` earns 6 bonus power; separate owners at `[1000]` and
`[10,10,10,10]` earn 9 combined.

This arithmetic was checked using exact rational calculations. Describe the
feature as an incentive for diversity within a game owner's portfolio, not
general resistance to alternate accounts or proof of independent operators.
Aggregation occurs after the existing commission split. The owner bonus should
not be commissioned a second time unless that is an explicit new game rule.

### Make formula rounding and cleanup explicit

Use integer intermediates and one final division:

```text
bonus = 0 when S1 == 0 or S2 == 0
otherwise:
bonus = floor(S1 * min(maxBps*S2, slopeBps*(S1*S1-S2)) / (10000*S2))
```

Do not price from rounded display values of effective reactors or basis points.
Specify checked conversion to stored capacity, permissible parameter ranges, and
block-hook overflow behavior. Remove zero-power owner/reactor rows so derived
state does not retain obsolete positions indefinitely. These are current-state
requirements, not a request for historical billing records.

### Treasury policy remains a separate release decision

[SetOwner](/Users/abstract/Documents/Structs/Code/structs/x/structs/keeper/guild_cache.go:707)
clears the outgoing owner's direct guild row, not rank registers or membership.
The plan correctly calls out retained rank-derived asset authority, but its two
suggested fixes have different gameplay consequences. Direct-only authority
eliminates rank-based treasury delegation generally; clearing asset rank grants
on transfer requires the buyer to reauthorize roles.

Resolve this explicitly for all applicable asset permissions, not just sends.
Preserve the user's established policy on unrelated independent direct grants
and the separation of guild ownership from membership.

### The proxy-join fix remains valid

The [default entry path](/Users/abstract/Documents/Structs/Code/structs/x/structs/keeper/msg_server_guild_membership_join_proxy.go:127)
checks existence but not closing status. Add the admission check and a rollback
regression. Keep this small fix separate from the economic replacement.

## Changes to phases, tests, and documentation

1. **Checkpoint selectively.** Preserve intended tracked and untracked source;
   do not stage node homes, credentials, build artifacts, or review logs simply
   because the worktree is large. Do not perform wholesale file restores.
2. **Prove a flat-power baseline first.** Resolve the cache and repair issues
   before layering diversity onto them. Preserve generic SDK slashing fixes and
   remove only the cancellation-efficiency patch hunks with no remaining callers.
3. **Keep cap and diversity integration sequential.** They overlap in staking
   hooks, initialization, rollback, and tests. Independent design work is possible;
   parallel changes to shared files make attribution harder.
4. **Add tests with each change.** The later testing phase should consolidate
   coverage, not supply the first tests. Preserve generic slash-liveness,
   cancellation, balance conservation, and defusion-cycle assertions from files
   marked for deletion.
5. **Measure real resource limits.** Include multiple live positions, repeated
   owner checks, two-owner combat, signed-transaction gas, and worker read/write
   budgets. The existing 2,048-row owner limit remains; do not mistake owner
   isolation fixes for removal of that limit.
6. **Audit test_chain.sh in detail.** Add genuine multi-validator cases. Use
   fixture-specific cap settings rather than changing production defaults. Count
   delivered assertions and inspect receipts; missing fixtures must not become
   silent success. Use skip-mining for iteration, then cover the final mining,
   generator, and affected combat lifecycle.
7. **Rehearse the composed upgrade.** Use supported v0.21.0 testnet state, record
   chain/height/source hashes, compare asset conservation and per-owner capacity,
   and continue through cold restart. Report base repair separately from bonus
   issuance. The complete migration can still cause legitimate brownouts even
   though adding the bonus alone increases capacity.
8. **Keep event work in scope.** Verify zero-bonus transitions, owner associations,
   actual amounts, deterministic order, rollback, and genesis reconstruction.
   Distinguish stored bonus from live usable bonus during deferred cleanup.
   Indexer implementation remains user-owned.
9. **Preserve honest evidence.** Update current product/operator docs to describe
   what ships. Retain dated review and test reports as historical evidence, with
   clear supersession. A grep should not erase the history of which candidate was
   actually tested. No old acceptance result certifies the replacement.

## Remaining clarification questions

These concern policy, not permission to perform routine engineering work:

- Confirm the exact bonus curve: 750 basis points per additional effective
  reactor and a 3,000-basis-point maximum?
- Confirm the cap defaults of 20% and ten bonded validators, and whether
  enforcement stays enabled after first activation. Persistent activation is
  recommended.
- Can bonus parameter changes be restricted to coordinated upgrades for this
  release? That avoids a separate runtime recalculation mechanism.
- Which guild-sale treasury policy should apply: reauthorization of asset rank
  grants after transfer, or direct-only treasury authority?

Cancellation counting as cap inflow is a sensible recommendation to document
with the chosen cap policy. Flat 1:1 plus diversity and rejection of failed
required guild migration are already decided.
