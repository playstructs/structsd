# v0.22.0 economy implementation history

Archived from the consolidated plan on 2026-09-10. This is a chronological work
record, not the current specification or release status. Statements such as
"unwired", "pending" and "unimplemented" describe the checkpoint where they were
written and may have been superseded. Consult the [main plan](v0.22.0-economy-plan.md)
for requirements, current evidence and remaining release gates. The record below
is preserved verbatim to retain investigation and test provenance.

### Implementation progress

Current release checkpoint (the detailed entries below are chronological):

- Latest user decisions supersede the earlier rebase and self-stake proposals:
  retain validator self-stake at its existing operator address, provided it remains
  accessible, and grandfather legitimate existing reactor fuel at the legacy 100%
  rate before commission. New deposits use the new bands and blend into the old
  position. Withdrawals/slashes reduce that blend proportionally; withdrawn fuel
  does not regain its bonus on redeposit. Inactive reactors keep their historical
  weight but produce zero energy. Historical phantom capacity is still repaired.
  Self-stake retention is an approved exception, implemented for ordinary source
  accounts as a migration component, but not verified end to end.
  Verify operator key/access preservation, rewards, native minimum-self-delegation,
  pending queue/slashing destinations, vesting accounting and later address changes.
  Implementation default under the fair/fast direction: **new** deposits into
  inactive reactors lock 50% at deposit, with zero output until eligible. This
  default is an implementation choice, not an additional confirmed user decision.

- `test_upgrade.sh` now uses a v0.21.0→v0.22.0 rehearsal runner with isolated
  prepared genesis, strict population/governance confirmation, boundary exports,
  block-event capture, staking comparison and all-denomination bank event replay
  with vault routing checks. Mock-only control-flow tests pass; bank replay also
  passes against a real in-process SDK asset-phase upgrade fixture.
  Vesting account replay also passes against that fixture: events must match
  complete exported vault accounts and preserve source identities on conversion;
  unassociated vesting accounts must remain unchanged. This verifies event
  fidelity, with independent schedule/spendability tests still required.
  It has not been run live; final handler wiring and full asset/event acceptance
  checks remain outstanding, and its result does not claim release approval.

- `MigrateVaultAssets` composes vault provisioning, vesting conversion, bank,
  delegation, pending staking records and infusion relocation atomically. It
  has real-app rollback, vesting continuation, export/restart and asset-event
  upgrade-block coverage. A pre-upgrade staking snapshot replayed through the
  public asset-phase block events reconstructs every committed delegation,
  unbonding and redelegation record, including merged entries and exact shares.
  It is now wired into the named v0.22.0 handler; unsupported vesting self-stake
  still refuses the complete upgrade atomically.
  The real upgrade-block replay also reconstructs every infusion field and
  effective grid attribute through source deletion in EndBlock. It handles the
  SDK's raw `mode=EndBlock` envelope attribute separately from typed JSON fields.
  A second real upgrade-block test composes vault migration followed by efficiency
  rebasing with two active validators. It reconstructs the final infusion/grid
  state and published efficiency snapshot, checking each final weight and power
  against fuel at the grandfathered rate. A brownout variant adds historical
  phantom fuel and fills pre-upgrade capacity with an allocation, proves fuel
  reconciliation overloads it before
  EndBlock, and verifies the cascade deletes it with a public event while
  preserving capacity. The next block commits with healthy SDK accounting.
  Inactive-entry lifecycle validation, wider cascades and final-handler wiring remain outstanding.
  The rehearsal runner now requires infusion/effective-grid event replay against
  its boundary exports and saves a hashed report. The Python verifier passes on
  the real SDK asset-phase fixture; queue storage, final-handler economics and
  downstream indexer acceptance remain separate requirements.
  That verifier also checks complete efficiency-snapshot replacement against
  post-upgrade export, including empty replacement, denominator and rate
  validation. Publication in the active case has real SDK composed-test coverage.
- The concrete vesting schedule format no longer consumes an SDK `Any` unpack
  call per source. Signed infusion coverage includes 10,000 simple schedules
  within the free-message gas cap; actual migration cardinality and other
  schedule/operation shapes still need verification.
- `MigrateReactorEfficiency` supplies an atomic one-time rebase, but final
  activation and ongoing eligibility/snapshot transitions remain unfinished.
  New inactive fuel uses the implementation default of 50% at deposit. Validator self-stake is now
  explicitly retained at the operator address, subject to accessibility checks.
- The registered `reactor-efficiency-consistency` invariant checks persisted
  weighted records for valid fuel/weight/power, commission, health-ratio and
  owner fields. Corruption tests exercise writes that bypass the atomic cache.
  It accepts unweighted reactor records only before activation. After activation,
  every reactor row must carry a weight, including zero-fuel/defusing-only rows.
  A regression detects activation over legacy rows and accepts them only after
  grandfathering; the assembled-handler normal and brownout tests run the
  invariant after the upgrade. The full Go suite passes. This establishes stored
  weight presence and validity, not comparison with live stake, current eligibility
  or grid reconciliation; those remain separate release checks.
- Efficiency migration now validates every existing weight before filtering by
  destination type. Previously, a struct or unknown-enum row carrying a reactor
  weight bypassed the check even though genesis would reject it on restart.
  Real-app regressions reproduced both acceptances before the fix and now verify
  rejection with unchanged infusion/grid state, snapshot and events.
- The registered `vault-ownership-consistency` invariant and vault export
  validation check derived addresses, existing owners/auth accounts and absence
  of signing public keys or player-signing indices on provisioned vaults.
  Unprovisioned owners remain valid; complete asset migration is a separate gate.
- `ReactorEfficiency` exposes a reactor's published snapshot rate through gRPC,
  REST (`/structs/reactor/{reactorId}/efficiency`) and CLI
  (`query structs reactor-efficiency`). The response includes validator address,
  denominator, rate, explicit snapshot availability and `efficiencyActive`.
  Activation and rate availability are independent: published rates alone do not
  enable the new economy, and an empty snapshot does not disable it. The query
  does not publish a snapshot, assert current validator eligibility or substitute
  an inactive entry rate. The pinned query regression covers both distinctions,
  JSON round-trip and read-only behavior. Protobuf/REST bindings and OpenAPI are
  regenerated; the full Go suite passes.
- Published efficiency snapshots now round-trip through genesis as validator/rate
  records, independently of each infusion's historical blend. Import validates
  canonical addresses, unique validators, valid bands and staking references
  before replacing any prices; export uses deterministic raw-address order.
  Real-app height-preserving and zero-height restart tests verify that subsequent
  deposits use the restored price while existing fuel retains its old blend.
  Legacy genesis without a snapshot remains unpublished. This closes snapshot
  loss on export/restart, not the outstanding activation or refresh scheduling.
- Efficiency snapshot refresh emits a complete replacement event only when
  prices change, including an empty replacement when all rates are removed.
  Block-one genesis events replay persisted prices without recomputing them.
  Real-app tests verify decoding, store agreement, unchanged-refresh suppression,
  cache rollback and replay guards. Final upgrade/lifecycle event delivery and
  downstream indexer consumption remain release gates.
- Rank pricing, separate purchase admission, vault transactions and guild-owned
  infrastructure foundations are implemented. Security inheritance review and
  complete live-chain coverage remain open. The chain script has not been run.
- The final named upgrade, full event replay into an indexer, production-size
  rehearsal and the complete release acceptance audit are still required.

## Evidence consolidated on 2026-09-10 after restoration and reward-routing review

This section preserves the former release-status narrative verbatim. Its earlier
limitations and pending items may be superseded by later entries or the current
release-gate table in the main plan. It is evidence history, not a second specification.

Cross-player reward routing now has composed-migration coverage in both source
address orders. Rewards sent to another registered player's key are settled
before any bank sweep and reach that recipient's vault with exact balances and
SDK community-pool dust. Public reward/sweep events and the preceding vault
association are checked. Unassociated recipients remain unswept, and existing
withdrawal settings are preserved.

The script audit now checks complete conversion balance changes: player Alpha
and tokens, minted/burned supply and collateral pools, including both legs of
cross-guild conversion. Slippage refusal must preserve every affected balance.
Offline corruption tests execute the actual assertion blocks and reject
one-unit errors; all 17 shell-helper tests and syntax checks pass. Live script
execution is still required.

Pending automatic restoration now survives both height-preserving and zero-height
export/restart in the real SDK fixture. The exported genesis contains partially
restored positions; import rebuilds all 130 vault positions from staking with
exact historical weights, owner capacity and vault associations, and the next
block commits. Genesis reconstruction completes the pending ramp rather than
exporting the internal reconciliation queue. The existing pending-slash variant
continues to verify proportional fuel and weight reduction.

Gradual restoration now has public-event replay coverage across both committed
recovery blocks. The reconstructed complete infusion records and effective grid
match chain state after each block, and events advertise exactly the positions
restored in that block while retaining pending zero-power positions. The event
contract document also now distinguishes current production-handler coverage
from earlier phase-only fixtures; live rehearsal and downstream indexer
acceptance remain unverified.

Activated automatic reactor restoration is now bounded: a bonded hook queues
the reactor instead of walking all its positions. Slash and restoration work
share a rotating 128-position block budget. A real SDK jail/rebond fixture with
130 player positions recovers across two committed blocks with fuel, historical
weights and owner capacity preserved. Recovery occurs after the existing grid
cascade and does not recreate shed allocations or agreements. Explicit paid
restart remains synchronous; immediate gating still needs a bounded design.

Interrupted restoration now has real-SDK regression coverage: a partially
restored reactor receives a 5% slash and is jailed again. Shared queue processing
cannot relight it while jailed, and a subsequent rebond restores exact reduced
fuel, historical weights and owner capacity for both grandfathered and 55%
positions. The test isolates hook/queue ordering; the separate committed-block

### Outage settlement interpretation under review

The working default is to retain brownout termination and date its settlement to
the actual loss of service. The user has also been asked whether billing should
instead pause and resume after recovery; that preference remains pending. No
pause/resume behavior has been implemented or treated as an agreed requirement.

Either outcome needs effective service history independent of queue-processing
height. A recovered source must not erase an earlier unavailable interval, and
a loss at one reactor must not terminate a contract still supported by sufficient
independent power. Provider checkpoints, per-agreement holdbacks/refunds, expiry,
capacity changes and zero-height export must use consistent service accounting.
The original regression exposed provider payments for an unavailable block after
expiry removed the nominal agreement. It now passes through default fresh genesis
without changing expected balances: the short outage case returns 150,000 ualpha
to the consumer and pays 50,000 to the provider. Healthy, recovered and independently
backed controls also pass. The [service-accounting investigation](v0.22.0-agreement-service-accounting.md)
records both the original failure and the implemented distinction between physical
agreement retirement and unresolved financial claims.

Migration and fresh genesis now initialize captured history after canonical module
state is ready. Durable obligations and provider reserves consume historical supply
evidence, including native backing, topology and ownership at each verified height.
Persistent jobs share a bounded interpreter; database and both genesis restart modes
preserve their progress. Interval verification distinguishes an unsupported span
from an unfinished proof, and recovery does not erase an earlier outage.

The finite FIFO scheduler retains failed payments for retry, rotates tasks beyond
the current pass's cutoff, and excludes tracked load from nominal provider billing.
Only certified amounts become provider revenue. Provider withdrawals use a provider
index and the same per-pass allowance; nested settlement completes before a fresh
CurrentContext loads the balances for withdrawal. Permission checks occur first,
and a rejected withdrawal rolls back earlier settlement and events.

Duration extensions fund only added principal. Capacity changes retain original
prices in historical windows and turn rescaling remainders into consumer refund
credit. Signed authority/rollback, multiple windows, old/new baselines and restart
continuation have test evidence. Safe history/window retention, historical payload
review, complete gameplay/lifecycle coverage and downstream financial snapshot
delivery remain release requirements.

The current-state supply checker now distinguishes supported, unsupported and
incomplete evidence. Admission still requires supported supply. Exhausting a
bounded inventory or graph walk does not prove a historical outage and cannot
by itself authorize a refund or provider payout.

## Financial snapshot consumer requirements

The block stream carries retained claims, collateral pools, closed windows and
terminal receipts from genesis or upgrade. `EventServiceSnapshotBoundary` brackets a frozen
inventory; `EventServiceSnapshotChunk.data` contains fragments of protobuf
`ServiceSnapshotRecord` bytes. `EventServiceCollateralPool` supplies live pool
replacements alongside existing obligation/window events. Use generated types
from the updated `service_obligation.proto`; this adds no transaction or query.

Stage records until the completion marker, verify contiguous indices/offsets,
counts and the content digest, then install them and apply all live financial
replacements and exact-key deletions buffered since the start marker. A new start replaces unfinished
staging; a database restart resumes the old stream. The start marker is delivered
even if the first chunk batch fails, allowing settlement to continue without
losing the indexer's intervening updates. Empty inventories have start/end markers.
Never infer asset transfers from these records.

Each block delivers at most 16 chunks of at most 4,096 raw payload bytes each.
Records may span blocks; JSON/base64 framing is additional. The exact digest,
restart, failure and overlay rules are in the [event contract](v0.22.0-economy-events.md#financial-snapshot-block-delivery).
Public `Agreement` heights remain physical; financial snapshot heights remain
logical and use `EventServiceClock` for mapping. Snapshot delivery can precede the
first EndBlock clock publication on fresh genesis or upgrade.

Native replay tests are evidence for the chain contract, not acceptance by GRASS
or structs-pg. Production consumers must still implement and verify this protocol,
including persistent staging, event deduplication and exact-once bank accounting.

`EventServiceFinancialDelete` selects one obligation, collateral pool or closed

production activation and deployed consumer acceptance remain unfinished.
`agreement-service` returns exactly one of `obligation` or `terminal_receipt`.
A terminal receipt holds immutable `final_obligation`, original `reader_sequence`
and bounded window-cleanup progress. It is completed accounting, never payable
state. Financial snapshots include receipt records, and
`EventServiceTerminalReceipt` replaces their cleanup progress without moving
assets. Clients must not infer that historical storage is already being pruned.

`ServiceObligation.paid_window_prefix` (field 30) is an optional completed-prefix
checkpoint containing `next_revision`, `next_height` and `gross`. It does not
reset cumulative principal/payments or credit any asset. Earlier closed windows
are deleted individually with `EventServiceFinancialDelete`; remaining revisions
keep their original numbers. The claim replacement advances the boundary in the
same transaction as those deletions. A financial snapshot must apply its usual
replacement/deletion overlay, so old frozen windows cannot reappear. Archived
totals are completed accounting, not a claim that the node still retains the
past service evidence or can independently audit past transfers. The remaining
claim retains its existing historical verification and payout rules.

Private reader bases add `first_revision` (field 10); absent/zero preserves the
original window inventory. There is no new transaction or RPC for archival.
The bounded primitive has internal continuation controls, but production
scheduling and actual downstream acceptance remain disabled/unverified.


The internal terminal cleanup scheduler persists `ServiceGenesis.terminal_cleanup`
(field 23), with `through_sequence` and `after_sequence` in the stable reader-birth
namespace. Import preserves that pass and derives its candidate index from settled
claims without settlement tasks and all retained terminal receipts. These are
scheduling fields, not payment events or permission to prune history. Production
invocation remains disabled while the retention and downstream acceptance gates
are open. Older development databases need an export with their matching binary
and restoration with this binary to derive the new index; directly opening an old
service inventory does not backfill it.


Retired service pools retain their payout owner and protocol address associations
until both derived addresses have been drained. The internal reclamation API
moves a bounded batch of denominations to that owner's vault and emits ordinary
bank transfers. A pool-kind financial deletion then removes the pool and its
roles; it is not a second transfer. `terminal_receipt` query/snapshot records
remain valid without a pool. Restore retained pool roles even when the provider
is absent from the live provider list. Production pool-reclamation scheduling
and downstream acceptance remain open.


`ServiceGenesis.pool_reclamation` (field 24) preserves a FIFO queue of retired

ledger updates preserve the ticket; the internal worker rotates pending pools

explicit queues must match the complete retired inventory. Queue rotation is
scheduling metadata, not a bank transfer or history-pruning signal. Its production
caller remains disabled.


`ServiceCollateralPool.reclaiming` (field 8, false when absent) closes both
retained pool addresses to new bank deposits after the first successful partial
cleanup. Preserve it through export/import and pool replacement events. Native,
guild and other denominations are all refused; no funds are redirected. Existing
assets continue to move to the retained owner's vault. The flag cannot revert
before final pool deletion. Pool roles remain until deletion, so restoration
must install those associations even though the provider itself is gone.


Financial deletion kind `TERMINAL_RECEIPT` (4) selects one completed receipt by
agreement id, with revision zero. It changes no asset balance and does not delete
a provider pool. Retain the receipt tombstone over late frozen snapshot records.
After explicit reclamation, agreement-service queries return not found; keep
historical final accounting downstream. The internal terminal dispatcher reclaims a completed receipt on a later
one-unit visit; its production caller remains disabled. Export/import must preserve the allocation counter, which assigns
future agreement identities independently of retained receipts.

## Financial snapshot block delivery

Fresh genesis, restored genesis and the scheduled v0.22 upgrade prepare a frozen
financial inventory after canonical initialization and financial migration succeed.
It includes retained `ServiceObligation`, `ServiceCollateralPool`, closed
`ServiceWindow` and non-payable `ServiceTerminalReceipt` records, including claims and pools whose physical provider was
already deleted. Preparation writes a private persistent delivery queue in the
same outer SDK cache as initialization/migration. Any late refusal rolls the
whole operation back. These full scans run only at those lifecycle boundaries;
an architecture test rejects moving them to a transaction, query or block worker.

The additive events in `service_obligation.proto` have these meanings:

| Event | Consumer action |
| --- | --- |
| `EventServiceSnapshotBoundary`, `complete=false` | Start a new staged inventory identified by `snapshot_id`; retain the visible prior inventory until completion and begin buffering subsequent live financial replacements and deletions. |
| `EventServiceSnapshotChunk` | Decode `data` from protobuf-JSON base64, then append these raw protobuf bytes in the declared record/offset order. This is a fragment of one `ServiceSnapshotRecord`, not a transfer. |
| `EventServiceSnapshotBoundary`, `complete=true` | Validate the counts and content digest, install the staged inventory, then apply the last buffered operation per key. |
| `EventServiceCollateralPool` | Replace the pool record keyed by `provider_id`. Reserve changes and retained-owner changes do not themselves represent bank movements. |
| `EventServiceTerminalReceipt` | Replace non-payable final accounting and window-cleanup progress, keyed by final agreement id in the receipt namespace. Never count its cumulative paid amounts as transfers. |
| `EventServiceFinancialDelete` | Delete the exact financial key selected by `kind`, `object_id` and, for a window, `revision`. Retain the deletion in the live overlay until the snapshot completes. This event represents no bank transfer. |

`ServiceSnapshotRecord` contains exactly one obligation, pool, window or terminal
receipt. Keys are respectively agreement id, provider id, `(agreement id,
revision)` and agreement id in a separate terminal-receipt namespace. Existing
`EventServiceObligation` and `EventServiceWindow` events retain their replacement
semantics. While a snapshot is incomplete, coalesce the latest live operation
per key in stream order, retaining either the replacement value or an explicit
deletion marker. Apply these operations after the baseline even if a later chunk
contains the old version of that same record. Merely deleting a key from the
staged inventory or from the overlay loses this information and permits
resurrection. A later replacement supersedes an earlier deletion; a later
deletion supersedes an earlier replacement. Repeated deletion, including deletion
of an absent key, is idempotent. Outside a snapshot, apply either operation
immediately. This prevents an early payment from being overwritten and a deleted
record from being restored by a late baseline fragment. Financial records
remain separate from bank balance accounting: neither snapshots nor cumulative
paid/reserved fields may be counted as an additional asset transfer.

Chunk indices and record indices begin at 1. Each record starts at offset 0;
subsequent offsets must be contiguous, with an unchanged `record_size`. Require
exactly `record_count` complete, distinct records and exactly `chunk_count` chunks.
Each chunk contains at most 4,096 payload bytes. BeginBlock emits at most 16 chunks,
or 65,536 raw protobuf payload bytes, plus small boundary metadata. JSON/base64
and ABCI framing increase the encoded size; this is not a total block-size or
block-time bound. A record may span blocks, so consumers should stream its bytes
and must not allocate blindly from an unverified size field.

Snapshot-only encoded transport now has a 128 KiB regression guard. A maximum
field-width fixture with sixteen full chunks and both boundaries uses 93,091
bytes in an ABCI `ResponseFinalizeBlock` and 97,592 bytes in CometBFT's
`block_results` JSON-RPC success envelope. It includes the SDK `mode` attribute
and a 32-byte app hash. The guard is not a consensus limit or a size limit for
the complete block response: transactions, other events, validator changes and
consensus-parameter updates require additional space. Clients must not cap their
whole block response at 128 KiB based on this component measurement.

The transport tests round-trip actual emitted chunks through ABCI protobuf and
the pinned CometBFT RPC codecs before the reference consumer receives them. A
record larger than sixteen chunks reconstructs exactly over two batches; valid
inventories of 20 and 129 claims also reproduce the frozen financial records
without changing bank/auth state. Metadata remains protobuf-JSON encoded; retain
the exact string-encoded uint64 values rather than converting them to floating
point. These checks do not establish deployed sync-state/GRASS acceptance.
Evidence: `/tmp/structs-snapshot-wire-final-focused.log`. See the
[encoded transport measurements](v0.22.0-economy-performance.md#snapshot-encoded-transport-and-queue-growth).

The lowercase hex `snapshot_id` is the SHA-256 digest of this byte sequence:

1. UTF-8 bytes of `structs/service-snapshot/v1`.
2. The baseline logical service height as an unsigned 64-bit big-endian integer.
3. For each record: its protobuf byte length as unsigned 64-bit big-endian,
   followed by the exact reassembled protobuf bytes.

Preparation orders obligations first, pools second, windows third and terminal
receipts fourth, each in canonical store-key order. Hash the received bytes, not JSON or a re-encoded
object. Start and completion metadata must agree on id, baseline height and both
counts. Reject an incomplete, reordered, duplicated or digest-mismatched stream;
never publish it as a complete financial inventory.

The digest identifies content, not a globally unique restart. A new start marker
replaces unfinished staging and its live overlay even if the digest repeats.
Indexer block/event deduplication must distinguish processing the same committed
block twice from receiving a new start on a later genesis continuation. Ordinary
database restart retains the existing frozen bytes, started flag and cursor;
it emits no second start. Genesis export omits this transient queue, exports the
current financial state instead, and InitChain prepares a fresh stream. Thus a
new genesis may replace an unfinished old stream. An empty snapshot still emits
start and completion so stale indexed financial records can be cleared.

BeginBlock commits the start marker before attempting the first chunk batch. If
a chunk is missing or malformed, that batch emits no chunks, advances no cursor
and deletes no queue rows; the start marker remains and live settlement proceeds.
Indexers therefore buffer payments even during a failed first delivery block.
Later successful batches use the same start and cursor. Invalid replay headers
cannot establish a trusted boundary; their repair requires restoring a valid
snapshot origin or generating a fresh genesis stream, not trusting later chunks
in isolation. Corrupt payloads that pass local framing checks are still rejected
by the consumer's final digest check. No automatic source-state rescan or queue
repair runs in BeginBlock.

`EventServiceFinancialDelete.kind` accepts exactly obligation (1), pool (2),
window (3) or terminal receipt (4); unspecified and unknown enum values must be rejected. `object_id`
selects an agreement for an obligation/window/receipt and a provider for a pool. Preserve
the literal id; do not normalize or truncate it. `revision` must be zero for
obligation/pool/receipt and selects exactly one revision for a window. Window revision
zero is a real key, never a wildcard. Invalid namespaces, empty suffixes, embedded
NULs and non-window revisions are rejected by `ValidateKey`. This validates the
selector only, not eligibility to delete canonical state.

The frozen snapshot still contains only existing records, not deletion markers.
Even a subsequently deleted frozen record must be fully reassembled, counted and
included in the content digest before the live overlay is applied. Snapshot
format and digest domain remain unchanged.

The internal terminal transition now removes a fully paid claim, releases its
reader, creates a non-payable receipt and disposes closed windows in bounded
batches. It emits the associated deletion/receipt events in the same SDK cache.
Errors and gas exhaustion roll back both state and events. Claim/window cleanup
moves no coins. The separate internal `ReclaimRetiredServicePool` operation now
drains at most 128 denomination rows from the two derived addresses to the frozen
retired owner's vault, preserving ownership until both total balances are empty.
Its bank transfer events describe the actual assets moved; the final pool-kind
`EventServiceFinancialDelete` removes only the financial pool record and its
protocol address roles. Never count that deletion as another asset transfer.
A provider's earlier deletion does not erase a retained service pool or its
address associations. Restored pool records with `retired_owner` preserve those
roles independently of the live provider list; snapshot consumers must do the
same using the provider id and its deterministic collateral/earnings addresses.
Terminal receipts remain readable after pool removal. Production invocation
remains disabled pending retention integration and downstream acceptance. See the
[terminal receipt contract](v0.22.0-history-retention-design.md#terminal-receipts-and-bounded-window-disposal-implemented)
and [pool reclamation contract](v0.22.0-history-retention-design.md#bounded-retired-pool-reclamation-implemented).

Completed receipt reclamation emits kind 4 with the agreement id and revision
zero. Remove only the receipt namespace, preserving any independent pool state.
This deletion makes no payment and cannot authorize history pruning. Retain its
live tombstone during an unfinished frozen financial snapshot. Once reclaimed,
the chain service query returns not found; downstream historical presentation
must use its previously delivered final record. Receipt dispatch is implemented internally; production activation remains pending.

The first successful partial drain emits `EventServiceCollateralPool` with
`reclaiming: true` (pool field 8). This replacement reports that both retained
pool addresses reject further deposits; it is not an asset transfer. Preserve
the flag in live and frozen snapshot records. Failed first drains emit no closure
or transfer events, and final pool deletion removes this state with its roles.

The internal pool scheduler persists FIFO tickets in service genesis and emits
no financial event merely for rotation. Asset transfers and the final pool
deletion still come from the atomic reclamation operation. A pending or failed
visit retains both payout ownership and queue reachability. Production scheduling
remains disabled; the existence of queue state is not evidence of live cleanup.

Transport controls cover injected future deletion sequences and actual terminal
claim/window/pool removal during an unfinished frozen snapshot. They cover both
operation orders, exact window selection, repeated/absent deletion, application
reopen, and fresh genesis replacing obsolete staging/tombstones. The reference
consumer remains a test fixture, not the deployed downstream indexer. The new
receipt payload and query variant must be supported before production activation.
History/window retention remains unfinished for live claims and safe pruning.
