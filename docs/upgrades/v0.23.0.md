## Upgrade setup

The on-chain plan name is **`v0.23.0`**. Following the previous releases,
`app/upgrades/v0_23_0/constants.go` defines the name and `upgrades.go` supplies
`CreateUpgradeHandler` and `NewUpgrade`. `app/app.go` registers the handler and
uses the existing upgrade-info/store-loader mechanism.

The handler runs `ModuleManager.RunMigrations`, then backfills missing planet
sectors. There are no new store keys, and it does not replay the v0.22.0 economy
conversion. Add future v0.23.0 migrations to this handler as development proceeds.

Build a development binary with `make build VERSION=v0.23.0`. Without an override,
the Makefile retains its existing Git-derived development version. A release tag
triggers publishing, so do not create one as part of development setup.

## Substation connection capacity maximum

A substation can now set an optional maximum per player connection. The calculation
remains `max(floor(rawCapacity * 9 / 10) - load, 0) / max(connectionCount, 1)`,
then is capped at `connectionCapacityMaximum` when that setting is nonzero.
Zero (including a missing row on existing substations) means unlimited. A cap is
not a guaranteed minimum: capacity shortages and outgoing load can still reduce
the share below it. It does not change raw input, usable station capacity, or
outgoing allocation admission.

The new grid attribute is `connectionCapacityMaximum`, enum ID **15**, stored as
`15-<substationId>` (for example `15-4-1`). `GridAttributes` adds protobuf field
**16** with that name; existing field numbers and attribute IDs are unchanged.
Substation queries expose it in `gridAttributes`. Writes use the existing
`EventGrid` record contract. Genesis export/import preserves the configured value
and rebuilds the derived share; station deletion clears the setting.

The transaction is `MsgSubstationUpdateConnectionCapacityMaximum`, with `creator`,
`substationId`, and uint64 `connectionCapacityMaximum`. It uses the existing
`MsgSubstationUpdateResponse`. The CLI is:

```sh
structsd tx structs substation-update-connection-capacity-maximum 4-1 20000 --from alice --gas auto
# Remove the limit:
structsd tx structs substation-update-connection-capacity-maximum 4-1 0 --from alice --gas auto
```

`PermUpdate` is required on both the signing address and the substation through
the existing permission resolver, including authorized guild owners and rank
grants. Cosmetic UGC moderation permission does not authorize this economic
setting. Missing, wrong-type, deleted, or closing stations cannot be updated.
The transaction follows ordinary free Structs message admission and does not
introduce proof, charge, signature-proof, or object-global throttle requirements.

All reads and writes use `CurrentContext` and the substation/grid caches. The
existing allocation and connection-count update paths recalculate shares; the
maximum setter does likewise. A connection-capacity row is marked changed only
when its newly computed value differs from the cached value. Repeating an
unchanged maximum also avoids rewriting the maximum. This keeps surplus input
and connection-count changes from generating redundant share writes/events
while the cap remains binding, without iterating over connected players.

The new message and changed gas/event behavior ship at the coordinated v0.23.0
upgrade. No bulk initialization, new store, or replay of earlier migrations is
needed. Clients/indexers and the structs-ai gameplay documentation should adopt
the new setting, transaction, and grid attribute before exposing cap controls.
No downstream repository has been modified as part of this chain change.

Regression coverage includes arithmetic/uint64 boundaries, real allocation and
player-connection paths, unchanged-share event suppression, query exposure,
deletion, protobuf genesis round trips, signed owner/delegate/guild/rank authority,
restricted-key rejection, missing/closing stations, and multi-message rollback.
`tests/test_chain.sh` phase 4 also runs the sourced
`tests/substation_capacity_maximum.sh` scenario: cap changes/removal, denied
updates, connection and allocation changes, and delivered-event write counts.
The scenario restores player associations and the original main feeder power.
Its assertion helpers have offline tests in `test_substation_capacity_maximum.py`.

## Group/authz nested execution boundary

The v0.23.0 ante guard closes a reproduced route around the existing prohibition
on wrapped Structs messages: a group proposal can contain `authz.MsgExec` for a
registered player's grant to the group policy account. Before this change, signed
transactions executed the Structs handler through group submission with
`EXEC_TRY`, stored-proposal `MsgExec`, vote with `EXEC_TRY`, and authz wrapping
that group execution. The handler still enforced the granter's permissions, but
Structs ante quotas/throttles did not see the inner action.

The guard now follows both authz and group containers. It checks all group
submissions, and resolves stored proposals for `MsgExec` and `MsgVote(EXEC_TRY)`;
this also blocks proposals created before the upgrade. Mixed nesting and stored
proposal references share a depth limit of 8 and a transaction-wide budget of
256 visited messages (including roots). Cycles, malformed containers, nil nested
messages, and unreadable proposal references fail closed with existing error
`structs-ante/2004`. Stored proposal reads run under the transaction gas meter,
after fee deduction and signature verification, so only an authenticated fee
payer can make a node read proposals. Each distinct proposal is read and walked
once per transaction; a repeated reference replays its recorded height and visit
count, so it is accepted or rejected exactly as a full rescan would be without
paying for the read again. CheckTx, ReCheckTx, simulation, and delivery apply
the same rule.

Ordinary group/authz actions remain supported within those bounds. Voting without
execution and withdrawing old proposals remain available; governance's existing
MsgUpdateParams path is unchanged. An execution reference must already resolve
when ante runs: clients creating a proposal and executing it in one transaction
should use submission's `EXEC_TRY`, rather than a separate `MsgExec` pointing to a
not-yet-stored proposal. These restrictions change transaction validity and ship
with the coordinated v0.23.0 upgrade, not a rolling binary swap. No stored rows,
module versions, or store keys need migration.

`app/group_authz_signed_test.go` reproduces the previous accepted execution and
checks rejection with unchanged substation state after the fix, including
pre-upgrade stored proposals and a successful native group-action control.
`app/ante/nested_group_test.go` covers mixed wrappers, proposal references/cycles,
malformed input, traversal bounds, single reads of repeated references at the
visit and depth limits, admission modes, and allowed cleanup/native paths. The
live `test_chain.sh` run remains deferred.

## Planet sectors

`Planet.sector` is an additive uint64 protobuf field (19). Every newly created
planet receives one of **127, 999, 44**, with equal probability per draw. The
assignment uses the existing `math/rand`/`rand.NewSource` block-AppHash approach:
the first eight AppHash bytes interpreted big-endian provide the seed, plus a
stable FNV-1a 64-bit hash of the planet ID as its offset. Short/absent AppHash uses
seed zero. The sector list order and seed calculation are consensus rules.
This is deterministic pseudo-randomness, not unpredictable randomness or an
exactly balanced partition. It does not consume or change player combat nonces.

The v0.23.0 upgrade assigns sectors to all zero-sector planets, including
completed and ownerless planets. Already assigned sectors are preserved; reruns
make no further writes or events. The migration changes only the sector field
and uses per-planet CurrentContext caches to publish normal EventPlanet updates.
It scans all stored planets once at upgrade time; event volume scales with the
number of previously unassigned planets and belongs in the rollout rehearsal.

Genesis imports preserve assigned sectors and deterministically assign legacy
zero-sector records. Genesis validation accepts zero for backward compatibility
and rejects nonzero values outside the three sectors. Exports, individual/list
queries, and EventPlanet carry sector through the normal Planet record. There
is no player transaction to choose or change sector, and sector currently has
no effect on combat, mining, travel, or permissions.

The Go regression tests cover deterministic same-block creation, valid-sector
coverage, query persistence, migration idempotence and field preservation,
registered upgrade execution, and protobuf genesis round trips with a changed
restart AppHash. `test_chain.sh` phase 6 checks new planets have valid
sectors, and the naming phase checks that renaming preserves the assignment; the live suite remains deferred. Downstream SQL projections and client
models need corresponding sector support before they can expose this new field;
this change adds the on-chain data/event contract only.

Sector validation on November 10, 2026: `make proto-gen` and `make proto-swagger`
regenerated the bindings/schema. Focused sector and registered-upgrade tests,
full `make test`, `make build VERSION=v0.23.0`, shell syntax validation for
`test_chain.sh`, and `git diff --check` passed. No live-chain tests were run.
