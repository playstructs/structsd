# v0.22.0 upgrade notes

The v0.22.0 release finishes separating fee classification from security
classification in `app/ante`. This document is the operator-facing index; the
decorators and their tests remain the source of truth.

## Binary behavior changes

### Ante gating

- `CheckTxThrottleDecorator` and `StakingThrottleDecorator` now gate on message
  content instead of the free-gas flag, matching `StructsDecorator` and
  `ThrottleDecorator`, which moved in v0.21.0.
- `IsFreeTransaction` requires every message in a transaction to be a Structs
  message, and `IsFreeStakingTransaction` requires every message to be a staking
  message. Pairing one gameplay or staking message with any other message
  therefore left the transaction outside both rate limits. That cost nothing:
  `fixed_min_gas_price` is 0 and the conditional mempool fee check returns early
  on a zero minimum.
- `CheckTxThrottleDecorator` runs whenever a transaction carries a gated Structs
  message or a staking message, so a mixed transaction can no longer buy extra
  per-address CheckTx admissions. A transaction carrying neither still falls
  through untouched; this is not a chain-wide rate limiter.
- `StakingThrottleDecorator` runs whenever a transaction carries a staking
  message, and skips messages from other modules rather than rejecting them.

### Address registration proof

- The proof an address key signs to join a player account is now
  domain-separated, bound to the chain id, and single-use. It was previously
  signed over `PLAYER<id>ADDRESS<addr>` — a pure function of two values that
  never change.
- The only barrier to reusing it was the address index, and `AddressRevoke`
  deletes exactly that. A player could revoke an address, wait for it to receive
  funds again, resubmit the original proof, and sweep the balance a second time
  with no fresh consent from the key that owns it.
- Nothing bound the chain, so a proof signed on one Structs chain verified on any
  other chain carrying the same player id.
- Proof bytes are now built by `AddressRegisterProofInput` over the chain id, a
  domain separator, the player id, the address, and a per-address nonce that is
  read from state and burned on success.
- The nonce lives in its own `Address/nonce/` store. `AddressRevoke` deliberately
  does not clear it, and it is exported and imported in genesis, because a
  revoked address is exactly the one whose old proof is still in circulation.

### Guild join minimum

- `GuildMembershipJoin` now rejects a duplicate entry in `infusionId` rather than
  counting the same infusion more than once.
- The field is an unconstrained repeated string, and the branch taken when an
  infusion's reactor already belongs to the destination guild only reads the
  record and adds its fuel. Naming one owned infusion N times therefore counted N
  times its fuel, and `joinInfusionMinimum` is the only economic gate on a direct
  join — so a guild's advertised entry stake could be cleared with a fraction of
  it.
- Fuel accumulation is now overflow-checked. The total is compared against a
  minimum, so a wrap yields a small number, which is the direction that admits.

### Guild join stake migration

- `GuildMembershipJoin` now requires `PermTokenMigrate` before it will redelegate
  the stake behind an infusion whose reactor is outside the destination guild.
- The message names only `creator` as a signer, so the infusion's address never
  authorized that redelegation; the handler was the entire authorization and it
  asked only for `PermGuildMembership`. `ReactorBeginMigration` gates the same
  staking call behind `PermTokenMigrate`.
- No coins leave the delegator address, but the stake changed validator, took the
  redelegation lock, and inherited the new validator's commission and slashing
  exposure — none of which membership permission should decide.
- The bit is checked in the handler rather than the ante, because a join only
  migrates when an infusion's reactor is elsewhere. An ordinary join that moves
  nothing is unaffected.

### Proxy guild join

- `GuildMembershipJoinProxy` now requires `PermGuildMembership` on an address that
  is already registered to a player. Onboarding a genuinely unregistered address
  stays permissionless, which is what the path exists for.
- `UpsertPlayer` is an in-get, not an insert: for a registered address it returns
  that whole existing player, and the handler then sets its guild, rank,
  substation connection and profile fields.
- The direct join path demands `PermGuildMembership` of the acting address, so a
  secondary key deliberately scoped without it could do through the proxy exactly
  what it is barred from doing directly.
- A primary address holds `PermAll`, so ordinary players are unaffected.

### Guild kick

- `GuildMembershipKick` now clears the kicked player's direct permission row on
  that guild.
- The kick previously cleared only `guildId` and the rank. A direct object grant
  is honoured with no membership predicate, so a dismissed administrator kept
  `PermAdmin`/`PermUpdate`/`PermGuildMembership` — and `PermAdmin` is all
  `GuildUpdateOwnerId` requires, with no membership check of its own.
- The owner's row is deliberately untouched: ownership is stored as
  `PermGuildAll`, and an owner need not be a member. The kick path already
  refuses to kick the owner.
- Scoped to kick. A member who leaves by joining a different guild keeps any
  direct grant on the old one; withdraw it with `PermissionRevokeOnObject`.

### Guild join bypass level `member`

- The `member` tier no longer waives the signing key's own permission ceiling.
- Permission checks have two independent layers: the key that signed must hold
  the permission, and the player must have standing on the object. The `member`
  tier is about standing only, but it was implemented by skipping the check
  entirely, so a member's delegated key carrying no `PermGuildMembership` could
  approve, deny, invite and revoke.
- The `permissioned` tier next door kept the ceiling, so the same restricted key
  got different answers depending on a guild setting unrelated to it — and
  opening a guild's join policy silently un-scoped every delegated key its
  members held.
- Standing is still waived. A member holding no grant on the guild object acts on
  membership exactly as before, provided the key they sign with carries
  `PermGuildMembership`.

### Primary address lockout

- `PermissionSetOnAddress` and `PermissionRevokeOnAddress` now refuse a write that
  would leave a player's current primary address with less than `PermAll`.
- Every recovery route runs back through the primary:
  `PlayerUpdatePrimaryAddress` needs `PermAll` to rotate to another key, and a
  grant can only hand over bits the granting address itself holds. A narrowed
  primary can neither restore itself nor authorize anything else to, so the state
  was permanent.
- The authorization check could not catch this on its own: the player's own
  `PermAll` key passes precisely because it still holds the rights it is about to
  destroy.
- The supported way to hold a narrow key is unchanged: rotate the primary to the
  address you intend to keep whole, then narrow the old one.

### Proof-of-work difficulty

- Difficulty is computed in integer arithmetic. It previously came from
  `math.Log10`, which Go implements in assembly on some architectures and
  portable code on others.
- Those implementations disagree in the last bit, and truncating to an integer
  turned that into a whole leading hexadecimal zero — so validators could require
  different proofs for the same block and the same object, accepting a hash their
  peers reject. That is an app-hash split, not a wrong answer, and no amount of
  testing on one machine would have found it.
- The replacement is the same curve expressed without a logarithm:
  `e = max{k : range^k <= age^63}`, difficulty `= 64 - e`.
- It feeds every proof path: struct build, ore mining, ore refining, planet raid
  and the guild charter.

### Raids on historical planets

- `PlanetRaidComplete` now refuses a planet that is not active, and a completed
  planet neither carries nor starts a raid clock.
- A completed planet keeps its `owner` stamp and stays in the store, but every
  defence that makes a live raid hard works on the owner's *current* planet. A
  clock started on a historical planet was therefore never reset, decaying to a
  one-zero puzzle while the owner came and went from the planet they actually
  occupy.
- Stored ore is a player attribute, not a planet one, so an obsolete planet paid
  out the victim's whole live balance.
- `FleetMove` also refuses a completed planet as a destination, so a fleet cannot
  arrive at one at all. Only player-chosen destinations are gated; the internal
  moves that send a fleet home are unaffected.

### Bank policy on transaction-chosen recipients

- `PlayerSend` and `ProviderWithdrawBalance` now apply the blocked-address set
  and the per-denom send-enabled flags before moving coins.
- `SendCoins` is not the bank's policy layer — those two checks live in the
  bank's own `MsgServer`, which a module calling `SendCoins` directly never
  reaches. The app's `BlockedModuleAccountsOverride` (fee collector,
  distribution, both staking pools, nft) was therefore not enforced on these
  paths, and neither was a governance send-disable.
- Sending into the bonded or not-bonded pool with no matching delegation leaves
  the pool balance disagreeing with staking's recorded tokens — an invariant
  break that surfaces as a panic on the next export-and-restart.
- These are the only two destinations in the module a transaction chooses; every
  other transfer targets an address the module derives itself.
- `PlayerSend` also rejects a malformed recipient rather than discarding the
  parse error, and rejects a non-positive amount.

### Guild rank fallback

- `PlayerUpdateGuildRank` now requires `PermAdmin` on the signing address before
  it will fall back to rank authority.
- The permission check fails for two unrelated reasons — the key does not carry
  the bit, or the player has no standing on the guild — and the handler treated
  both alike, falling through to a comparison of player-level ranks. A restricted
  secondary key therefore inherited its player's whole rank authority.
- Rank substitutes for standing, not for the key's own bits. The rank bounds
  themselves are unchanged: an actor must still outrank the target and cannot
  hand out a rank better than their own.
- This was the only rank check in the module that substituted for a permission;
  the entry-rank and kick paths apply theirs after a permission check.

### Provider substation validation

- `ProviderCreate` now requires its `substationId` to name an existing substation
  in the substation namespace.
- The getter it used builds a cache around any string and reads nothing, and the
  permission check was not a backstop: object permissions are keyed by the raw id
  string, and every player holds `PermAll` on their own player id — so a player
  id passed the check against a substation that did not exist.
- Grid attribute ids are derived from the object id alone, so such a provider
  read its available capacity from the player's own counters and sold grid the
  substation accounting knew nothing about.

### Provider id validation

- Every handler taking a provider id from a message now resolves it through
  `GetExistingProvider`: the six provider update handlers, `ProviderDelete` and
  `AgreementOpen`.
- Object permissions are keyed by the raw id string with no type namespacing, and
  every player holds `PermAll` on their own player id — so that id passed the
  permission check against a provider that did not exist, and the handler went on
  to mutate and commit a zero-valued record.
- Nothing was persisted, because the commit panicked on the empty id and the
  transaction failed. That is not a check; the same shape wrote real state
  elsewhere where the key happened to be non-empty.

### Generator infusion amount

- `StructGeneratorInfuse` now requires `infuseAmount` to name exactly one coin,
  and moves and burns only the coin it validated.
- The field is a free-form string and the parser accepts a comma-separated list,
  sorting it by denom. The handler checked the first coin and then transferred
  and burned the whole collection, so `1ualpha,1000000uguild.1-2` passed and
  destroyed the guild tokens while crediting only the alpha as fuel.
- The handler asks only for `PermTokenInfuse` and spends the player's primary
  account, so a delegate scoped to infusion alone could destroy asset classes
  `PermGuildTokenBurn` exists to protect.
- The `BurnCoins` error is now propagated; by that point the coins have already
  left the player's account.

### Substation deletion and open agreements

- Deleting a substation now disconnects an arriving `providerAgreement`
  allocation instead of destroying it. The agreement survives with no
  destination.
- Destroying it settled the agreement at the *provider's* cancellation price,
  which is correct when a provider ends service and a gift when a consumer does.
  A consumer could therefore pick the favourable price by deleting a substation
  rather than closing the agreement.
- The deletion still succeeds — refusing it would let a stranger pin a substation
  in place, since connecting an allocation asks for no rights on the destination.
- Outbound allocations are unchanged: an agreement sourced from a provider's own
  substation is that provider ending service, and the provider penalty is right.

### Infusion fuel rounding

- Reactor infusion fuel now converts delegation shares by truncating a
  multiply-first quotient, matching `Validator.TokensFromShares`. It previously
  rounded a divide-first one.
- Fuel is written per delegation and `RoundInt` is banker's rounding, so a shard
  worth exactly x.5 rounded up. After a 1% slash a 50-share delegation is worth
  exactly 49.5 — splitting a million across twenty thousand addresses returned
  every shard to 50, leaving a million Fuel and a million of grid capacity
  standing on 990,000 tokens. Nothing sums fuel against `validator.Tokens`.
- **This upgrade carries a state migration**, `MigrateInfusionFuelRounding`,
  which recomputes every reactor infusion. Without it the fix would only reach an
  infusion the next time staking touched that delegation.

### Shared message quota and recovery

- A recovery message — `MsgAddressRevoke` or `MsgPlayerUpdatePrimaryAddress` —
  sent from a player's **primary address** no longer spends the shared per-player
  message quota.
- The quota is keyed by player, so every address of a player draws on one budget,
  and it is charged in the ante before any handler runs — therefore whether or not
  the message succeeds. A delegated key could exhaust a block's budget on messages
  that all fail, locking the owner out, including out of the revoke that would
  remove that key.
- The exemption is the primary address, not the message type: a delegate naming a
  recovery message gets no exemption. Both messages already demand `PermDelete` or
  `PermAll` at the ante and neither carries a throttle key, so this opens no free
  channel.
- A bad key can still exhaust the quota for a block. What changed is that the
  owner can always evict it.

### Grid cascade

- `GridCascade` now does a bounded amount of work per block
  (`GridCascadeBlockBudget`), and what it does not reach stays queued for the
  next block.
- It ran to exhaustion in the EndBlocker, which has no gas meter, over a graph
  an attacker sizes for nothing: an allocation of one power feeds a substation,
  that substation allocates the same power onward, and two free messages add a
  link. Destroying the root collapsed the whole chain inside one block — a halt,
  and a deterministic one, so every retry of that block did the same thing.
- **Game rule change:** a cascade larger than the budget now sheds over several
  blocks instead of one. A grid a real guild builds is orders of magnitude below
  the budget and still finishes in the block it starts.
- A waiting object cannot sell power it does not have — every capacity gate
  already reports zero headroom when load exceeds capacity. What it keeps doing
  is powering what is already attached, which is the "one last block of power"
  the cascade has always accepted, over more blocks.
- The queue is now FIFO rather than keyed by object id. That is a security
  property: object ids sort lexicographically, so under the old ordering an
  attacker could hold a substation whose id sorts late out of the queue
  indefinitely by keeping cheaper-sorting entries in front of it.
- The queue is also imported at genesis now. It was exported and never imported,
  which only worked while the cascade drained it inside the block that filled it.
- The cascade also loads only as many of a source's allocations as it could
  shed in that block. Bounding the destroys did not bound the reads, and a
  source's capacity can be split into arbitrarily many one-power allocations, so
  a single wide source could still put unbounded work in the EndBlocker.
- Operators will see a `Grid Queue (deferred)` warning naming the backlog
  whenever a block ends with work outstanding. A `Grid Queue problem` warning now
  means only what it says — a source that genuinely cannot be brought under
  capacity — rather than also firing when the block simply ran out of budget.

### Agreement capacity resize

- A capacity change that would rescale an agreement to zero duration is now
  refused, whatever the provider published as its duration minimum.
- The rescale trades duration for capacity and truncates, so a small,
  nearly-expired agreement grown by a large amount lands on zero duration — which
  sets `EndBlock` to the current block. Expiry runs in the EndBlocker, *after*
  every message in the block, so the raised capacity was live and usable for the
  rest of that block against collateral that only covered the old capacity.
- On any chain built by transactions this was already blocked, because every
  provider setter floors `DurationMinimum` at 1. The gap was a genesis file:
  `GenesisImportProvider` assigns a whole record and skips the setters.
- **Operators importing or hand-editing genesis:** `structsd genesis validate`
  now rejects a provider whose `durationMinimum` is 0 or whose duration range is
  inverted. A file carrying either will fail to start rather than start unsafely.

### Genesis import and provider checkpoints

- A provider's `checkpointBlock` is now restored from the exported grid
  attributes, and a provider that arrives without one is stamped with the genesis
  height.
- It was previously filtered out of the grid import along with load and capacity.
  Those two are correctly excluded — the import rebuilds them from the agreements
  — but the checkpoint is a clock that nothing else on the export records, and an
  unset grid attribute reads as zero.
- Consequence on any chain restarted from a height-preserving export: the first
  `Checkpoint()` billed `currentBlock - 0` times the full reconstructed load.
  `SweepRevenue` clamps to what the collateral pool holds rather than failing, so
  it did not error — it emptied the pool into the provider's earnings, and that
  pool is the escrow backing service consumers had not yet received.
- **If you have already restarted a chain from an export and then checkpointed a
  provider, its collateral pool may be short.** Check
  `provider-collateral-solvency` before upgrading.
- A restored checkpoint below the genesis height is left alone — that is a
  provider owed for the blocks between export and restart.

### Agreement expiration heights

- At most `AgreementExpirationBucketCap` (256) agreements may share one
  expiration height.
- Everything expiring at a height is torn down in that block's EndBlocker, which
  has no gas meter, and each teardown checkpoints a provider, moves money and
  destroys an allocation. The consumer picks the duration and so picks the
  height, which made the size of that block's work chooseable.
- **Game rule change:** `AgreementOpen`, `AgreementDurationIncrease` and both
  capacity changes can now be refused with *"too many agreements already expire
  at block N"*. The remedy is to shift the duration by a block. An agreement
  already indexed at a height keeps its slot, so a capacity re-price that lands
  back on the same block is never refused for this.
- Unlike the grid cascade, this is bounded at creation rather than at
  processing. An expiry gets exactly one attempt — the index is read at one exact
  height — so deferring one does not delay settlement, it bills the missed
  agreement's capacity to other consumers' escrow.
- No migration. The check counts the bucket and stops at the cap, so a chain
  arriving with heights already over 256 simply accepts nothing new at those
  heights until they drain.

### Zero-height export

- `structsd export --for-zero-height` now rebases live agreements onto the new
  chain's clock instead of carrying their absolute heights across.
- Previously an agreement exported at height H with `E-H` blocks left was
  re-indexed to expire at `E` on a chain restarting near 1 — it kept supplying
  capacity for roughly the entire age of the old chain, with no collateral
  behind any of it.
- The export now checkpoints every provider first, so the span actually served
  is settled against the old clock, then rewrites each agreement to
  `StartBlock = 0`, `EndBlock = remaining` and rebases the provider checkpoints
  to match. Both clocks move together or the next checkpoint bills a span the
  agreements no longer claim.
- An agreement with no time left is given one block rather than zero, so it
  expires on the new chain's first block instead of never.
- **`InitGenesis` now refuses a genesis file containing an agreement whose end
  block precedes the genesis height** — it could never expire, and would hold
  provider capacity forever. If you are setting a custom `initial_height` on a
  restored chain, this is the check that will stop you.
- Agreements and provider checkpoints are the only absolute heights that survive
  a structs import; planet and struct block clocks are exported but never read
  back, and the guild charter anchor clamps.

### Destroyed allocations

- `GetAllocation` now reports a destroyed allocation as not found, and
  `Destroy` on an already-destroyed allocation is a no-op rather than a second
  teardown.
- Destruction defers both the cache removal and the store removal to
  `CommitAll`, so within one operation a destroyed allocation still looked live.
  Since `Destroy` never zeroes the power attribute, a second destroy took the
  full power off the source's load again — and that load belongs to whatever
  allocations still share the source.
- Measured: a source carrying 250 with 100 destroyed should read 150; it read
  **50**, advertising 100 of headroom that did not exist. `SetPower` on the same
  stale handle drove it to 40.
- Handlers that name an allocation id now reject a destroyed one; teardown paths
  treat it as already done.

### Self-assigned defenders

- A struct can no longer be set as its own defender, and existing
  self-registrations are cleared by the upgrade.
- Nothing previously refused it: the range check compares locations, and a
  struct is trivially co-located with itself.
- The effect was on ordering. An attack resolves defender counters, then the
  volley, then the target's own counter — a target counters only *after*
  surviving the shots. A self-registered target was picked up in the defender
  pass, so its counter fired first, and a counter that destroyed the attacker
  voided the whole volley. The target took no damage at all, repeatably.
- This restores the documented combat sequence rather than changing it. No
  behaviour changes for anyone who was not self-assigned.

### Genesis fleet ids

- A genesis file containing a fleet whose id does not parse is now rejected —
  by `structsd genesis validate`, and again by `InitGenesis` for paths that skip
  validation.
- Previously such a fleet was dropped in silence. The keeper resolves a fleet by
  parsing its id into an index, a malformed one produced an untracked cache, and
  only tracked caches are committed — so the fleet vanished while the players and
  structs referencing it imported normally, leaving owners with fleet-bound
  assets and no fleet.
- Fleets were the only import affected this way; every other record type uses an
  allocator that always commits.

### Grid attribute arithmetic

- Adding to a grid attribute now saturates at `MaxUint64` instead of wrapping,
  in both `SetGridAttributeIncrement` and `SetGridAttributeDelta`. Both already
  guarded their subtraction; only the addition was unguarded.
- Capacity, load, stored ore and the replay nonces are treated as monotonic by
  their callers, so a wrap would destroy accounted value, understate committed
  load, or reset replay protection.
- A saturating add logs an error naming the attribute. No normal operation can
  reach it — this is a backstop, not a behaviour change any player will see.

### Validator slashing

- `BeforeValidatorSlashed` now queues the affected reactor instead of
  reconciling every delegation inline. Reconciliation runs in the EndBlocker,
  `ReactorSlashReconcileBudget` (128) infusions per block, resuming from a
  stored cursor.
- The hook runs in BeginBlock with no gas meter, and the validator's active
  delegator set is unbounded, so one slash previously cost whatever the
  delegators had accumulated.
- **Game rule change:** an infusion not yet reconciled keeps its pre-slash fuel
  and the grid capacity standing on it. The window is bounded by the slash
  fraction and by delegators/128 blocks. This is deliberate — zeroing the
  reactor's contribution up front would brown out every delegator's grid over a
  slash that took 5%.
- Operators will see `Reactor slash reconciliation deferred` / `complete` log
  lines naming the reactor.
- No migration and no genesis change: genesis import already rebuilds every
  reactor's infusions from staking, which is a full reconciliation.

### Permissions on objects

- `PermissionGrantOnObject`, `PermissionSetOnObject` and
  `PermissionRevokeOnObject` now reject a target player that does not exist.
- The target id becomes half of a KV key, and nothing resolved it — the object
  check speaks to the object, and an owner acting on their own object passes the
  permission check whatever target they name. Any string was storable.
- A permission record that drops to zero is now removed rather than written as
  eight zero bytes, and a revoke that removes nothing writes nothing. A missing
  key already reads as no-permission, so a stored zero carried no information
  and cost state permanently.
- Legitimate grants, sets and partial revokes are unchanged.

### Struct trash charge admission

- `MsgStructTrash` is now a registered charge message, so the ante applies the
  same charge floor and per-transaction duplicate check it applies to the other
  eight charge actions.
- Trashing costs the same charge as building and the handler discharges, but the
  ante reads the map rather than the handler. A transaction carrying two trashes
  was therefore admitted at CheckTx and failed in delivery — free to submit, and
  rolled back only after the block had paid to execute it.
- **Player-visible:** two `MsgStructTrash` messages in one transaction are now
  rejected up front, and a trash is refused if the player has already discharged
  this block. Both already applied to activate, attack, move, build-initiate,
  defense set/clear and the stealth actions.

### Substation creation

- `MsgSubstationCreate` now rejects an allocation that already feeds a
  substation.
- Connecting an allocation to a new substation is a *move*, so the same
  allocation could previously be submitted over and over — each call minting a
  substation and a permission record, and leaving the previous substation with
  nothing feeding it. Creation is free, so the only limit was the per-block
  message cap.
- **Player-visible:** create a substation from a fresh allocation, or release the
  existing one with `MsgSubstationAllocationDisconnect` first. An allocation that
  has been disconnected can seed a new substation again — the rule is about being
  connected, not about having been used.
- No migration. Substations orphaned by the old behaviour are ordinary
  substations with no incoming allocation and can be removed with
  `MsgSubstationDelete`.

### Permission cleanup

- Clearing the permissions granted on a destroyed object is now bounded per
  block; anything left is carried in a queue and finished in later blocks.
- The row count is chosen by whoever owned the object, and an agreement's expiry
  height is chosen by the consumer who opened it, so all of that work previously
  landed in one EndBlocker with no gas meter.
- Rows awaiting cleanup grant nothing — a permission is only consulted after its
  object has been loaded, and a destroyed object cannot be — so the deferral is
  collection, not deferred settlement.
- Operators will see `Permission cleanup deferred` / `complete` log lines naming
  the object.
- No migration and no player-visible change.

## Operator expectations

- The release is a coordinated binary upgrade. The ante changes are active as
  soon as the new binary runs, not inside the migration handler. Nodes running a
  mix of old and new binaries would accept different transactions and diverge,
  which is why the upgrade is named rather than shipped silently.
- There is no state migration and no store-key change. `CreateUpgradeHandler`
  runs `RunMigrations` and nothing else.
- **Behavior change to expect:** a transaction that mixes a staking message with
  any other message is now subject to the same one-staking-operation-per-address
  -per-block limit as a pure staking transaction. That was already the rule on
  the free path; the mixed form was a loophole. Clients batching a delegation
  alongside other messages more than once per block will now see
  `ErrStakingAlreadySubmittedThisBlock`.
- Transactions mixing Structs gameplay with other modules' messages now count
  toward the per-address CheckTx admission cap (`CheckTxAddrCap`, default 5).
  Operators who see legitimate clients hitting it can raise the cap; it is
  node-local and not part of consensus state.
- **Client-breaking:** the bytes signed for an address registration proof have
  changed. Wallets and tooling that produce these proofs must be updated in step
  with the upgrade, or `AddressRegister` will reject them as
  `signature_invalid`. There is no transition period by design — accepting the
  old format alongside the new one would leave the replay open for its duration.
- The current nonce for an address is served by the existing
  `/structs/address/{address}` query as `proofNonce`. It answers for
  unassociated addresses too, which is the case a re-registration needs.
- Every proof issued before the upgrade is invalid afterwards. Nothing on disk
  needs migrating: the nonce store starts empty and every address correctly
  begins at 0.
- Expect grid capacity to fall for validators whose stake was slashed while
  finely split, and expect the usual grid cascade to shed the allocations that
  capacity was carrying. The migration logs `infusionsVisited`,
  `infusionsChanged` and `fuelReleased`; on healthy state `infusionsChanged` is
  zero or close to it.
- **Game rule change:** deleting a substation no longer ends agreements arriving
  at it. Consumers must close an agreement through `MsgAgreementClose`, which
  charges the consumer cancellation penalty.
- `MsgStructGeneratorInfuse` now rejects an `infuseAmount` naming more than one
  coin. Clients should send a single `ualpha` or `alpha` amount.
- A message naming a provider that does not exist now returns a clean
  object-not-found error instead of failing with a recovered panic. Clients
  parsing the old failure mode should expect the typed error.
- Any provider already stored against a non-substation id keeps working at the
  bank level but will no longer be creatable. Worth a state audit before the
  upgrade: query providers whose `substationId` does not resolve to a substation.
- A delegated key used to manage guild ranks now needs `PermAdmin` on that
  address. A primary address holds `PermAll`, so only deliberately restricted
  keys are affected.
- Transfers to blocked module accounts and send-disabled denoms now fail through
  `MsgPlayerSend` and `MsgProviderWithdrawBalance` where they previously
  succeeded. Any tooling relying on either is broken by design.
- **Game rule change:** completed planets are unreachable. A fleet can no longer
  move to one, and a fleet somehow on one cannot complete a raid there. Fleets
  are already evicted when a planet completes, and returning home is unaffected.
  Raids and movement between live planets are unchanged.
- **Game rule change:** the integer form is the exact floor, so it differs from
  the old float wherever `63 * log_range(age)` landed exactly on an integer and
  the float fell a hair short. Across the reachable parameter space that is 13
  points, all at exact powers of the range's base — range 125 at ages 5 and 25,
  range 2187 at ages 3 and 243, and so on. At each, the requirement drops by one
  leading zero, which is the correct value. Every other age and range is
  unchanged.
- Miners built against the old CLI will still find valid proofs: the requirement
  only ever got easier at those 13 points, never harder.
- Tooling that narrows a player's primary address in place will now be rejected
  with `primary address ... must keep full access`. Rotate the primary first.
- In a guild at bypass level `member`, delegated keys used for membership
  administration now need `PermGuildMembership` on the address itself. A primary
  address holds `PermAll`, so only deliberately restricted keys are affected;
  grant the bit with `PermissionSetOnAddress` where that was intended.
- Anyone relying on a kicked member retaining guild rights (an external
  administrator kept on after dismissal) must re-grant them explicitly with
  `PermissionGrantOnObject` after the kick.
- A restricted secondary key that could previously be proxy-joined into a guild
  now needs `PermGuildMembership` granted to that address. Recruiting flows that
  onboard brand-new addresses are unchanged.
- A delegated key that could previously join a guild *and* migrate the stake
  behind its infusions now needs `PermTokenMigrate` in addition to
  `PermGuildMembership` for the migrating case. Grant it explicitly where that
  was intended.
- A client that legitimately sends the same infusion id twice in `infusionId`
  will now be rejected with `duplicate_infusion` instead of silently having it
  double-counted. List each infusion once.
- No error codes were added or renumbered. The reject paths reuse
  `ErrCheckTxAddrCapExceeded` (2041), `ErrDuplicateStakingInTx` (2042) and
  `ErrStakingAlreadySubmittedThisBlock` (2043).
