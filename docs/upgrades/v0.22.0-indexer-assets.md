# v0.22.0 indexer asset preservation

**Indexer scope confirmed, 2026-09-21:** The user owns indexer implementation,
schema changes, deployment and downstream ingestion testing separately. These
are not acceptance gates for this chain task. Chain events must still be present,
informative and accurate: verify complete payloads, actual asset amounts and
addresses, vault creation/ownership associations, deterministic ordering,
rollback, duplicate prevention and genesis/restart delivery. Existing downstream
findings and draft patches are reference material only; earlier downstream
acceptance requirements in supporting records are superseded by this decision.

The patches below are saved handoff drafts, not deployed changes or completed
end-to-end integration. No further indexer implementation/testing is planned in
this task. Remaining downstream limitations are recorded for the user's review.

## Current combined patch set: assets and vault ownership

The following patches supersede the assets-only pair below. Apply this pair to
the same recorded base commits, **not on top of** the earlier pair:

- [Combined indexer writer, vault handler and inventory projections](patches/docker-structs-pg-v022-vaults.patch).
- [Combined ledger identity and vault schema migrations](patches/structs-pg-v022-vaults.patch).

They are prepared and tested in `build/v022-indexer-vaults/`, not deployed.
`EventVaultAddress.eventVaultAddressDetail` now writes a dedicated `structs.vault`
association. A vault never becomes a `player_address` signing key. Owner IDs must
be canonical player/guild IDs; account numbers preserve the full unsigned 64-bit
range. Replays preserve the same association, while conflicting owner/address/
account-number combinations fail within the router's existing savepoint.
The handler also runs successfully under the actual `structs_indexer` role.

`structs.asset_owner_address` combines player signing addresses with player and
guild vaults, giving vault ownership precedence if a stale signing row names the
same address. Incremental inventory, ledger-based repair, complete backfill and
nightly drift reconciliation/repair all use that ownership relationship. Later
vault bank credits dirty the correct owner. Retained native-address balances
remain included; changing a signing address's player association moves only that
address's remaining balance and does not reassign the player's vault.

Guild treasury balances have `owner_type='guild'` rows and a separate
`view.guild_vault_inventory` exposing exact denominations and base-unit amounts.
The existing `view.guild_inventory` continues to describe member balances, now
including their vaults through player inventory. It does not mix treasury assets
or collateral pools into member wealth. Existing formatted address/player views
still have their legacy unknown-denomination display limitations; exact values
are in `api_inventory`, and complete web/API presentation remains separate downstream work.

The startup schema check now requires vault ownership relations and the
multi-denomination replay index before ingestion can begin. Coordinated schema
and binary rollout is still required. Reverting a populated vault table refuses
atomically rather than deleting associations.

Real PostgreSQL/Timescale tests cover malformed fields, maximum account numbers,
association replay, conflicting assignments, absence of signing-key rows, role
grants, incremental credits, retained balances, guild treasury separation, full
rebuilds, drift detection/repair and signing-address reassignment. The previous
code fails the same acceptance cases: it creates no vault association and reports
7 units for a player who owns 107 across retained and vault addresses. Exercising
nightly repair also exposed an existing PostgreSQL parameter-type ambiguity;
explicit casts now make that query execute successfully.

The full indexer Go suite passes, alongside the targeted real-database vault/
inventory and multi-asset tests. Schema verify/revert/reapply and guarded reversal
pass. These are handler, inventory and database proofs, not a complete RPC-to-API
ingestion run. Staking/vesting relocation, efficiency/revision/rank event
projections, held-maturity credits and downstream migration/restart acceptance
are not covered by these drafts. This patch set adds no on-chain history.

## Tested patches, not deployed

The existing indexer takes only the first coin in a bank event and truncates
SDK denominations containing `/`, `:`, or `_`. Vault migration moves all bank
assets, so successful chain migration alone would leave the indexed balances
wrong. These paired downstream patches preserve every denomination and its exact
amount; they add no chain state or billing history.

## Behavior

- Transfers emit both bank legs for every coin. Mint and burn events also emit
  every coin. Full SDK denomination paths survive, and amounts remain text through
  PostgreSQL NUMERIC conversion, including values above JavaScript's safe range.
- A malformed nonempty list or duplicate denomination returns an error before
  emitting any rows for that event. The existing bank savepoint/buffer rollback
  reports the failure instead of accepting a partial asset movement. Existing
  missing/empty amount behavior is unchanged.
- The ledger replay key adds `denom` to the existing time/chain/transaction/message/
  encoded-event identity. Existing leg indexes stay unchanged. Each coin can reuse
  those indexes without colliding with another coin or the next chain event.
- Gameplay's existing Alpha-specific transfer suppression applies only to Alpha;
  another denomination in the transfer retains its debit and credit. Broader
  correlation of unrelated Alpha transfers in a multi-message transaction remains
  a separate review item; this patch does not claim to solve it.

The schema change validates that identified rows have a nonempty denomination,
then replaces the unique index in one transaction. Its verifier checks the exact
index columns. Stop the writer for the paired schema/binary rollout: old and new
writers use different conflict targets. A rollback after distinct coins occupy
one old identity intentionally fails atomically; it must not delete asset rows
merely to restore the old uniqueness constraint.

## Evidence

The unchanged baseline fails the new regression: the 23-coin transfer plus one
adjacent transfer produces 4 rows instead of 48. It also accepts malformed tails.
With the patch:

- The indexer's complete `go test ./...` suite passes. Database-dependent tests
  are skipped in that invocation; they are accounted for separately below.
- `go test ./internal/bank ./internal/buffers -count=1 -v` passes with a real,
  isolated PostgreSQL 18/Timescale database; no database tests in those packages
  are skipped. It uses the actual ledger schema, formatting function, source-ID
  migration, new denomination migration and defusion table. The unrelated cron
  cleanup job is omitted from this fixture.
- The replay test starts with the old first-coin rows, then ingests both coins.
  Only the missing debit/credit is inserted, with exact signed amount/denomination
  deltas; the third replay inserts nothing. All four rows persist in the transaction.
- Tests cover 23 denominations, long IBC/factory paths, integer precision, adjacent
  event identities, malformed/duplicate coin lists and mixed-asset gameplay events.
- Schema apply/revert/reapply and verification pass. After inserting rows that
  differ only by denomination, reversal fails and preserves both rows and the new
  index. The disposable database container was stopped after testing.

`verification.json` records hashes and scope. This is real database writer testing,
not a complete block-ingestion, API projection, or deployed upgrade acceptance run.

## Remaining downstream work

New vault ownership, staking/vesting movement, efficiency, commission-revision and
rank-purchase handlers/projections still need implementation. Held-maturity bank
credits need exact accounting without duplicating transfers or ordinary completion
payments. Genesis/restart, API projections, full migration payload ingestion and
replay must then pass against the frozen chain candidate.

For historic repair, a correctly indexed first coin with missing additional coins
can use the tested replay path. A previously truncated denomination is different:
blind replay would retain the incorrect old rows and add the correctly named asset.
Rebuild or explicitly repair the affected projection under an audited procedure.
Do not call a successful replay evidence that those earlier wrong rows disappeared.
