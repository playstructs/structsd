# Substation Switchboards

## Design and implementation proposal — September 24, 2026

**Superseded design:** the subsequent discussion chose continuing maintenance and
player-discovered imbalance sabotage rather than capped permanent upgrades and
automatic efficiency reconciliation. See the [current maintenance design](v0.22.0-substation-maintenance-design.md),
including funded creation collateral. This document is retained as an alternative,
and its arithmetic prototype is not validation of the newer mechanics.

**Recommendation:** make substations configurable power converters. Owners choose
whether a station is best at forwarding power, serving connected players, or doing
both. Every station consumes some power. Alpha buys permanent efficiency upgrades.

This replaces the proposed age/wave/drift/sabotage system. It preserves its useful
goals—an energy sink, valuable infrastructure, player decisions and an alpha sink—
through routing and specialization. It deliberately offers infrastructure strategy
rather than a recurring maintenance or sabotage minigame.

Status: design proposal. The arithmetic has a standalone prototype; no chain
implementation is included. Numerical defaults below are starting points for
balance testing, not approved release parameters.

## 1. The player experience

Each substation has three selectable profiles:

| Profile | Good at | Tradeoff |
| --- | --- | --- |
| **Relay** | Sending allocations to other stations and selling power through providers | More power is lost when serving its own connected players. |
| **Community** | Supplying its connected players | Forwarded power is more expensive. |
| **Balanced** | Running a mixed network | Neither specialized efficiency is available. |

A guild might operate a relay station supplying several community stations. A
small group might use one community station directly. A merchant serving players
and selling agreements might prefer balanced operation. Extra hops always cost
power, so adding infrastructure must serve a purpose.

The recurring decisions come from changing demand: admit more players and share
the local supply, sell more power and leave less for residents, upgrade a busy
station, shorten a route, or buy supply from another operator. There is no timer
requiring players to check in to avoid an unexplained penalty.

Stations gain value through invested alpha, useful supply relationships, existing
tenants and a known role in a guild. Upgrades stay with the station when ownership
changes. Age can remain descriptive; it grants no hidden economic advantage.

### A concrete example

With 1,000,000 incoming power, sixteen connected players and no upgrades:

| Power allocated onward | Relay: power/player | Balanced: power/player | Community: power/player |
| ---: | ---: | ---: | ---: |
| 0 | 42,875 | 52,675 | **57,575** |
| 200,000 | 33,566 | 40,174 | **40,789** |
| 600,000 | 14,949 | **15,174** | 7,217 |
| 800,000 | **5,640** | 2,674 | Cannot support these outgoing commitments |

The outgoing allocation is the same delivered amount in every column. The
difference is how much incoming power is consumed delivering it and how efficiently
the remainder serves players. No profile wins in every situation.

The interface should preview these outcomes before a profile change or new sale.
It should explain, for example: “This contract delivers 200,000 power, consumes
232,559 of your incoming supply, and leaves 40,174 per connected player.”

## 2. Rules selected for the first version

| Decision | Recommended rule |
| --- | --- |
| Energy sink | Fixed operating overhead plus conversion loss on both output channels. |
| Profiles | Relay, Balanced, Community; no player-defined coefficients. |
| Upgrade tiers | 0–3; permanent; each tier improves both conversion rates by one percentage point. |
| Retuning | Free, authorized, with a 60-block cooldown after a successful change. About six minutes at six-second blocks. |
| Existing contracts | A voluntary profile change must still support all outgoing allocations. Otherwise reject it. |
| Connected players | Keep the current shared connection share; no individual power guarantees or new membership caps. |
| Alpha | Creation and upgrades burn alpha paid from an explicitly authorized vault. No escrow or bounty account. |
| Contributions | Incoming contributions remain open, subject to valid routing. More input cannot reduce output capacity. |
| Supply loss | Existing brownout behavior and bounded GridCascade continue to apply. |
| Loops | Allow multi-station cycles. Enforce real conversion loss and bounded propagation; retain existing direct self-connection rejection. |
| Time | Only a retuning cooldown; no aging, accumulated debt, oscillation or periodic maintenance worker. |

These are recommendations I have selected so the proposal is implementable without
a long list of unanswered economic rules. The initial old-to-new routing restriction
was removed after review: economic dissipation does not require ordering station IDs.
Safe cyclic propagation is an explicit implementation and acceptance requirement.

## 3. Exact power accounting

Keep outgoing allocation amounts in **delivered power**, as they are today.
Contracts, provider rates and consumer receipts retain that meaning.

Let:

- `R` = sum of incoming allocation power, before station losses.
- `H` = operating overhead; proposed starting value: 20,000 power.
- `L` = sum of outgoing allocation power, including provider agreements.
- `N` = connected player count.
- `er`, `ep` = relay and player conversion efficiency in basis points.

Tier-zero profiles:

| Profile | Relay efficiency `er` | Player efficiency `ep` |
| --- | ---: | ---: |
| Relay | 9,400 (94%) | 7,000 (70%) |
| Balanced | 8,600 (86%) | 8,600 (86%) |
| Community | 7,000 (70%) | 9,400 (94%) |

Tier `t` adds `100 × t` basis points to both values. At tier three the best channel
is 97% efficient, so upgrades never eliminate transmission loss.

```text
A = max(0, R - H)                       # input available after overhead
C = floor(A × er / 10,000)              # maximum outgoing delivered power
D = ceil(L × 10,000 / er)               # input reserved for existing allocations
P = floor(max(0, A - D) × ep / 10,000)   # total player-delivery budget

available outgoing capacity = max(0, C - L)
connection share = floor(P / N), or 0 when N = 0
```

Use integer arithmetic. Ceiling division is `(numerator + denominator - 1) /
denominator` in an arithmetic width that cannot overflow. Do not round each inbound
allocation separately: aggregate incoming power first, then apply the formula.
Likewise, calculate relay draw from aggregate outgoing load. Splitting one allocation
into many must not improve the station's conversion rate.

Calculate `R`, intermediate products and `D` exactly. Clamp the final `C` and total
player budget `P` to the supported uint64 power maximum before publishing them;
divide that clamped `P` by the connection count. Extra input beyond representable
output remains unused. This preserves correct subtraction from raw input when a
very large incoming allocation is later removed.

### What is consumed, what is merely unused

The station reserves its overhead and extra input required by conversion. This
reduces usable grid power; it does not debit alpha or invent a banked energy token.
Unclaimed local capacity is unused capacity, not an accumulated battery or a
claimable reward. Display unused capacity separately from conversion losses.

Outgoing contracts have priority over the shared local remainder, matching the
current relationship between outgoing reservations and connection capacity. New
contracts can reduce residents' shares. That consequence must be shown in previews.

In a healthy station, `L + P <= R`. Local integer division can leave a small unused
remainder. When supply drops below commitments, local share clamps to zero and
GridCascade sheds outgoing load using its existing bounded process. The design does
not claim instantaneous network-wide conservation during that pre-existing repair
window; downstream stale allocations can persist until processed.

### Why this fits the existing system

For substations, the existing `capacity` grid attribute becomes `C`: the maximum
deliverable outgoing power after losses. The existing `load` remains `L`: outgoing
delivered commitments. Their units still match, so allocation admission and ordinary
GridCascade compare like quantities.

The connection-share calculation changes to the formula above. It must not use
`(C - L) / N`, because the two output channels now have different efficiencies.
Raw input `R` is stored separately and maintained by allocation deltas.

No efficiency changes merely because another block arrived. A station needs
recalculation only after input, outgoing load, profile, tier or connection count
changes. Read-only queries neither mutate state nor enqueue work.

## 4. Alpha spending and ownership

Suggested prototype prices:

| Action | Burn |
| --- | ---: |
| Create a tier-zero station | 100,000 ualpha |
| Upgrade 0 → 1 | 300,000 ualpha |
| Upgrade 1 → 2 | 1,200,000 ualpha |
| Upgrade 2 → 3 | 4,800,000 ualpha |
| Change profile | No alpha payment |

A jump across tiers pays only for the tiers climbed. Tier three is the maximum;
there is no renewal, downgrade refund or founder multiplier. Destroying a station
does not refund its creation or upgrades. Recreating it starts at tier zero.

The numbers must be evaluated against starter power, current stations and the
alternative of obtaining more reactor power. In particular, the overhead cannot
make a normal starter station unusable. Do not ship these prices merely because
the arithmetic prototype uses them as a design reference.

Use existing player/guild vaults. The default payer is the signing player's vault;
a guild payer must be named and separately authorized. Naming a guild or another
player as station owner does not authorize debiting that owner's vault.

Creation/upgrades require the signing key's `PermTokenTransfer`, the appropriate
vault authority, and existing station/source authority. Retuning requires station
`PermUpdate` and its address-level ceiling. Preserve existing guild rank authority
and ownership-transfer policies; add no permanent personal grant as a side effect.

Burn through the existing bank module path and emit ordinary coin/burn events plus
the station action event. No new escrow address, withdrawal mechanism, association
type or financial-history store is needed.

## 5. Retuning, upgrades and everyday operations

A retune is accepted only if the station exists, is not closing, the signer is
authorized, the profile is valid, the cooldown has expired, and the proposed
forward capacity still covers `L`. A no-op is rejected without consuming cooldown.

Set the next retune height only after success. Failed transactions must neither
spend money nor reserve the cooldown. Upgrading does not clear a retune cooldown.
A tier increase improves both conversion rates and cannot reduce capacity or local
share for unchanged inputs and load.

Retuning can lower local shares while keeping everyone connected. Include minimum
acceptable outgoing capacity and connection share in the retune request, so a
quoted result can fail cleanly if state changes before execution. Those limits
are chosen by the authorized operator; they are not individual tenant guarantees.

An operator who wants an otherwise-incompatible profile must first reduce its
outgoing commitments through existing authorized cancellation/resizing paths.
There is no new force-retune bypass for other parties' allocations or agreements.
An automated allocation reserving the station's entire output can therefore limit
retuning until it is legitimately changed or removed.

Directly changing a station's input cannot hurt it at fixed profile, tier and load:
the formulas are monotone in `R`. This matters because outsiders can contribute
allocations. There is no input-dependent maintenance multiplier to manipulate.

Deleting a station continues to use the existing bounded deletion lifecycle. Its
burned investment disappears with it; existing contract settlement and connection
migration behavior remain authoritative.

## 6. Allow loops; bound the work of updating them

Stations may feed older or newer stations. Multi-station loops are allowed; the
existing direct self-connection rejection stays in place. No ancestor search,
creation-order restriction or mutable graph rank is introduced.

### Real loss prevents self-sustaining power

The proposed loss is applied to actual usable output, not merely to admission
while old commitments keep their full power indefinitely. At a consistent settled
state, each station's delivered output is strictly below its incoming power.

For a group of stations, let `E` be external input, `F` the total power carried
on internal edges and `U` useful output leaving the group, including player shares.
Every conversion rate is at most `q = 0.97`; overhead only strengthens the bound:

```text
F + U <= q × (E + F)
(1 - q) × F + U <= q × E
```

With no outside input, nonnegative `F` and `U` must both be zero. With outside
input, circulating more power consumes more of that input in losses. A loop does
not generate additional useful power. Raw incoming totals can count the same
circulating flow at several stations, so they must not be labeled fresh generation
or used as a reward for useful energy production.

This argument requires all output paths to use the new accounting, no efficiency
of 100% or more, safe rounding and correct aggregates. It describes settled state;
it is not proof that an implementation always reaches that state safely.

### Economic convergence and computational safety are separate

An automated allocation can change its destination's capacity, which changes
another automated allocation and eventually feeds back into the first station.
Loss limits the sustainable power, but does not alone bound the number of store
operations in a transaction or block. Integer rounding, stale caches and scheduling
also require explicit testing; a mathematical loss factor is not a proof that
an arbitrary update algorithm cannot oscillate or keep re-enqueueing work.

Use the bounded propagation described below: recompute from current cached state,
publish only actual output changes, deduplicate pending jobs, process work in a
deterministic fair order, and never recursively finish a graph in one transaction.
Do not repeatedly process a station in the same pass. Unfinished work remains
queued across blocks, with its limits visible in events/queries. Reaching a work
limit must not be mistaken for reaching equilibrium.

Before release, establish convergence and resource bounds for static, automated
and mixed cyclic networks, especially after removal of every external source.
Test rounding boundaries, intersecting loops, provider agreements, failed settlement,
restart and continuous unrelated queue traffic. If those tests expose a propagation
problem, fix its accounting/scheduling rule; an ID restriction is not the default
fallback. Secondary player power remains unavailable for onward allocation.

## 7. State, caches, messages and events

### Stored state

Add profile, tier and next-retune height to the station's canonical configuration.
Add one current raw-input aggregate per station, maintained through its cache.
Do not store samples, power histories, age curves, per-player entitlements or
per-block accrual records.

Raw input must use a bounded exact integer representation: sums of many uint64
allocations can exceed uint64 even though public capacity fields cannot. Reuse
the SDK integer/protobuf conventions, with an explicitly validated bound. Compute
before applying the existing uint64 output limit; never saturate raw input and
then subtract from the saturated value. Validate genesis and imported values.

Keep each changed object in the same CurrentContext. Update raw input and derived
capacity together; never let a nested committing context overwrite a cached outer
station total. Use deterministic sorted commits. This design depends on resolving
the currently open nested-cache ownership defect rather than adding another
independent cache-sharing convention.

### Message surface

- Extend `MsgSubstationCreate` with an optional initial profile and explicit optional
  payer owner. An omitted profile selects Balanced for new creation requests.
- Add `MsgSubstationSetProfile` with profile and minimum-result constraints.
- Add `MsgSubstationUpgrade` with target tier, payer owner and maximum accepted cost.
- Extend existing station queries with raw input, overhead, both rates, outgoing
  draw/capacity, local budget/share, cooldown and overload/pending-work status.
- Add a read-only preview for a proposed profile/tier and proposed outgoing load.

Reject unknown enum values at setters, handlers and genesis boundaries. Omitted
creation defaults must not make an unknown explicit value valid.

### Events and consumer contract

Publish station creation/profile/upgrade configuration and a coalesced power-state
event after relevant mutations. Include raw input, profile, tier, both efficiencies,
forward capacity/load, local share/count and whether downstream work is queued.
Payment events identify the station and paying owner/vault; the bank's burn events
remain the authority for supply changes. Migration publishes initial configuration
and derived values, plus ordinary brownout and settlement events.

An event reports committed local state, not a promise that all descendants have
already converged. A station may wait for bounded downstream processing. Since
efficiency itself is time-independent, clients do not need to synthesize unseen
curve changes between events. The user's separate indexer work consumes this
contract; implementing or testing the indexer is outside this plan.

## 8. Integration into existing grid accounting

Centralize the formulas in a pure helper and mutations in station-cache helpers:
apply incoming delta; refresh outgoing capacity; refresh connection share; queue
required downstream work. Do not scatter profile arithmetic across handlers.

Audit all of these existing paths:

| Area | Required integration |
| --- | --- |
| `allocation_cache.go` | `SetPower`, `SetDestination` and destruction update destination raw input, not net capacity directly; outgoing load changes refresh source connection share. |
| `allocation_context.go` | Creation/import and automated allocations use the same accounting and bounded propagation. |
| `substation_cache.go` / `substation_context.go` | Lifecycle, profile/tier, exact raw aggregate, cache mutation and deletion cleanup. |
| `grid_context.go` | Connection shares use the dual-conversion formula; cascade compares outgoing load with net outgoing capacity. |
| `player_cache.go` | Retain the one shared connection-capacity read; verify readiness and defenses observe reductions. |
| Provider/agreement paths | Admission sees net capacity; promised delivered amounts and existing checkpoint/settlement semantics remain unchanged. |
| Ante and permission maps | Register new messages, creator/asset bits, applicable throttles and spend restrictions without bypassing fixed checks through dynamic-map entries. |
| Genesis/export/invariants | Reconstruct derived accounting and cyclic pending work, and preserve retune cooldown during zero-height rebasing. |

### Propagation must stay bounded

Recomputing one station is constant work. Updating a network is not. Do not call
automated resizing recursively through every downstream station from one input
change. Queue a station whose automated output must be refreshed, including when
capacity grows. An overload-only queue check would miss those increases.

Extend the existing bounded grid work coordinator with that explicit task reason
or equivalent state. Processing must refresh automated output before deciding
whether further load shedding is needed. Any next station is queued, with reads,
visits and mutations charged to a shared block budget. Small local updates may
finish immediately only within a fixed allowance; long chains continue later.

Reuse the queue's retry/fairness protections, and do not reprocess a failed entry
in the same pass. A failed agreement settlement must retain an actionable retry
without an allocation disappearing or a second payout becoming possible. All new
work reasons survive restart/export and are removed on successful completion.

No new worker scans every station each block. No readiness check traverses its
ancestors. The branch's known limits on temporary downstream stale capacity remain
explicit and must be included in acceptance tests.

## 9. Migration policy for v0.22.0

Existing stations become **Balanced, tier zero, immediately eligible to retune**.
Preserve their IDs, owners, names and connections. Do not charge existing owners
retroactively, create alpha, or manufacture a refundable opening balance.
Lower usable power and ensuing brownouts are expected consequences of the new rule.

Before touching implementation, produce a read-only migration impact report from
the saved testnet state: input/net capacity differences, stations newly overloaded,
player-share changes, and cyclic components needing propagation after conversion.
List associated agreements and prospective brownout settlement effects. This
report is for review; it is not a new on-chain history table.

Use the existing atomic upgrade boundary. Keep pre-existing vault/reactor repairs
on their expected accounting while they run, then perform one final conversion
to the new station model. Use an explicit migration-only accounting mode if needed;
do not infer “legacy behavior” indefinitely from missing fields on live records.

Conversion steps:

1. Initialize station configuration and rebuild the complete incoming-power
   aggregates from canonical allocations in deterministic order.
2. Preserve existing routes, including cycles. Verify raw input and outgoing load
   against canonical allocations and derive net capacity and shared connection values.
3. Enqueue every overloaded station and automated output requiring adjustment,
   including cyclic components whose old promises cannot survive the new losses.
4. Verify accounting and pending-work invariants before publishing the upgrade cache.
   Let bounded propagation/cascade continue across later blocks. If brownout removes
   a paid agreement, use its full existing settlement lifecycle.

Full scans belong to this one-time migration and explicit invariants. Closing
stations remain closing and advertise no available connection service. Do not
reset their deletion progress or reconnect their players.

Genesis import must also rebuild raw/derived values rather than trust stale
exported capacity. Ordinary restart preserves state. Zero-height export preserves
the remaining retune cooldown by rebasing it, rather than granting a free retune
or blocking retuning until an old absolute height is reached.

There is no ID-based route cutting. Lower net capacity can still end allocations
and agreements through normal brownout processing. Review that impact manifest,
and rehearse convergence of existing cycles rather than assuming they are already
settled when the upgrade block commits.

## 10. Implementation sequence and completion gates

### Step 1 — Stabilize the existing branch and measure the proposal

Resolve the open nested infusion-cache consistency issue and complete the larger
readiness/combat gas review. Capture a new recoverable local checkpoint and list
the changes this feature is allowed to touch. Run the read-only migration impact
analysis and compare typical station budgets with the proposed overhead and prices.

**Gate:** understood migration consequences, cyclic-propagation feasibility and viable starter economics.

### Step 2 — Lock the integer rules with a reference model

Extend the prototype with real station distributions, multi-station examples,
upgrade economics and adversarial topology changes. Test integer boundaries and
all profile transitions. Select versioned parameters; rates and overhead should
change only through an upgrade that rebuilds affected derived state, not an
ordinary parameter update that leaves old capacities installed.

**Gate:** clear tradeoffs, no power creation in healthy accounting, and no profile
or upgrade arithmetic surprises. Fun and balance still require playtesting.

### Step 3 — Add schema, pure math and cache state

Change `proto/` and run `make proto-gen`; never hand-edit generated files. Add
configuration validation, the exact raw-input aggregate, pure conversion helpers
and cache commits. Keep construction, load, genesis and mutation invariants aligned.

**Gate:** golden arithmetic tests, unknown-enum rejection, deterministic commits,
read-only queries and complete cache rollback.

### Step 4 — Integrate every allocation and propagation path

Replace direct destination-capacity deltas with raw-input deltas followed by
derived recalculation. Adapt source-share updates, imports, deletion and automated
allocations. Add bounded work for automated-output increases and decreases, and
verify convergence of cyclic as well as acyclic networks.

**Gate:** conservation/accounting invariants, no recursive graph walk, fair bounded
continuation, and agreement teardown regressions pass against real application state.

### Step 5 — Add paid creation, upgrades, retuning and queries

Follow the existing handler pattern: signer, cached objects, authority, validation,
payment/mutation, then one commit. Wire CLI/autocli, ante maps, query previews and
events. Failed checks publish neither fees nor state changes.

**Gate:** delegated-key ceilings, player/guild vault spending, rank changes,
ownership transfer, cooldown and batch rollback tests pass.

### Step 6 — Implement and rehearse migration

Integrate the conversion after the existing repairs, with atomic failure behavior.
Test representative cyclic, acyclic, overloaded, closing and contract-bearing
stations. Rehearse against the saved structstestnet-111 state, recording its limits
as testnet evidence. Verify retained and zero-height export/import and cold restart.

**Gate:** every changed route and payment is accounted for; no stranded agreement,
stale raw aggregate or unbounded upgrade-followup work.

### Step 7 — Complete release acceptance and interface handoff

Update `test_chain.sh` and its expectations for station creation prices, upgrades,
profiles, provider capacity, shared player power and post-upgrade brownouts. Exercise
the existing mining/combat lifecycle under the new power budgets. Publish the event
and query contract and a player-facing explanation of profile and transmission-loss tradeoffs.

Run appropriate full Go, native lifecycle and restart checks on a newly identified
candidate binary. Do not reuse the September 23 acceptance hash as evidence for
this different economy. Keep indexer implementation outside this work as requested.

**Gate:** a new acceptance matrix names the exact binary, state fixtures, measured
gas/block work and remaining release limitations.

## 11. Required adversarial and regression coverage

- At fixed commitments, extra incoming power never lowers capacity or local share.
- Upgrades never lower either output budget; no retune can evade an existing contract.
- Split/merged inputs and outputs cannot improve aggregate conversion through rounding.
- Healthy delivered commitments plus local entitlement never exceed raw input.
- Zero input, below-overhead input, no players, exact-full load and brownout clamp safely.
- Multi-station loops remain usable; an isolated loop loses its output after external
  supply is removed, with bounded, convergent work. Cover automated, static, mixed
  and provider-mediated cycles; secondary player power cannot be allocated onward.
- Large incoming dust inventories do not make an ordinary capacity read scan the graph.
- Long automated chains and wide fan-out respect the block budget, converge after
  increases/decreases, and survive restart without repeated payouts or starvation.
- A failed consumer payout or teardown leaves a retryable, internally consistent job.
- Creation and upgrades cannot debit an owner merely because a caller named it;
  spending always respects signer bits and the selected vault's authority.
- Multi-message failure rolls back earlier profile changes, burns and cooldown writes.
- Retuning with many connections performs no per-player rewrite, while real combat
  readiness observes the new shared capacity within the 20M free-gas cap.
- Migration is deterministic; derived rebuilding is idempotent; old captures are not
  silently treated as new-format genesis; closing stations finish their existing work.

## 12. Prototype evidence and remaining judgment

The reference model in `build/substation-switchboard-design/model.py` generated the
example table and passed 20,000 deterministic randomized samples covering healthy
conservation, input monotonicity, tier monotonicity and the cost of extra outgoing
load. Results are in `build/substation-switchboard-design/results.json`.

Those checks establish only arithmetic properties of this proposal. They do not
establish production SDK integration, gas bounds, migration success or whether the
economy is enjoyable. The next useful experiment is a short playtest with a few
guild layouts and provider contracts, alongside the saved-state impact analysis.

Two balance risks need particular attention. Fixed per-station overhead favors
consolidation, so test whether one enormous community station crowds out interesting
guild layouts. Also, profile selection is intentionally understandable mathematics;
if playtesting finds switching trivial, the interesting decisions must come from
contracts, investment and network changes. Adding hidden timers would not solve
that problem. Tune the profile tradeoffs and upgrade prices first.

The principal tradeoff is visible: this design rewards building and operating a
useful network, with specialization and investment decisions. It does not create
an unattended-station hunting game. If that competitive minigame remains a separate
goal, add it later with a bounded effect on this stable accounting foundation.
