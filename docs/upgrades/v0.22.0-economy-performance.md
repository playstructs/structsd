## Player headroom arithmetic

Player availability and online checks use fixed-width carry arithmetic to
compare the exact sums of two uint64 capacity fields and two uint64 load fields.
This avoids wrapping before the brownout comparison without introducing a scan
or variable-size arithmetic on transaction paths. Tests use a separate `big.Int`
oracle. This fixes the aggregate read calculation; it does not establish bounded
shutdown propagation or change stored grid update limits.

## Infusion maturity bookkeeping

`DequeueMatureInfusionSweeps` now examines at most 128 raw queue rows per block.
The cap applies before deduplication and key validation; otherwise many duplicate
or malformed rows could still force an unbounded read even with few returned
infusions. Unprocessed rows remain indexed by their original completion time
and are eligible on later blocks. Processing stays in chronological/key order.
The regression reproduced the former full drain for distinct, duplicate and
malformed rows. Three bounded passes now drain 257 due rows while preserving a
future row. Reading the first batch consumes equal metered gas with 1,000 and
10,000 queued rows of equal key width.

Native staking refunds run before this Structs bookkeeping and are not held
back by the budget. `TestMaturityBacklogDoesNotDelayNativeVaultRefund` places
129 stale queue rows ahead of a real migrated vault's full withdrawal. The actual
committed maturity block credits the vault and emits the native refund events;
its zero-power infusion may still show 7M defusing until the next block. That
block clears the backlog and pending infusion without a second bank credit.
Clients should use native staking/bank events for refund completion rather than
requiring the cached `Defusing` field to reach zero in the same block.

This bounds queue enumeration and the number of reconciliations, not total

## Dependency constraints for a bounded shutdown design

The current grid provides allocation indices by source and destination.
`CurrentContext.GetAllocationsBySourceUpTo` bounds source reads, while
`GetAllAllocationByDestination` loads the whole incoming prefix. Infusions are
stored by destination/address; a player's aggregate capacity getter does not
retain a breakdown by backing reactor. Player secondary capacity reads the
connected substation's stored connection capacity. An implementation must not
replace the full reactor walk with unbounded incoming-edge or owner-position
walks elsewhere.

The accepted topology also includes cycles.
`TestGridCascade_CharacterizesCycleAfterExternalSupplyRemoval` builds two linked
substations and uses the actual AllocationCreate/SubstationAllocationConnect
handlers to connect the tail back to the head. After removal of the root supply,
three cascade passes leave both circulating allocations and an empty queue.
Each station has capacity one, load one and zero available capacity; attempts to
allocate another unit fail. This demonstrates cyclic dependencies, not free
spendable power, permanent useful energy creation or validator-hook behavior.
The direct self-link guard does not imply an acyclic multi-hop graph.

The replacement design must therefore account for all of the following before
it can close the shutdown gate:

- A bounded eligibility change at the reactor, plus authorization that consults
  current backing along affected power paths, including secondary player power.
- Scoped indices and a shared work budget covering raw rows, duplicate inputs,
  cycles, depth and multiple sources; the transaction gas ceiling is not a
  bound on infinite-meter block hooks.
- Explicit treatment of cyclic components and mixed valid/unavailable supplies.
  Recursive getters that simply trust a visited node's stored capacity can
  preserve the very stale backing they are intended to detect.
- Separate stored accounting from currently usable capacity so later queued
  updates cannot subtract the same loss twice or overwrite a fresh cache value.
- Continued operation on unrelated grids, preservation of withdrawals and key
  revocation, and indexer visibility of eligibility versus delayed row updates.

These are implementation constraints, not a completed or approved replacement
algorithm. A global pause while any cascade is pending would allow one network
to stop unrelated gameplay and is not an acceptable shortcut. Bounded cleanup
alone remains insufficient, as the stale-admission characterization above shows.

### Bounded allocation ancestry in admission

Substation headroom, allocation creation from substations and dynamic allocation
increases now validate upstream allocation accounting before admitting additional
load. One traversal shares a 2,048-unit allowance across visited objects and raw
incoming index rows; it never gives each ancestor a fresh allowance. Incomplete
knowledge reports no available capacity (or `unsupported_supply` for allocation
mutation). This intentionally refuses a healthy topology whose complete proof
exceeds the allowance. Operators must account for this complexity limit when
preparing the upgrade; the value is protocol behavior, not a production capacity
benchmark or a configurable parameter in this version.

The traversal compares each source's capacity with its committed allocation load,
requires each edge to fit within that load, and requires a substation's complete
incoming power sum to equal its stored capacity. Active recursion detects cycles;
completed shared ancestors can be reused within the check. Positive results are
not retained across checks on CurrentContext, so a subsequent cached power cut
invalidates the next admission even before commit. No accounting fields are
rewritten by validation, preserving the cascade's later settlement deltas.

Regression coverage includes the stale 296-link chain, an independent healthy
grid, a supported fork that rejoins, a cycle with positive stored headroom, a
cached supply cut after a successful check, and the shared budget boundary.
A 10,000-link imported topology stops at the same metered cost as a topology just
beyond the allowance. This is an allocation-accounting guard: stored root power
can still be stale during deferred reactor work, the full gameplay readiness
audit remains open, and existing service settlement continues unchanged.
It does not close the complete immediate-shutdown release gate.

### Bounded infusion owner lookup

The derived infusion owner index provides an owner-scoped reader with an explicit
raw-row allowance and completion flag. Malformed rows consume the allowance;
adjacent owners do not contribute work. The 1,000- and 10,000-position fixtures
have identical metered cost for the same 16-row prefix. This measures the index
reader, not canonical record verification or a complete primary-power proof.

Loaded infusion caches retain the original committed owner, avoiding a second

work remains proportional to state size and still needs production-cardinality
validation. Player readiness now consumes this index through its cache-aware
inventory reader to discount stale primary reactor contributions.

The CurrentContext inventory reader shares one allowance between raw owner-index

counts in both categories. Repeated calls can therefore have different allowance
requirements as the operation loads more caches. The 10,000-probe test verifies
early refusal, not a production admission limit.

row then requires current subject ownership, validator and delegation resolution.
These reads are not positively memoized across checks, because a later staking
transition must invalidate an earlier healthy result. Secondary ancestry still
has its own allowance; the two limits are not a shared whole-message gas budget.
Repeated checks and many positions therefore require full signed-message gas
measurements before production acceptance. Reactor commission-root proof and the
