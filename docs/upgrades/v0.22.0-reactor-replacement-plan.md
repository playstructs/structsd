# v0.22.0 reactor replacement implementation plan

**September 28 staking-policy update:** Existing delegations, unbondings,
redelegations, reward positions and native vesting accounts remain at their original
addresses. Only ordinary liquid balances move to vaults. All local SDK patches
and the fork are removed. The release uses upstream
Cosmos SDK v0.53.8; the known partial-payment slash overcharge is accepted pending
an upstream fix. [Current behavior and verification](v0.22.0-retained-staking.md) supersede
any staking/vesting relocation instructions or earlier acceptance evidence below.


Date: September 23, 2026  
Status: September 23 candidate completed local acceptance; September 24 review follow-ups are open.  
Starting point: `118b-reactors`, committed HEAD `ae08f243`, plus the existing
uncommitted economy and security work.

Replace the unshipped rank-based reactor efficiency system with flat 1:1 base
power, a validator stake-share admission cap, and an owner diversity bonus. Do
this within the existing v0.22.0 migration while preserving vaults, guild
economics, permissions, payments, events, and security improvements.

This document incorporates the replacement-plan review and the user's subsequent
decisions. The work described below is implemented, with current-candidate evidence
in the [acceptance matrix](v0.22.0-reactor-replacement-acceptance.md). It supersedes
the reactor implementation approach in the earlier economy plan, not the other
requirements of that plan.

Current execution status and the remove/retain/adapt inventory are in the
[implementation record](v0.22.0-reactor-replacement-progress.md).

## 4. Validator stake-share cap

Enforce the cap through staking hooks so native messages, authz, ICA, and Structs
handlers share one rule. Ante checks may provide ordinary authorization and
throttling, but are not the authoritative cap boundary.

September 24 ICA policy: ICA is unused, so disable hosting and clear the wildcard
allow-list in the upgrade and fresh genesis defaults. Keep the ICA cap regression
with explicit test-only enablement. Supporting gameplay through ICA remains out
of scope; see the [ICA policy](v0.22.0-ica-policy.md).

For a stake-increasing operation, calculate the post-operation share using exact
integer arithmetic:

```text
denominator = bonded-pool tokens
            + target validator tokens, if the target is not bonded

accept when:
    target validator tokens * 10_000 <= capBps * denominator
```

The denominator must be measured at the verified SDK hook boundary, after the
operation's applicable token/pool writes. Test bonded and unbonded destinations,
both redelegation source statuses, cancellation, and validator creation. This is
an inflow limit, not a guarantee that passive validator-set changes can never
leave a validator above the cap.

Use before-hook token snapshots scoped to the delegation/validator pair and
operation, then compare in the after-hook. Establish explicit snapshot overwrite,
consumption, and rollback rules for multiple messages. Normal transaction paths
must not accidentally bypass enforcement through missing snapshots. Genesis
initialization and non-increasing consensus operations need deliberate handling.

Return a typed cap error before ordinary infusion-reconciliation errors can be
deferred. Slashes and unbonding must remain able to reduce stake, including when
the validator already exceeds the cap. Verify this against real SDK hook timing,
not just the mock staking keeper.

Under the recommended activation policy, genesis/upgrade initializes the flag
from the selected validator-set definition; later activation occurs at a defined
validator-set boundary. Once enabled, a temporary outage does not disable the
cap. Bootstrap with zero bonded tokens remains supported. Validate parameter
ranges and persist/export activation explicitly. Avoid loading the full validator
set on every delegation merely to test the threshold.

All required guild-join redelegations use the same cap. Return an error if any
fails, even after an earlier one succeeded. The SDK message transaction must roll
back membership, rank, staking, related message-side payments, and their success
events. Existing ante behavior remains unchanged. Do not add optional migration,
catch-and-continue handling, or a “joined without migrating” event.

Provide a query with share numerator/denominator, cap, activation, and remaining
cap headroom. A cap-eligible result must not promise that a particular delegation
will succeed despite jail, balance, authorization, or other native constraints.

## 5. Owner diversity bonus

The owner is a player or guild. Aggregate all of that owner's addresses on the
same reactor before calculating diversity. Membership does not combine members'
personal stake into the guild's portfolio. Only guild-owned infusions count for
the guild. Generators and received allocation power are excluded.

Let `p[r]` be the owner's live reactor power after the existing commission split.
Missing, jailed, or unbonded validators contribute zero. Retain existing
stake-to-fuel and commission rounding; calculate the bonus once per owner.

```text
S1 = sum(p[r])
S2 = sum(p[r] * p[r])

if S1 == 0 or S2 == 0:
    bonus = 0
else:
    bonus = floor(
        S1 * maxBps * min(S2 * targetExtraReactors, S1*S1 - S2)
        / (10_000 * S2 * targetExtraReactors)
    )
```

Use arbitrary-precision integer intermediates and one final division. Do not
round effective-reactor counts or displayed basis points before pricing power.
Specify checked conversion into stored capacity; never permit uint64 wrapping.
Validate reachable capacity bounds and overflow handling on both transaction and
block-hook paths before shipping.

For the existing uint64 grid representation, retain the exact portfolio totals
and clip the applied bonus to `MaxUint64 - baseCapacity`. Remove the prior applied
bonus before changing base capacity, then recompute the amount that fits; otherwise
temporary saturation can discard base power. A later base decrease can restore
the previously clipped portion. Expose the applied amount separately from the
formula inputs. This retains the grid's existing ceiling without wrapping a new
bonus or claiming that power above the representable ceiling is installed.

With `maxBps = 5000` and `targetExtraReactors = 9`, equal portfolios earn
0%, about 5.6%, 11.1%, 22.2%, and 50% at one, two, three, five, and ten reactors. The bonus is owner
power; it does not mint tokens or apply a second commission to the bonus.

This rewards distribution across reactor identities, not proven independent
validator operators. Portfolio splitting can sometimes increase total bonus:
`[1000,10,10,10,10]` earns 4, while owners holding `[1000]` and `[10,10,10,10]`
earn 6 combined. Document and test this limitation; do not add identity tracking
to solve it in this release.

Deposits can reduce total owner power under this curve. The user explicitly
accepts that behavior: apply the capacity decrease and normal GridCascade; the
interface will explain it. Readiness must still avoid overstating the live bonus
when stored infusions lag staking. See D3 in the revised review for the concrete
2,859-to-2,855 example and the required live-portfolio accounting.

### Current state and cache behavior

Store current power per `(owner, reactor)` and current `S1`, `S2`, and applied
bonus per owner. This is derived current state, not a history of changes. Remove
zero position rows and unnecessary empty owner summaries.

Reconstruct the owner-scoped `Address/owner/` index from canonical address
associations during upgrade; normal association writes maintain it thereafter.
This lets readiness discover native stake even when a failed hook left no
infusion row. Include the associated player or guild vault separately.
`ReactorDiversity/ready` marks completed reconstruction: genesis and upgrade
suspend live diversity updates while rebuilding flat backing, then publish the
derived state and marker atomically. Neither record is activity history.

Use `CurrentContext` caches for these records. When a position changes from `old`
to `new`, update its owner's totals by `new-old` and `new*new-old*old`. The existing
owner-capacity mutation path is the integration point; generator changes bypass
diversity accounting. Re-homing updates both owners.

Implement one owner-bonus refresh operation that runs before a dependent capacity
read and before commit. It consumes dirty totals, applies the bonus difference,
and uses the existing propagation behavior for automated allocations and cascade
queueing. A bonus-only capacity change must not feed back into the reactor
position totals. Flush remaining dirty owners deterministically before committing
dependent caches. Extend the cache architecture tests to cover the new maps.

Do not solve nested-context problems with additional reads at commit alone.
Staking hooks that commit can invalidate an outer cache's infusion, owner index,
capacity, and diversity summary together. Finish hook-driven work before loading
dependent outer caches, or explicitly reload/rebase affected state at the known
boundary. Add a regression proving all four representations remain consistent.

### Outages, repair, and parameter lifecycle

Live readiness recomputes usable owner contributions within the existing
owner-scoped inventory budget and discounts stale base power and excess stored
bonus. Reads do not mint newly available capacity; ordinary reconciliation does.
Preserve cross-owner isolation and repeated-check behavior. The existing
2,048-row limit remains a known limit; the replacement must not claim to remove it.

Native portfolio discovery separately bounds owner addresses and delegations to
2,048 each. If either inventory is incomplete, withhold the uncertain bonus;
continue the existing conservative base-power checks. An incomplete infusion
inventory still cannot establish usable primary capacity. Expose both inventory
statuses in the owner query so clients can distinguish an unavailable projection
from a proven zero bonus. Cache native validator reads within one readiness check,
never across calls that may straddle a staking change.

Persisted cleanup remains bounded. If the loss of a reactor or diversity bonus
causes a brownout, existing GridCascade may shed allocations and settle their
agreements. No per-block owner-wide or chain-wide diversity scan is introduced.

Register an invariant that reconstructs totals from stored reactor infusions and
compares positions, summaries, and applied bonuses. Separately verify live
eligibility while cleanup is pending; stored accounting consistency alone cannot
prove that a stale position is currently usable.

For this release, the recommended parameter lifecycle is genesis/upgrade only.
Changing slope or maximum requires rebuilding bonuses and applying capacity
deltas through a reviewed upgrade. An ordinary parameter setter must not leave
existing owners indefinitely priced at different settings.

## 6. Preserve repair safety and resolve adjacent findings

Keep the existing commission revision/certification protection and finite repair
interval until a smaller replacement proves the same properties. These protect
slash accounting independently of historical efficiency. They may be renamed or
simplified, but their guarantees are not in the efficiency deletion budget.

The worker must bound reads, writes, retries, and events per block; preserve fair
progress across reactors; and prevent stale commission from backing new
allocations before repair completes. Permissionless restart is not evidence that
a healthy source should lose eligibility.

Address the outstanding findings as separately reviewable changes:

| Finding | Required outcome |
| --- | --- |
| Guild-sale treasury ranks | Accepted existing behavior; no change requested. Preserve ownership, membership, and unrelated direct grants. |
| Repeated failures rewind repair | Preserve forward progress while retaining failures behind the cursor for a later bounded retry. Also test a persistently failing early row, a new slash during repair, and continuous insertion. Merely ignoring another enqueue is insufficient. |
| Proxy joins a closing default entry substation | Check admission on the default path and prove rejection preserves the player's membership and connection state. |
| Nested commit leaves stale owner index | Fix the overlapping cache lifecycle and prove owner, index, base capacity, and diversity totals agree. A stored-previous-owner lookup by itself is not the complete fix. |

Reproduce each issue first. Add the regression with its fix, before layering
diversity onto the affected ownership and repair paths.

## 7. Migration, genesis, continuation, and events

Keep one atomic v0.22.0 upgrade handler. Preserve the dependency order of the
existing queue repairs, fuel/security repairs, guild permissions, vault asset
relocation, derived index rebuilds, and module migrations. Remove only the
efficiency phase and its feature-specific activation/event work.

After final infusion ownership, flat-power backing, and required indexes are
established, build diversity positions and summaries from that canonical state.
Apply the owner bonus once, propagate resulting grid changes, and initialize cap
parameters/activation before publishing the completed upgrade. Set the exact
phase order from dependencies in code and test the complete handler; do not
invoke selected repair phases as an alternative upgrade procedure.

Every phase shares the outer SDK cache. A failure publishes no partial migration
state or success events. Existing vault addresses, asset routing, stake/reward
ownership, and retained native accounts must still match their migration contract.

The diversity addition increases a correctly repaired baseline. The complete
upgrade may still reduce capacity through existing fuel, ownership, or backing
repairs; preserve their intended cascade consequences. Report base repair and
bonus deltas separately in the rehearsal comparison.

Genesis import excludes derived capacity and load from the exported GridList.
Rebuild positions, totals, and capacity from canonical infusions, then apply the
bonus exactly once. No separate applied-bonus genesis field is required merely
because GridList exports capacity. Preserve the validated asset-owner importer,
including vaults, retained native addresses, unbonding-only rows, and maturity
appointments. Test normal and zero-height export, pending repairs, persisted cap
activation, and native database restart.

Add typed diversity events and queries exposing owner, applied bonus power, and
the formula inputs or clearly rounded display values. Distinguish stored/applied
accounting from a live usable projection when repair is pending. Emit zero-bonus
transitions so indexers can clear prior values. Coalesce unchanged/repeated writes
where possible without dropping real committed changes; use deterministic order.

Preserve vault-address associations, bank/staking movements, and ordinary grid
and infusion events. Verify rejected joins and failed upgrades publish no success
events. Genesis/rebuild delivery must let consumers reconstruct the new state.
Indexer implementation and downstream ingestion testing remain user-owned work.
