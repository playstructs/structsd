# v0.22.0 ICA hosting policy

September 24, 2026. The user confirmed that Interchain Accounts (ICA) are not
currently used. Disable inbound ICA hosting for this release instead of adding
support for gameplay through a second execution path.

## Scope of the completed review

The pinned ibc-go v10.7.0 host authenticates the ICA signer and checks the message
allow-list, then dispatches messages directly through the message router. The
inner messages do not pass through Structs' transaction ante chain. Handler
permissions and staking hooks still apply; ante-only message restrictions and
quotas do not automatically apply. Allowing `authz.MsgExec` can also expose
messages nested beneath an allowed top-level wrapper.

The existing reactor-cap ICA test proves hook enforcement, batch rollback and
same-context retry for protobuf and proto3 JSON packets. It explicitly enables
hosting in its fixture and calls the host keeper. It does not certify gameplay
support, IBC proof verification or a full remote-chain/relayer lifecycle.

The saved `structstestnet-111` export has hosting enabled with `allow_messages:
["*"]`, but no ICA accounts or channels. That historical export is not evidence
of current mainnet configuration; the release decision also uses the user's
confirmation that ICA is unused.

## Release behavior

- Fresh application and CLI genesis defaults set `host_enabled: false` and an
  empty `allow_messages` list.
- The v0.22.0 upgrade applies the same policy after module migrations, inside the
  existing atomic upgrade cache. A later failure rolls back the policy and event.
- The installed ICA IBC module rejects incoming channel handshakes and packet
  execution. The empty list also denies messages if hosting alone is re-enabled.
- Existing account and channel records are retained. The ICA controller and
  ordinary ICS-20 token-transfer configuration are unchanged.
- The successful upgrade emits `ica_host_policy` with `host_enabled=false`,
  `allow_messages=[]` and `upgrade=v0.22.0`.

Re-enabling hosting requires an explicit supported-message policy. Review
dispatch wrappers and all required authorization, charge and quota rules before
allowing gameplay. Do not restore the wildcard as a convenience default.
