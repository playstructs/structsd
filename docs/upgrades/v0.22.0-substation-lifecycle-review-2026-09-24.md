# Substation lifecycle proposal review

September 24, 2026. Review of the supplied braindump against the current workspace.
This is feedback, not an approved implementation plan. No gameplay implementation
was changed for this review.

## Assessment

Paid infrastructure, visible maintenance cycles and permissionless sabotage could
give substations a useful identity. Keeping current state small and letting players
discover targets off-chain also fits the chain's constraints.

I would not implement the complete proposal as written. Its largest gaps are the
meaning of drift, treatment of existing commitments, connection accounting and
bounded repair. These determine both gameplay and correctness; the curves should
be chosen after those rules. Several claims about the existing code are outdated.

I accept the stated decisions: sabotage is judged at submission time; owners may
sabotage their own station; the upgrade may reset existing stations rather than
preserve old economic promises; and ordinary supply withdrawal still invokes
GridCascade. Those decisions do not require reopening here.

## 1. Update the baseline before designing around it

The old recursive `CheckSubstationSupply` implementation is absent from this
branch. [GetAvailableCapacity](../../x/structs/keeper/substation_cache.go) uses
clamped local capacity/load accounting. Player secondary power uses the station's
shared connection-capacity attribute. The proposal's DFS performance arguments
and its claim that this checker currently rejects cycles cannot be used as evidence
about the current branch.

[GridCascade](../../x/structs/keeper/grid_context.go) has a shared work budget and
persistent queue. A brownout is not guaranteed to finish in one or two blocks.
[Substations](../../proto/structs/structs/substation.proto) also already carry
deletion state, and deletion is bounded. These protections must survive this work.

Creation has no alpha payment today, but it requires an unconnected allocation
and is subject to transaction controls. Adding an alpha price is still meaningful;
it should not be justified as fixing completely unconstrained creation.

## 2. Existing commitments turn this into a power-credit system

Suppose a station receives 100 power and promises 90. Its efficiency later falls
to 50%. If it still delivers 90, the 40-power shortfall is an intentional credit
allowance. Recording drift does not consume that credit or guarantee its removal.

That can be a valid game rule. It is different from continuously losing power on
every hop. Existing allocation amounts remain unchanged, so existing chains do
not automatically decay to zero. An admission check only constrains new promises.
The proposal therefore does not establish either cycle elimination or shorter
graph traversal as a consequence of efficiency.

There is also a liveness choice: if the pool is empty, tiny, or uneconomic to
attack, who ends the excess service? A maximum escrow caps rewards, so arbitrarily
large drift cannot guarantee somebody will repair it. Decide whether indefinite
excess service is acceptable when nobody intervenes. If it is unacceptable, the
model needs a deterministic limit or fallback, not solely a bounty expectation.

**Question:** Is the goal an actual reduction in delivered power as efficiency
falls, or continued delivery with a growing risk of disruption? The document
currently describes the second while claiming benefits of the first.

## 3. Drift does not currently have a consistent definition

`D += max(0, commitments - throughput) × elapsedBlocks` produces accumulated
shortfall. It never decreases. Adding input stops new shortfall; it cannot erase
the past. That conflicts with “drift reverses through ordinary play.”

Choose between:

- **Recoverable stress:** overload raises it; spare capacity cools it at an explicit
  rate. This matches the transformer metaphor and gives ordinary repair a benefit.
- **Historical shortfall:** it persists until a specified reset/payment/sabotage.
- **Current instability:** a present imbalance and its duration, with explicit rules
  for when recovery resets the duration. This is not accumulated unpaid service.

My preference is recoverable stress, with a clear grace period and capped recovery
rate. It still needs precise arithmetic, including what happens when input is zero.
If one dust change can erase weeks of stress, upkeep and sabotage can both become
irrelevant. If healthy operation never reduces it, normal recovery feels ineffective.

Specify the units too. Absolute power-blocks make a large station cross a fixed
threshold much faster than a small one at the same percentage overload. If the
intended rule is equal tolerance for equal relative neglect, normalize stress or
scale the threshold. Changing that denominator must not itself erase accumulated
stress or let a temporary incoming allocation conceal it.

There is a second inconsistency: lowering load to today's throughput does not stop
future drift permanently when efficiency continues to oscillate. The next trough
can restart it without the owner making a new commitment. Re-syncing after the
bounty drain is necessary, but does not prove that the harvest loop terminates.

**Question:** After a station becomes healthy, should its stress clear immediately,
cool gradually, or remain until an explicit repair? How long should recovery take?

## 4. The proposed checkpoint shortcut is not equivalent to provider billing

The existing [provider checkpoint](../../x/structs/keeper/provider_cache.go) can
multiply load by elapsed blocks because load is constant between correctly ordered
mutations. Your efficiency changes with time even when no mutation occurs.

For example, with load 80, throughput 50 for 90 blocks and throughput 100 for the
last 10 blocks, actual positive shortfall is 2,700 power-blocks. Pricing the entire
interval at the final throughput records zero. An owner could automate a trivial
interaction at favorable phases; this need not represent meaningful maintenance.
Open incoming allocations could give other players ways to trigger such checkpoints.

“Sample-and-hold” normally means holding an earlier sampled value for the interval.
Retroactively applying the ending value is a separate policy. Either approximation
must be named and evaluated as gameplay, not treated as exact lazy settlement.

An epoch loop is also not bounded merely because one year has 365 days. Dormancy
has no natural maximum, and a fixed-period loop grows with chain age. Conversely,
clipping a simple piecewise-linear curve at zero does not inherently prevent exact
integration: segment crossings can be calculated. The combined age, pool and
variable-frequency model is what makes a cheap exact formula difficult.

**Recommendation:** begin with one fixed-period, integer-defined curve and choose
either a proven bounded integral or an explicitly different checkpoint-based rule.
Do not retain a record for every block or epoch. A few current accumulators are
compatible with the earlier decision to avoid historical billing logs.

## 5. Connections are the largest accounting change

Current station `load` is outgoing allocation reservations. Connected players share
the remainder: `(capacity - allocationLoad) / connectionCount`. Their actual struct
usage is not included in station load. See
[UpdateSubstationConnectionCapacity](../../x/structs/keeper/grid_context.go) and
[GetCapacitySecondary](../../x/structs/keeper/player_cache.go).

If connections keep individual grants, the station needs an aggregate of those
promises as well as per-connection state. Otherwise admission can spend the same
capacity twice. A station with 100 throughput, 40 allocated out and a retained
60-power player grant has no room for a new 60-power player grant.

This affects sabotage too. If retained player grants alone exceed throughput,
destroying every outgoing allocation cannot restore balance. “Do not disconnect
players” is feasible; “never reduce their grants” may prevent repair entirely.
Counting actual player consumption instead would couple local station accounting
to many combat/build changes and is substantially more expensive.

Your willingness to reset state at upgrade solves old-state migration. It does
not decide whether a player joining on Tuesday retains a different promise from
one joining on Wednesday after the upgrade.

**Recommendation:** retain a shared connection share for the first version. Let
explicit re-sync change that share while keeping memberships/connections intact.
Be clear that attached players can brown out after a re-sync.

**Question:** Do you want to preserve who is connected, or also preserve each
player's previous power entitlement? These are different promises.

## 6. Sabotage verification can be cheap; sabotage repair is not constant work

A local difficulty check and hash verification can be bounded. Destroying thousands
of allocations, settling their agreements and propagating grid changes cannot be
done as one constant-cost transaction.

The current GridCascade stops when load fits **raw** capacity. Enqueuing a station
whose load exceeds adjusted throughput but still fits raw capacity will not make
it shed anything. Sabotage needs an explicit repair target/state and bounded
continuation, while ordinary age changes must not accidentally trigger global
per-block reconciliation.

Define the lifecycle before paying the bounty:

- Which commitments are shed first? Can attackers manipulate that priority?
- Does the accepted sabotage freeze its repair target, or can it move during repair?
- May players add commitments while repair is pending?
- When is the bounty paid, and how is a second payment prevented across retries?
- What happens when agreement settlement fails halfway through bounded work?

Reuse the existing settlement rules: checkpoint providers before changing load,
pay consumer obligations correctly, and do not strand agreements after an error.
The [agreement teardown](../../x/structs/keeper/agreement_cache.go) protections are
especially relevant because this feature creates another teardown trigger.

For proofs, bind work to the chain, station, submitter/reward recipient and a
station sabotage nonce. Increment that nonce on success, reject below the stress
threshold, and make pending repair ineligible. This prevents replay and copied
proofs from being redirected to another recipient. Submission-time eligibility
already accepts that upkeep can invalidate work; that does not require a new debate.
Failed proofs must not reserve a target-wide slot that blocks valid sabotage.

## 7. The bounty economics need tuning and adversarial examples

Only the burned portion is a permanent alpha sink. Escrow temporarily locks alpha;
bounties redistribute it. Maintain actual bank backing for the pool, not merely a
grid counter. Lifetime upkeep and remaining escrow are distinct quantities.

“The economics work out without tuning” is unsupported. Expected hashwork depends
on the chosen difficulty representation; a difficulty exponent and a hash target
scale differently. Reward is bounded by available escrow, and submission races
reduce expected reward further.

Self-sabotage does not require an identity ban. It does require comparing a closed
loop: deposit, burn, deliberately overcommit, collect one's own bounty, and repeat.
The effective maintenance cost may be far below the nominal payment. Also test
colluding owners/providers and the cancellation consequences of shedding paid
agreements. Bounties must come only from the station's escrow, never agreement
collateral or a guild's unrelated funds.

Dropping the founding multiplier initially would remove one source of re-founding
arbitrage. Define deletion/refund rules too: deleting and recreating must not become
the easiest way to recover escrow or erase maintenance consequences.

**Questions:** What fraction burns, what fraction becomes escrow, and what happens
to unused escrow on deletion? Is anyone allowed to fund another station's upkeep?

## 8. Scaling upkeep is useful, but raw incoming power is externally controllable

The suggested direction makes sense: a small station should need less alpha for
the same maintenance quality. But incoming allocations deliberately remain open.
An outsider can change raw input, then withdraw it.

If raw input directly sets upkeep cost, phase, or sabotage thresholds, helpful-looking
contributions may make the receiver worse off. Test the complete resulting
throughput function for monotonicity; a lower efficiency percentage alone does not
prove harm, but neither does increased raw input prove safety.

**Idea:** scale buffer requirements with promises accepted by the station, rather
than unsolicited input. For example, an explicitly maintained commitment total
could set a saturating coverage ratio `escrow / (baseRequirement + k × commitments)`.
Use reservations, not actual usage that would require scanning connected players.
Changing this denominator must still settle the previous interval first.

## 9. Resolve the lifetime curve before adding more knobs

The prose requires a monotonic age advantage; your last answer favors repeating
good and bad periods. A repeating curve alone does not create a permanent maturity
advantage. A capped maturation curve multiplied by a repeating maintenance cycle
could provide both, but that is a choice rather than a resolved requirement.

“Every older station's trough beats every newer station's peak” is also too strong
for a continuous age curve with nonzero oscillation. A practical target would be
that a fully mature station performs better than a brand-new one over a defined
comparison window, without making the first generation permanently unbeatable.

**My preference:** a nonzero starting efficiency, modest capped maturation, a fixed
period with per-station phase, and a buffer that only improves the downside. Keep
efficiency at or below 100% if the goal is transmission loss rather than extra
generation. Postpone upkeep-controlled frequency, phase nudging and founding bonuses.

A phase derived from a predictable ID can be selected by choosing when or how many
stations to create. It staggers phases; it is not unmanipulable randomness. Creation
cost and acceptable phase selection should be considered together.

Show the maintenance curve and upcoming danger clearly. Attachment through useful
infrastructure and tenants is stronger design ground than relying on players not
noticing future costs.

**Question:** Should age provide a capped lasting benefit, or should all stations
repeat the same lifecycle regardless of how long they have existed?

## 10. Migration, permissions and release scope

An implementation needs explicit initial age/phase, pool, stress, checkpoint and
connection values for every existing station, including closing stations. Resetting
is acceptable under your instruction, but the reset must not mint a bounty pool
without backing. A zero-height export must preserve economic age/phase/stress through
rebasing or offsets; merely resetting birth heights changes the economics.

Payments need signing-key `PermTokenTransfer` and the correct player/guild vault
authority; permission to operate a substation does not authorize spending its
owner's wallet. If creation still allows naming another owner, the creator must
not thereby debit that owner's vault. Define maintenance versus administrative
authority, ownership transfer of escrow/obligations, and foreign sabotage separately.

Predictable escrow addresses must tolerate unsolicited deposits without blocking
creation or inventing upkeep credit. Reuse the branch's vault/account hardening
where applicable, and publish address associations, payments, burns, pool changes,
sabotage acceptance/completion and shed-allocation events accurately. Time-varying
read-only efficiency will not emit an event every block: clients need parameters,
checkpoint state and query height to derive/forecast it. Indexer implementation
remains the user's separate responsibility.

Use deterministic integer/fixed-point arithmetic, specified rounding and bounded
inputs. Avoid floating-point trigonometry in consensus. Test maximum age, zero
input, depleted pools, same-block changes, overflow and import/restart behavior.

For 0.22.0, I would first resolve the open owner-cache and worst-case readiness gas
findings. This proposal touches the same caches, grid propagation and agreement
settlement, so it creates a new acceptance gate rather than inheriting the previous
native lifecycle result. Include `test_chain.sh`, paid agreements, full vault
permissions, migration/restart and adversarial fan-out in the new coverage.

## Suggested next design pass

Settle three decisions first: continued excess delivery versus actual throughput
loss; how stress recovers; and whether re-sync may reduce connection shares. Then
write a small simulation covering steady operation, long absence, repeated troughs,
large/small stations, self-sabotage, empty pools, open input changes, cyclic graphs
and competing saboteurs. A simulation would test incentives; it would not substitute
for keeper invariants or real-chain gas tests.

A smaller first version could have paid creation, a backed maintenance pool, one
integer efficiency curve, one recoverable stress measure, shared connection shares
and a bounded sabotage repair job. Defer additional oscillation controls and
individual connection promises until that model is internally consistent.
