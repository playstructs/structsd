# v0.22.0: retain existing staking positions

Decision: September 28, 2026. This replaces the earlier all-assets staking and
vesting relocation plan. It does not change flat reactor power, owner diversity,
stake caps, guild economics or fixed substation operating loss.

## Upgrade behavior

- Provision player and guild vaults and emit their address associations.
- Transfer ordinary associated accounts' liquid balances in all denominations
  using native bank events. Unassociated balances remain untouched.
- Leave every existing delegation, unbonding and redelegation at its original
  address, including validator self-stake. Preserve queue entries, operation IDs,
  holds, slashing exposure, shares and distribution starting information.
- Do not withdraw rewards or change configured reward recipients.
- Keep native vesting accounts whole, including liquid balances, original
  schedules, account identity and delegated counters. This applies to all native
  vesting accounts, not only validator operators.
- Reconcile Structs energy backing at original addresses and restore maturity
  bookkeeping. Apply the new power rules and normal GridCascade consequences.
- Emit no staking-relocation or vesting-relocation events: those moves do not
  happen. Existing wire types are retained; their presence is not an emitted move.

All phases remain inside the atomic upgrade cache. A later failure discards
vault provisioning, balance transfers, backing changes and their events.

## Player behavior

Existing associated addresses continue contributing backed reactor power under
the new rules. Their native rewards and staking operations remain accessible.
A player can undelegate using an explicit legacy delegator address, wait the
normal unbonding period, send the refunded coins to their vault, and infuse from
there. New Structs infusions without an explicit delegator default to the vault.
There is no forced unstaking, automatic delayed relocation worker or deadline.
Native vesting restrictions continue to govern which refunded coins are spendable.

Guild-required validator migration still follows existing admission and stake-cap
rules. Address registration, primary rotation and revocation retain their existing
security policies for movable delegations; they do not merge pending records.
Revocation must continue to remove compromised-key authority without allowing
in-flight staking operations to prevent eviction.

## SDK simplification

Removed the write-batching and pending-withdrawal cursor changes from SDK slash
processing, and removed the custom pending-balance context API. Ordinary native
entry limits now apply to new vault staking records; the upgrade never merges
many addresses' pending records into one oversized record.

Following the decision to pursue the slash overcharge upstream, the remaining
burn correction and the entire `third_party` SDK fork are also removed. The
chain builds against upstream Cosmos SDK v0.53.8 using normal Go module checksums.
The partial pending/active redelegation slash overcharge is an explicitly accepted
SDK limitation, not a corrected behavior of this candidate. The
[upstream report](v0.22.0-upstream-slash-overcharge.md) preserves a reproduction.
The binary builder records `go.mod`, `go.sum` and the linked module versions.

## Verification scope

Real-app tests cover byte-identical staking/distribution stores through the asset
phase, original pending IDs and queues, held maturity, native slash accounting including
ABCI evidence delivery, reward withdrawals, voluntary unbond/send/vault-delegate,
normal and zero-height export/restart, vesting preservation, event replay and
upgrade rollback. Scale fixtures now assert one native record per original
address instead of oversized merged vault records.

The Python upgrade verifiers require unchanged staking addresses and vesting
accounts. Historical merged-vault performance measurements and the old composite
vesting continuation fixture do not certify this candidate. A fresh native-chain
upgrade/reopen rehearsal remains a release gate; unit and real-app tests do not
replace it.

Validation of the retained-staking change before removing the final SDK patch
(the upstream-switch report records subsequent validation):

- `go test ./...` passed.
- The nested SDK staking keeper suite passed separately.
- All 457 Python tests passed, including retained-staking and vesting verifiers.
- Three freshly generated real-app export/event fixtures passed the independent
  Python staking, bank and vesting checks applicable to each fixture.
- SDK provenance verification passed for all 2,136 files; `test_chain.sh` passed
  shell syntax checking. Its new legacy-delegation preservation assertion has
  not yet been exercised against a running node.

No fresh native-node upgrade/reopen rehearsal or full `test_chain.sh` run was
performed for this change. Earlier merged-vault rehearsal results remain
historical evidence only.
