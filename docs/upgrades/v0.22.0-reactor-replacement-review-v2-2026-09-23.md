# Deep review of the revised reactor replacement plan

September 23, 2026. Reviewed against `118b-reactors` at `ae08f243` plus the
current uncommitted work. This reviews the revised attachment with **50% maximum
diversity at ten effective reactors and a 30% stake cap**.

Source: [revised plan](/Users/abstract/.codex/attachments/b50ec9d5-8593-4650-a672-d739aff638b7/pasted-text.txt).
SHA-256: `e013fc0ba9f1b6318e574f92c114ca7e5f46ab9b603fddc546804a5c52b74602`.

**Verdict: substantially improved, but not appropriate to implement unchanged.**
The main remaining issues are contradictory deletion instructions, shared vault
genesis behavior hidden inside an efficiency file, and accurate live-readiness
accounting with the new curve. The user has confirmed that adding stake may
reduce total power: keep that behavior, explain it in the interface, and apply
the normal GridCascade consequences when capacity falls. This is no longer an
open economic decision or a reason to change the curve.

This review supersedes the conclusions about the attachment's contents in the
[earlier review](/Users/abstract/Documents/Structs/Code/structs/docs/upgrades/v0.22.0-reactor-replacement-review-2026-09-23.md).
It does not implement the plan or certify replacement code that does not yet exist.

## What this revision resolves

The following are now sound directions in the plan, subject to implementation
and the stated tests:

| Earlier concern | Revised approach |
| --- | --- |
| Join continuing after a required migration fails | Reject the entire join and preserve transaction rollback. |
| Deleting slash safety with historical efficiency | Retain commission certification and the finite repair interval. |
| Assuming the new binary runs only after its migration | Classify activation callers and handle initialization explicitly. |
| Repeatedly disabling the cap below the validator threshold | Persist activation once reached, including across restart. |
| Bonus stale until CommitAll | Refresh before dependent reads and propagate through allocations/cascades. |
| Nested contexts repaired only by an index read | Address the overlapping cache lifecycle and test all affected representations. |
| Runtime bonus changes leave owners at different rates | Restrict bonus settings to upgrades and reject ordinary parameter changes. |
| Retry fix misses failures behind the cursor | Require forward progress and retained retry obligations. |
| Alternate accounts described as universally ineffective | State and test the portfolio-splitting limitation. |
| Tests deferred and shared files changed concurrently | Sequential phases with accompanying tests and multi-validator acceptance. |

The revised arithmetic using a target of nine extra effective reactors is also
better specified than rounding a fractional slope into integer basis points.
The displayed example percentages and the revised 4-versus-6 portfolio-splitting
example agree with the exact formula.

## Changes required before implementation

### D1 — High: the keep and delete instructions still contradict each other

**Plan locations:** Keep list, “Strip back to HEAD,” proto deletion, store-key
deletion, and tests marked “Delete entirely.”

The revised policy retains commission repair, but later instructions still say
to delete its backing state, events, and tests:

| Retained mechanism | Conflicting instruction still present |
| --- | --- |
| Commission revision/certification | Delete `Reactor/commissionRevision/`. |
| Finite repair interval | Delete `Reactor/repairSnapshot/`. |
| Commission event replay | Delete `Reactor/commissionReplayPending` and the commission-revision events. |
| Regression coverage for retained behavior | Delete `reactor_commission_revision_test`, `reactor_commission_events`, and `slash_repair_liveness`. |
| Adapt mixed files without wholesale restoration | The mixed-file list remains headed “Strip back to HEAD.” |

These are functional contradictions, not just terminology. The
[source gate](/Users/abstract/Documents/Structs/Code/structs/x/structs/keeper/reactor_energy.go:30)
uses the revision pair to refuse stale commission; the
[worker](/Users/abstract/Documents/Structs/Code/structs/x/structs/keeper/reactor_slash_queue.go:254)
publishes completion only after accounting commits. The
[replay implementation](/Users/abstract/Documents/Structs/Code/structs/x/structs/keeper/reactor_commission_events.go:11)
uses both the replay key and typed events, including restored chains starting
above height one.

**Change:** make the remove/retain/adapt inventory authoritative throughout the
document. Retain these keys, events, and behavioral tests unless a specific
replacement is designed and verified. Change “Strip back to HEAD” to “Adapt mixed
files.” Retire broad line-count estimates until the corrected inventory exists.

**Verification:** create/increase reactor-backed allocations during an unfinished
non-jailing slash; complete repair; export/restart before completion; verify
eligibility, progress, and event reconstruction throughout.

### D2 — High: a file marked for deletion also restores vault and unbonding state

**Plan locations:** deletion of `infusion_efficiency_genesis`; deletion of
`genesis_efficiency_test`; adaptation of `reactor_context` and module genesis.

The current
[GenesisImportWeightedInfusion](/Users/abstract/Documents/Structs/Code/structs/x/structs/keeper/infusion_efficiency_genesis.go:13)
does much more than preserve a weight. It resolves player/guild ownership from
validated address or vault associations before their indexes commit, reconstructs
fuel and unbonding balances from staking, checks eligibility, applies grid
contributions, and schedules maturity cleanup.

The legacy
[GenesisImportReactorInfusions](/Users/abstract/Documents/Structs/Code/structs/x/structs/keeper/reactor_context.go:59)
only traverses active delegations and resolves their addresses through the
signing-address player index. It skips an address with player index zero.
[Vaults deliberately have no such signing-player association](/Users/abstract/Documents/Structs/Code/structs/x/structs/keeper/vault_cache.go:8).
It also cannot discover an unbonding-only position after its delegation disappears.

Deleting the weighted importer and falling back to that legacy path would lose
Structs infusion/power state for vault-backed stake and miss unbonding-only
positions during export/import. Native stake would not necessarily disappear,
which makes bank-only conservation checks insufficient to detect the regression.

**Change:** extract a general asset-owner reactor importer before deleting the
efficiency file. Remove rate-history work, but preserve owner validation, player
and guild vault handling, live staking reconstruction, unbonding-only records,
eligibility, and maturity scheduling. Handle association availability explicitly;
adding a vault keeper lookup before the association exists is not enough.

**Verification:** port the existing
[six-mode genesis test](/Users/abstract/Documents/Structs/Code/structs/x/structs/module/genesis_efficiency_test.go:18)
instead of deleting it. It already covers active player vaults, guild vaults,
registered addresses, jailed/inactive validators, and unbonding-only records.
Change its obsolete weighted-power assertions, retain its ownership and maturity
assertions, and repeat the round trip with real staking/distribution state.

### D3 — Accepted gameplay: apply power reductions and keep readiness accurate

**Plan locations:** Diversity formula, Readiness, and the proposed
`min(row.Power, ratio × liveFuel)` projection.

The formula is mathematically consistent, but total power is not necessarily
monotone in deposited stake. With all values representing post-commission owner
power on healthy bonded reactors:

| Portfolio | Base power | Bonus | Total |
| --- | ---: | ---: | ---: |
| One reactor at 600; twenty reactors at 70 each | 2,000 | 859 | 2,859 |
| Add 50 to the first reactor, leaving the other twenty unchanged | 2,050 | 805 | 2,855 |

Adding 50 base power removes 54 bonus power. Conversely, withdrawing those 50
increases total power by four. This is a property of the curve, not floating-point
error. It can occur with portfolios within the existing inventory limit; the
global validator cap does not constrain an owner's portfolio enough to rule it out.
For example, another 1,000 stake distributed across the other twenty validators
keeps both portfolios comfortably within the 30% network cap.

**User decision after this review:** this gameplay effect is accepted. A deposit
may worsen a brownout. Keep the formula, explain the effect in the interface,
and trigger normal GridCascade behavior if resulting capacity is lower. Do not
add a deposit restriction, preserve an old bonus, or change the curve to prevent
the reduction.

There is also a correctness consequence. The
[current readiness projection](/Users/abstract/Documents/Structs/Code/structs/x/structs/keeper/player_primary_supply.go:128)
limits each row to its stored power, even if live staking backing is higher.
That is conservative for linear power. It is not necessarily conservative for
the new portfolio formula:

1. Stored contributions are the first portfolio above.
2. Staking contains the added 50, but infusion reconciliation has been deferred.
   Ordinary reconciliation failures are currently
   [queued rather than aborting staking](/Users/abstract/Documents/Structs/Code/structs/x/structs/keeper/hooks.go:117).
3. Clamping each live contribution to its stored value reconstructs the first
   portfolio and leaves 2,859 available.
4. The formula applied to the actual live portfolio permits only 2,855.

Thus “counting less stake cannot overstate available power” is no longer a valid
proof. The arithmetic counterexample is verified; the full staking failure path
has not been reproduced against a replacement implementation.

**Implementation requirement:** retain the confirmed curve and apply its actual
capacity changes through automated allocation updates and normal GridCascade.
Base-power credit can remain conservative, but the bonus eligibility bound must
use the complete relevant live portfolio, including higher backing that has not
yet been credited. If that portfolio cannot be established, fail closed on the
uncertain bonus. Prove behavior for missing/zero rows and deferred repairs too.
This is ordinary accounting correctness, not a guard against the accepted
gameplay effect.

Do not remember each owner's highest prior bonus: that would reintroduce
historical entitlements and prevent the capacity reductions the user intends.

**Verification:** include the example above, its reverse withdrawal, delayed
reconciliation, rebond/restoration, and an independent property test that admission
never exceeds the chosen live entitlement. A test that incremental totals equal
stored-row totals does not establish that live-supply property.

## Additional implementation contracts to tighten

### D4 — Medium: initialize and validate the new parameters before any dependent hook

The plan correctly protects bonus settings in MsgUpdateParams, but it needs an
explicit initialization contract. Existing serialized Params records decode new
fields as zero; `T = 0` makes the formula divide by zero. A zero cap can also
accidentally reject every inflow after activation.

The current [parameter setter](/Users/abstract/Documents/Structs/Code/structs/x/structs/keeper/params.go:23)
stores a record without itself validating it. Message ValidateBasic validates
Params through the router, but direct migration/genesis writes must also receive
valid values. Staking/genutil can call hooks before Structs InitGenesis sets its
own parameters.

**Change:** define defaults and validation together, including `T >= 1`, allowed
maximum-bonus range, cap range, and minimum-validator range. Specify zero/omitted
legacy values, when the upgrade installs defaults, and how fresh-genesis hooks
behave before module initialization. Keep bonus-change rejection in the handler
because it compares old and new state, not merely input shape.

For governance-updatable cap settings, state that raising the activation threshold
cannot clear an already-true activation flag. Define when lowering it activates
an inactive cap and when a changed cap percentage starts applying. Do not create
a numeric zero sentinel that unexpectedly disables enforcement.

**Verification:** old Params bytes, custom fresh genesis, no Params record in a
test keeper, invalid ranges, cap-only governance updates carrying unchanged bonus
settings, and activation across threshold changes/export/restart.

### D5 — Medium: an ICA allow-list must account for nested dispatch

The added ICA investigation is warranted. The pinned IBC implementation checks
the allow-list and account signer in
[authenticateTx](/Users/abstract/go/pkg/mod/github.com/cosmos/ibc-go/v10@v10.7.0/modules/apps/27-interchain-accounts/host/keeper/relay.go:97),
then sends messages directly to the router. It does not run the inner messages
through the transaction ante chain. The default host parameters allow all message
types; that default alone does not establish the actual production parameters.

An allow-list that excludes direct Structs messages but permits authz MsgExec
can still dispatch a Structs message underneath it. The SDK
[authz dispatcher](/Users/abstract/Documents/Structs/Code/structs/third_party/cosmos-sdk/x/authz/keeper/keeper.go:119)
even permits the same granter/grantee without a separate grant. The current
[nested-message guard](/Users/abstract/Documents/Structs/Code/structs/app/ante/nested_msg.go:10)
is in ante, so it cannot close that ICA route.

This confirms the execution-boundary concern, not a reproduced theft or complete
production exploit. Handler permissions still apply; ante-only quotas, charges,
or other rules need message-specific examination.

**Change:** give the investigation a separate release decision and explicit
scope. If choosing an allow-list, exclude generic dispatch wrappers unless their
descendants are safely checked. Apply the intended policy to fresh genesis as
well as upgrade state, and document any effect on existing ICA integrations.
Do not claim the issue is fixed by blocking only top-level Structs type URLs.

**Verification:** allowed native staking, direct disallowed gameplay, nested
authz gameplay, signer mismatch, atomic failed ICA batches, and cap rejection
through the real ICA path. The stake cap should remain effective through hooks
independently of the broader ICA policy.

### D6 — Medium: rank-purchase admission is optional, not a universal fallback

The new text says players avoiding migration use rank-purchase admission and
expects that path to succeed for the same player after a capped join fails.
The path does avoid redelegation, but it is conditional.

[RankPurchasePrice](/Users/abstract/Documents/Structs/Code/structs/x/structs/keeper/guild_rank_purchase.go:43)
requires rank purchasing and purchase admission to be enabled. The handler also
checks membership expectations, authority, rank range, destination availability,
and price; a nonzero purchase debits the player's vault in the guild token.

**Change:** say “where the guild has enabled purchase admission and the player
satisfies its terms.” “Moves no stake” is accurate; “moves guild, substation and
rank only” omits payment and application/event changes. Do not auto-enable this
setting to ensure a fallback—the user's established guild membership policy
allows guilds to choose which admission routes are open.

**Verification:** a funded player can purchase admission when enabled despite a
capped primary reactor; disabled purchase admission stays rejected; insufficient
funds and a closing entry substation also remain rejected with no partial payment.

### D7 — Lower priority: headroom depends on the funding path

For a bonded validator with 250 tokens and total bonded tokens of 1,000, a 30%
cap permits up to 71 whole tokens of new external delegation:

```text
(250 + x) / (1000 + x) <= 0.30
```

A redelegation from another bonded validator does not increase the denominator,
so it permits only 50:

```text
(250 + x) / 1000 <= 0.30
```

The proposed query's single “remaining headroom” field therefore needs semantics.
Either expose the current fixed-denominator margin as such, or distinguish paths
whose funding increases total bonded stake. Do not label the same number a
maximum for every operation. The plan's caution about balance/jail/authorization
is correct but does not explain this denominator difference.

## Simplifications and precision improvements

### Rebuild capacity at genesis; do not add a bonus export field by assumption

As established in the previous review, exporting grid capacity does not mean
import restores that capacity verbatim.
[Genesis import filters derived grid values](/Users/abstract/Documents/Structs/Code/structs/x/structs/module/genesis.go:261),
and [the filter excludes capacity and load](/Users/abstract/Documents/Structs/Code/structs/x/structs/module/genesis.go:531).
They are reconstructed from objects.

Phase 5 now prescribes export/import of the applied bonus even though the Genesis
paragraph still says to investigate it. Prefer rebuilding bonus totals and
applying the bonus once to rebuilt capacity. Only export extra accounting state
if the final algorithm actually needs it. Preserve canonical vault and unbonding
reconstruction as described in D2. Correct this point in my earlier implementation
plan as well when consolidating the final design.

### Spell out aggregate S2 deltas

“An owner's addresses on the same reactor are aggregated first” is correct.
Carry that definition into the update pseudocode: `old` and `new` must be the
old/new total for that owner/reactor pair, not one row's power.

For two addresses at 70 and 30 on the same reactor, increasing the first to 80
changes the pair's square by `110² - 100² = 2100`. Using `80² - 70² = 1500`
would misprice diversity while looking like the stated delta formula. Include
that small regression explicitly.

### Cache validator reads only within one read-only projection

The proposed per-call validator cache is sensible. Keep its lifetime inside one
live supply computation. Do not reuse eligibility or token balances across
staking mutations or subsequent readiness calls in the same CurrentContext.
Owner inventory/cache reuse and live staking freshness are different concerns.
Report gas for real active rows, as the new plan now requires.

### Preserve required migration ordering and distinguish capacity changes

“After vault phases” is necessary but not a complete placement rule. The final
importer/upgrade must have valid params, final asset ownership, repaired flat
backing, and any required indexes before building diversity totals. Hooks must
not subtract old contributions from uninitialized totals during that process.

Adding a first bonus to a correctly repaired baseline only increases capacity.
The complete upgrade still includes repairs that can reduce it. Preserve normal
cascade behavior and report base-repair deltas separately from bonus issuance.
Do not use “no cascade follows” to suppress necessary propagation or cleanup.

### Align event and documentation acceptance with the retained mechanisms

Retain commission-repair events if retaining their mechanism. Add a clear zero
bonus transition, deterministic event ordering, failure rollback, and recovery
after import at an initial height greater than one. Explain whether query/event
values are applied stored values or live usable projections during repair.

Narrow the final no-trace check to retired implementation identifiers in shipped
source/interfaces. The current broad grep conflicts with both retained generic
security concepts and dated review documents. Preserve honest evidence of what
was tested; historical reports do not certify the new candidate. The final gate
list should include the mining-enabled run already required by Phase 6.

## Decisions still needed

Treat the revised document's 1:1 base, 50% maximum at ten effective reactors, and
30% cap as the input design for this review. The old 30%-bonus/20%-cap recommendations
are superseded; this review is not asking to revert them.

The substantive remaining questions are:

1. **Is ten bonded validators the final activation threshold?** The sticky policy
   is sensible; verify the intended network's actual count and configured maximum.
   This review did not query a live network or confirm its validator inventory.
2. **Resolved: guild-sale treasury ranks remain unchanged.** The user explicitly
   chose to leave the current behavior alone. Do not clear rank grants or add
   direct-only treasury restrictions as part of this replacement.
3. **What ICA functionality must remain supported?** Decide this from verified
   deployment state and integrations before applying a restrictive migration.

Cancellation as a cap inflow and upgrade-only bonus parameter changes remain
reasonable recommendations. Required guild migration failure already means
rejection; that decision is settled. The user also explicitly accepts deposits
that lower total power, with interface education and normal GridCascade on a
capacity reduction; do not reopen that economic question.
