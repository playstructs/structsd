# v0.22.0 history retention implementation design

**Superseded by confirmed user direction, 2026-09-21:** Remove this entire added
on-chain billing-history/retention subsystem. Preserve existing elapsed-block
provider checkpoints, payment rules, cancellation/refund accounting, GridCascade
teardown and normal events. This document records work to remove, not a release
requirement. There is no outstanding checkpoint-trust or cleanup-only decision.
See the [current plan](v0.22.0-economy-plan.md#current-release-gates).

Status: incomplete implementation, 2026-09-16. Reader roots, stable enrollment
pagination, immutable reader snapshots, bounded original-window reads, durable
dependency proofs, per-reader collection continuations, snapshot-held reverse
protection, resumable per-span durable ownership handoff, and bounded snapshot
collection/protection/handoff dispatch, bounded orphan-archive cleanup and
cleanup-only retirement receipts, retained borrow lineages and atomic creation
with complete archive coverage, a persistent independent-admission boundary,
claim/interval/proof birth ownership, admission checks for mutable claim
terms, snapshot-owned proof release checks, and persistent bounded archive-release
scheduling exist. Internal terminal receipts, bounded closed-window disposal,
fixed-birth terminal scheduling, bounded retired-pool reclamation and persistent
FIFO scheduling across retired pools, deposit closure during draining, and explicit
completed-receipt reclamation through the fixed-birth dispatcher also exist.
An internal guarded per-fact pruning operation now combines completed reader
handoff, admission closure and exact dependency ownership. A finite birth-index
dispatcher persists bounded pruning visits across restarts. EndBlock releases unowned archive metadata. Terminal cleanup, pool reclamation and
boundary activation have no live callers, and no live history pruning is enabled.
Guarded scoped-tombstone reclamation now removes fact and count rows between
pruning passes, retaining an explicit absence floor and sparse genesis inventory.
Point-fact reclamation, obsolete scope-creation cleanup and guarded empty-header
reclamation now compose with the history cycle. An internal five-lane coordinator
shares its allowance with paid-prefix, terminal, pool and archive cleanup, skipping
idle lanes within that allowance. Production scheduling, aggregate resource
validation and downstream acceptance remain unfinished. This document
defines the remaining work; it is not evidence that the retention gate has passed.
The [main plan](v0.22.0-economy-plan.md#current-release-gates) remains the release
checklist. The [accounting dependency matrix](v0.22.0-agreement-service-accounting.md#retention-dependencies-and-required-deletion-order)
records which retained records currently require historical evidence.

## Guarded per-fact pruning implemented, without production activation

`PruneProtectedServiceHistoryFact` now selects and atomically applies a floor
for one fact. It requires an active matching snapshot with completed collection,
protection and durable handoff; counted pending indices must also be empty.
The persistent admission boundary must exist, and its grandfathered birth
ceiling must be covered by that snapshot. A snapshot made before an additional
pre-boundary reader therefore cannot authorize pruning.

The initial ceiling is the smaller of the admission height and snapshot seal.
The operation lowers that ceiling to the oldest exact dependency in both the
active snapshot and durable archives, including archives from earlier generations.
Scoped facts use their whole-scope dependency: an originally empty inventory
protects later insertions, tombstones and revivals. These lookups use indexed
first rows, not a scan of readers. At most 128 versions may be removed per call;
the history primitive retains its reconstruction anchor and change marker.
Gas failure rolls back the floor and version removals together.

Real-app regression coverage proves unrelated versions can be removed while an
old reader remains stalled; protected history still completes its original proof.
Each single-version batch survives service genesis export/import. Normal and
zero-height restoration preserve first-loss settlement and exact balances: the
fixture's outage at service block 2 pays 1 ualpha to the provider and 20 to the
consumer, while uninterrupted service pays 21 to the provider. Pruned and
unpruned branches end with identical financial records. An older archive holds
its dependency even after its source snapshot and reader disappear, until owned
archive cleanup completes. Corrupt pending/reverse rows and uncovered births
refuse without mutation. A two-version prune costs 26,445 gas in the fixture,
unchanged after adding 257 unrelated readers; this is a local measurement, not a
combined EndBlock budget or throughput certification.

This test exposed a separate archive restore defect before pruning: failed claims
shorten their live reader range, so comparing a frozen archive window against
that range rejected valid state after settlement. Archive validation now resolves
the retained contract end from the same claim cache. Frozen basis/seal bounds,
original revisions, prices, roots and independent proof replay remain enforced.

The internal dispatcher below is now the only allowed caller of guarded pruning;
the architecture test forbids live activation. Production scheduling, complete scope-inventory reclamation,
archived prefixes for still-live claims, combined resource bounds, native final
candidate validation and downstream acceptance remain outstanding. This operation
does not establish a total storage bound or satisfy the complete retention gate.

## Finite history pruning dispatch implemented, without live activation

History now indexes each fact's original birth by `(height, domain, scope, key)`.
A cumulative count is stored only at heights that introduce facts. Version
updates, deletion and revival retain the original birth. The index adds bounded
reads/writes to a new fact's capture; it does not allocate global sequence IDs.
Different cross-scope write orders in the same block produce identical index and
count state. Scope ordinals remain unchanged.

`BeginServiceHistoryPruning` fixes the completed protection snapshot's seal and
the fact count through that height. Facts born afterward cannot enter or extend
the pass, even when their identities sort before its cursor. The persistent
`ServiceHistoryPruningState` is additive field 25 of private service genesis.
`AdvanceServiceHistoryPruning` reserves at most 16 version-removal units for one
fact, visits at most four facts, and shares a caller allowance of 1..128 units.
It advances after a visit even when protection prevents removal or a fact has
more old versions. Later passes revisit that remainder. Completion means every
original fact was visited, not that all its history was reclaimed.

Fact-level failure commits the cursor and earlier successful visits, allowing
later facts to progress; the next pass retries it. Malformed inventory or gas
exhaustion rolls back the whole call. EOF cannot mark a pass complete unless
the visited count equals the frozen count. An unfinished pass prevents source
snapshot disposal and admission changes that would invalidate its coverage.
Completed source disposal removes the scheduler record atomically.

Genesis reconstructs birth rows and counts from the existing typed scope creation
inventory, independently of remaining version anchors. It validates the pruning
cursor against the actual original prefix, in addition to its matching completed
snapshot and admission coverage. A malformed import cannot omit the boundary and
strand an unfinished pass. Read-only export rejects missing or extra derived rows. Both service
clock modes preserve a partially finished pass and continue bounded cleanup.
Older development databases without the birth index require old-binary export
and new-binary genesis import (or a fresh reset); swapping binaries on their
existing database is not supported by this internal checkpoint. A v0.21-to-v0.22
upgrade initializes the history baseline with the new index.

The new real-app controls finish repeated one-version passes while a stalled
reader retains its five original versions; the unrelated fact shrinks from five
versions to one. Twenty-five later player creations cannot enlarge the frozen
inventory. Other controls cover counted missing births, forged genesis frontiers,
gas rollback, stale generations, completed-call idempotence, failed-fact rotation
and later retry. Two fact visits with 32 reserved units cost 77,663 gas in the
fixture. This is local operation evidence, not a combined block-cost or production
throughput certificate.

The healthy/outage financial matrix also runs this dispatcher over the entire
frozen fact inventory, restoring partial batches before settlement. All four
normal/zero-height cases retain the same financial records and exact 21/0 or
1/20 ualpha provider/consumer payouts as their unpruned controls, including
first loss at service block 2. Evidence is
`/tmp/structs-history-pruning-financial.log`; this extends the earlier single-fact
check to the complete visit pass.

Birth capture is chronological across domains. The full-suite review found one

different scope. Its setup now writes those same facts in block order; its
absence, tombstone, empty-scope and next-change assertions are unchanged. A new

## Preservation contract

Reclamation must preserve settlement amounts and order, the first unsupported
service block, resumable verification, both export/import clock modes, and
indexer reconstruction. It must not turn unavailable evidence into an outage,
release consumer collateral as provider revenue, or permit a second payment.
An unfinished cleanup remains scheduled and owned until its last row is removed.

The current genesis validator replays a claim from its original service origin,
including old capacity windows and an already paid prefix. A failed claim also
requires its first unsupported block. Completed child proofs do not replace those
references. Therefore moving `VerifiedUntil`, setting `Settled`, or deleting a
child cannot by itself advance the claim's history floor.

## Dependency collection at the interpreter

All mutable supply reads pass through `serviceSupplyView.fact` or `.scope`.
The optional `serviceReadTrace` records those calls using the same view as the
in-memory and durable proof interpreter. Its batch is bounded to 128 distinct
identities and 64 KiB of encoded/copied key material. It does not retain values.
An exhausted batch returns an error before the interpreter advances that step;
a caller must persist the batch with its continuation before retrying with a new
batch. The internal dependency-proof API below now installs and persists it;
ordinary financial proofs and live block workers do not opt in.

| Read | Required protection |
| --- | --- |
| Point fact `(domain,key)` | Original value or tombstone, absence before creation, reconstruction anchor and changes in the reader's interval |
| Scoped inventory `(domain,scope)` | Entire scope inventory, insertion ordinals, creation boundaries, scoped facts and tombstones, including empty results and entries not yet reached by the cursor |
| Repeated read | Same protection; deduplication may not shorten the original interval |
| Failed read | Partial observation only; never a complete dependency set or proof of unsupported service |

Point, scope and domain identities cannot alias. Output order is canonical,
independent of map iteration and traversal order. Key material is copied so a
caller's reused byte slice cannot change a registered dependency. Ordinary reads
with no collector add no store operations or key allocations.

Each batch conservatively covers its original `[height,end)` even if later reads
shorten a proof's supported span. A span ending at a change boundary must be
followed by a new proof at that boundary. A completed proof describes only that
span, not the other windows or unread sealed suffix of its containing claim.
Traversal must include the first loss and stop there; later recovery does not
bridge it. The durable dependency proof also observes entitlement reads during creation,
including immediate zero-step refusals.

The root index, enrollment registry and read collector serve different purposes. Root rows
enumerate potential readers attached to one source/allocation; the collector
discovers what a replay actually depends on. The registry gives every reader a
stable birth sequence for finite enumeration. None is a prune-floor authority.
Reserved dependency proofs now commit bounded read batches with their graph
continuation. Snapshot-held reverse protection now commits with per-span progress,
and a counted dispatcher covers every span in the frozen reader inventory.
Per-span archives now preserve completed ownership copies outside the snapshot.
Counted dispatch now covers every original reader and span. Borrow links and
retirement guards are implemented below; complete admission and owned release
scheduling remain required before reclamation.
Deleting a reference must use exactly the identity used to insert it.

### Durable dependency proofs implemented

`CreateServiceDependencyProof` creates an isolated proof in the reserved
`\x00dependencies/` namespace and returns its stable enrollment sequence.
Creation records entitlement reads, including absence when the entitlement check
immediately refuses with zero graph steps. Each later interpreter step creates a
bounded trace and commits its distinct observations, count and graph continuation
together. Observations remain associated with the proof's original
`[height,end_height)`, even when later reads shorten `ValidUntil`.

The batch validates every existing row and counter increment before its first
write. A changed row or exhausted counter therefore cannot commit earlier rows
from a failed step. Repeated observations retain one indexed row. An ordinary
error keeps only previously completed steps; a gas panic discards the entire
private pass. Ordinary financial proofs retain zero dependency count and write
no dependency rows; their cleanup does not scan the new prefix.

`AdvanceServiceDependencyProof`, `ServiceDependencyProofReads` and
`DiscardServiceDependencyProof` require the birth sequence. Recreating an ID
cannot make an old advance, cursor or discard request valid again. Pagination is
available only after the proof terminates and before discard starts. A caller
starts with an empty cursor, retains the same birth and checks its final total
against `DependencyCount`. Each page returns at most 128 records and 64 KiB of
encoded key/value material. A malformed or oversized record refuses; it does not
silently disappear from the inventory.

Discard immediately marks the proof unreadable for collection, then removes at
most the supplied allowance (maximum 128) of frames, visits and dependency rows.
The original count remains in the header until its final deletion. Only a
completed proof can enter this cleanup. A future collector must first commit its
own protection ownership before releasing these rows; no live caller can create
or discard a dependency proof under the architecture guard today.

`ServiceSupplyJob` adds `dependencies_discarding` (field 12) and
`dependency_count` (13); `ServiceProofGenesis` adds repeated typed dependencies
(field 4). The reserved namespace selects tracing; an untraced job cannot attach
those fields or observations. Invalid domains refuse before byte narrowing.
Genesis checks ordered identity, count, size, job ownership and discard state.
Historical replay independently reconstructs the observed set and count at the
recorded step, then checks any permitted terminal cleanup suffix. Removing an
observation and reducing its count together still refuses. No observation list
or count is accepted as a payment receipt.

## Finite collection and arrivals

Any collection pass must fix a sealed upper height and a finite reader inventory.
New captures must not extend the work of that pass indefinitely. The present
`ServiceReadersByRoot` lookup is explicitly not a stable multi-block cursor;
lexically inserting new reader IDs while paginating would miss readers.

Before a collector can sweep, implement these together:

1. Stable reader enrollment and an immutable snapshot boundary are implemented
   below. Neither starts a live collector or establishes a safe floor.
2. Snapshot preimages preserve original roots, window inputs and intervals across
   mutation and deletion. Dependency collection must still own and protect the
   referenced historical windows until that pass finishes.
3. Admission rules for new readers. A new historical reader may only read above
   the established retention boundary or inherit protection from an already
   protected parent that covers its complete original interval and roots.
   A parent may not release that coverage before child enrollment commits.
4. Per-reader continuations and the snapshot's visited frontier now establish
   incomplete/complete observation state. Partially visited graph nodes, an
   exhausted batch and missing evidence remain incomplete and cannot publish a
   floor. A durable completed prefix still needs replay while export/import
   depends on it.
5. Reader dispatch now rotates through an index of unfinished collections.
   History candidates still need finite enumeration and fair continuation. The same adversarially
   growing prefix must not consume every pass. Shared dependencies take the
   earliest protection among all their readers; unrelated dependencies do not.

A global minimum reader height is not sufficient: a stalled contract would pin
unrelated growing histories. A global stop-the-world mark followed by sweeping
also needs a demonstrated finite-work and fairness bound before adoption. The
collector's row/byte limits do not establish either property. Choosing and
implementing that protocol remains open; no unimplemented protocol is treated as
a reason to remove the existing pruning guard.

prune floor: unrelated facts may be reclaimed only after complete dependency

pass. Owned-reader inheritance and reclamation integration remain open.

### Stable reader enrollment implemented

Every claim, interval and proof now enrolls with its root references in the same
SDK cache. The private registry stores a monotonically increasing sequence,
`sequence -> (kind,id)` and `(kind,id) -> sequence`. Claim commits already follow
sorted `CurrentContext` ordering. Updates preserve a reader's sequence; final
cleanup removes both index rows without lowering the counter. Recreating an ID
assigns a new sequence. Exhaustion refuses rather than wrapping.

`ServiceReaderEnrollmentCeiling` reads the current upper sequence.
`ServiceReaderEnrollments(after, through, limit)` visits at most 128 raw rows in
`(after,through]`. Callers retain the original `through` between pages; later
arrivals cannot extend that range, even if their object IDs sort before a previous
page. Deleted rows leave gaps. End-of-range returns `next=through` and
`complete=true`; traversal does not loop through every missing integer.
Every returned enrollment checks its reverse index and current canonical owner.
Missing counters, inconsistent associations and malformed rows refuse without
repair. A missing index on an existing root cannot silently enroll it again.

This is a current identity enumeration, **not a snapshot of reader contents at
the ceiling**. A deleted reader disappears and a surviving reader's interval can
change. The separate snapshot component below now journals those changes.
Admission rules, dependency ownership and authority to delete history remain
unimplemented.

`ServiceGenesis` adds `last_reader_sequence` (field 13), `has_reader_counter`
(14), and `reader_enrollments` (15). Entries carry sequence, kind and ID;
kind values other than claim=1, interval=2, proof=3 refuse before narrowing.
Export/import preserve exact chronology and gaps, including a counter whose
readers have all been removed. Full inventory validation rejects missing,
duplicate, orphaned or out-of-order enrollments and unknown stored rows. The
existing on-demand reader invariant also covers the registry. Architecture
checks confine full registry reconstruction/export to genesis and the invariant.

Older development snapshots with all three new fields absent reconstruct once in
sorted `(kind,id)` order; existing captured facts and financial records are
unchanged. An older database with readers but no registry is not silently treated
as current: direct export refuses until reconstruction through its compatible
older export. Once collection continuation is added, its presence must forbid
this legacy fallback, since rebuilding chronology would invalidate its cursor.

### Immutable reader snapshots implemented

`BeginServiceReaderSnapshot` fixes the current enrollment ceiling, active reader
count and sealed history height without a full scan. Enrollment now retains each
reader's canonical basis and an active count. A changed or deleted reader saves
its first preimage in the same SDK child cache before its durable basis changes.
Later births, including reuse of an old ID, cannot join the original snapshot.
Repeated changes retain the original preimage. The basis records original roots,
service interval, window start, revision and required power.

`ServiceReaderSnapshotPage(generation, after, limit)` merges live enrollment rows
with those preimages in sequence order, preferring the original preimage. It
visits at most 128 identities, with at most two index rows per identity plus fixed
lookahead. Callers retain the generation and compare the completed inventory
count with the header. A persistent generation counter survives discard and
export/import: a stale page or discard request cannot affect a recreated snapshot
even when its reader ceiling and sealed height are identical. Counter exhaustion
refuses without mutation.

Discard marks the snapshot as clearing and removes at most 128 preimages per
call. Clearing refuses pagination and further snapshot creation, stops collecting
new preimages and retains the header until cleanup ends. It deletes no supply
history or financial state. Creation, preimage preservation and discard use SDK
child caches; half-budget and final-unit gas failures leave all affected rows
unchanged.

Typed genesis adds `reader_snapshot` (field 16),
`last_reader_snapshot_generation` (17) and `has_reader_snapshot_counter` (18).
It preserves active and partially cleared snapshots, original preimages and idle
generation counters. Validation checks chronology, identity, count, seal and
retained claim-window references. A sealed original window must agree with its
canonical capacity; same-block repricing of an unsealed window may legitimately
retain its revision while changing power. Forged windows and missing/mismatched
generations refuse atomically. New derived basis/count rows reconstruct from the
canonical reader inventory; older development databases require export with
their matching binary followed by import, not direct opening by this candidate.

### Persistent retired-pool scheduling implemented

`ProcessServicePoolReclamation` visits at most four retired pools and uses at
most 128 supplied work units per call, with at most 16 denomination rows per

commits retirement. Later payments preserve that ticket. Successful final pool
removal deletes the exact forward/reverse queue rows in the same cache commit;
partial or failed visits rotate to a later ticket. Each call captures the current
last ticket, so it cannot repeatedly service its own rotations or newly enqueued
work. New arrivals cannot overtake earlier pending tickets.

The queue uses `Agreement/servicePoolReclamation/`: `q + ticket` identifies the
provider, `i + provider_id` identifies its current ticket, and `n` retains the
monotonic counter even when the queue becomes empty. CurrentContext's sorted
pool commits make simultaneous retirement enrollment deterministic. Counter
exhaustion refuses before replacement. An existing next-ticket row also refuses,
so an understated counter cannot overwrite another pool's task.

ordinary visit failure leaves the assets and events unchanged for that visit and
rotates with its allowance charged. Malformed queue/index state, impossible
ownership, failed rotation and gas exhaustion discard the entire call, including
any earlier successful visit. This differs from the settlement coordinator's
ordinary-error behavior and is deliberate: no pool task can disappear between
removal of its old ticket and installation of its replacement. An empty queue
emits no events and changes no stored rows.

order, gaps and counter; it does not reset priority when financial caches commit.

sorted provider-id order. Export and the collateral invariant verify the actual
forward/reverse rows and refuse missing or extra rows instead of repairing them.

## Deletion sequence and financial records

The first reclamation path should handle fully terminal claims, rather than
quietly changing the meaning of a live certified prefix. All of the following
must be established from canonical state before removal: every consumer and
provider payment is complete, no cancellation reserve remains payable, the
settlement queue no longer references the claim, and its interval/proof cleanup
has completed. Claims waiting on payments or cleanup remain ordinary readers.

The accounting review identifies an important constraint for terminal cleanup:
a fully settled claim contributes zero to every current pool aggregate. The
invariant computes:

- `reserved = sum(principal - provider_paid - consumer_paid)`;
- `outstanding = count(!settled)`;
- `active_load = sum(capacity for retirement == LIVE)`.

`validateServiceObligation` accepts `settled` only at a final entitlement with
both legs paid exactly. Final entitlements sum to principal and require non-live
retirement. Therefore deleting an eligible settled claim must change none of
these three pool amounts. In particular, `payNext` already decremented
`outstanding`: decrementing it again during reclamation would repeat settlement.
No new payment or cumulative revenue release belongs in this transition.

The structural checks still prevent simply deleting the claim. The current pool
invariant requires at least one retained obligation, derives provider existence
from those obligations, and rejects orphan windows. Reclamation must make an
empty pool inventory valid only with independently checked canonical provider or
retained payout ownership and zero reserve/count/load. Nonempty pools must still
match the exact sums above. A terminal receipt must never authorize another
payment, reopen service or recreate an old agreement ID; reservation, migration,
query, export/import and coordinator paths must distinguish it from a payable
claim. A cleanup receipt can describe completed accounting, but cannot substitute
for service evidence still needed by any live claim/window.

Before the claim-to-receipt transition, prove exact final payment and retirement,
absence of the live agreement, and absence of settlement/interval/proof ownership.
The transition must also preserve any original claim inputs and windows still
needed by a frozen snapshot, including a reader not yet reached by its collector.
This needs indexed checks for that birth, not a blanket wait on unrelated claims.
Window removal must use a bounded continuation with a validated remaining suffix;
the current contiguous-window invariant cannot silently accept a missing prefix.
The terminal receipt and bounded suffix transition are now implemented as
specified above. Production invocation remains disabled. Paid closed-window
prefixes use the separate transition below; unpaid/current-window prefixes
and production coordination remain unfinished.

Deleting a pool is a separate operation. Zero service reserve does not mean its
derived addresses contain no assets. Before removing retained payout ownership,
all applicable collateral/earnings balances, including other denominations, must
remain reachable or be drained to the established beneficiary with bounded work.
Neither an empty claim inventory nor a zero `ualpha` balance proves that condition.

Long-lived claims with many capacity changes now have the bounded paid-window
prefix transition described below. A hash of deleted history is not a replacement
for semantic replay. Fully paid closed windows can leave the active replay
inventory; unpaid windows and the current window retain their original evidence.
This does not yet bound a long-lived, unrevised claim's history.

Implement deletion in this dependency order:

1. Consume results and complete all settlement, with the existing consumer-first
   ordering and exactly-once guards.
2. Finish bounded child cleanup and remove queue ownership only after no more
   work can be lost.
3. Atomically update the financial equations and remove/archive the eligible
   record, together with its deletion/replacement event and reader transition.
4. Release its dependency rows through owned, bounded cleanup. Shared rows remain
   protected by their other readers.
5. Publish a monotonic safe floor per fact/scope, then use the bounded version
   pruning primitive while retaining its reconstruction anchor and change marker.
6. Reclaim dead scope inventories only after proving no retained cursor or
   absence check needs them. Never renumber live ordinals. Version pruning alone
   does not bound an inventory that accumulates new keys forever.

## Unpaid service checkpoint decision

The remaining case cannot use the paid-window transition. In an unrevised
agreement charging 3 coins per block with a 40% provider cancellation penalty,
the first delivered block pays 1 coin and retains 2. The second delivered block
raises cumulative payable revenue to 3, so it owes another 2 coins. Calculating
each segment independently would pay only 2 coins total. Calculating the first
segment's holdback as `floor(3 * 0.4)` would retain only 1 coin; the actual unpaid
balance is `3 - floor(3 * 0.6) = 2`.

Creating a fictitious capacity revision is also not a storage-only operation.
It releases the first block's entire gross, making 3 coins payable instead of 1.
For an original 21-coin principal, provider cancellation immediately afterward
would refund 18 instead of 20 to the consumer. Healthy expiry still pays 21
in both cases, so an expiry-only test would miss the changed economics. Tests
now pin live progress, provider/allocation cancellation, first outage, consumer
cancellation and healthy expiry, plus the cumulative-rounding counterexample.
A real-app control drains the actual settlement worker at every height from 2
through 7, checks its exact earnings balance, and confirms paid-window archival
cannot change the current claim, evidence, assets or events. Genesis round trips
remain valid after each attempt.

The proposed alternative is a consensus-validated service checkpoint, not a
payment, pricing revision or hash pretending to prove deleted history. This is
a pending policy decision; no new checkpoint schema or production behavior is
implemented. Its required contract is:

- Keep all financial amounts and original pricing terms unchanged: principal,
  cumulative certified/released gross, provider/consumer payments, refund credit,
  legacy holdback, capacity windows and cancellation terms. The existing
  cumulative entitlement formula remains authoritative. Cleanup must not move
  money, reset rounding, increment a pricing revision or release collateral.
- Advance a separate historical replay boundary only over service the existing
  settlement worker has certified from sealed history. It cannot pass the first
  unsupported height, queued verification, an unapplied result or evidence still
  owned by a child. Refuse caller-written checkpoints through cache admission,
  just as paid-prefix edits are refused today.
- Preserve original reader birth and pricing-window coordinates. A checkpoint
  inside a window clips its replay interval; it does not rewrite that window's
  start, capacity or cumulative gross. Frozen snapshots and durable borrowers
  must release their own prefix before history deletion. Remaining windows and
  their cleanup cursor must still form a validated inventory during bounded
  disposal; no revision renumbering or unbounded catch-up loop is allowed.
- Validate retained financial equations, reserve backing, checkpoint coordinates
  and the entire remaining service suffix on import. A first outage at the
  checkpoint boundary must still be replayed and must prevent later payment.
  Normal-height export, zero-height export and database reopen must preserve the
  same logical boundary and every future payout.

Unlike a fully paid prefix, an unpaid checkpoint would remain authority for
future money. Genesis would trust its historical delivery assertion as canonical
consensus state; independently auditing that assertion would require archival
chain data. Financial conservation and suffix replay do not independently prove
the deleted past, and the interface/documentation must say so. Keeping independent
genesis replay of every unpaid block instead means retaining its necessary
historical evidence. Arbitrarily long agreements with arbitrarily many relevant
supply changes have no established fixed storage bound under that requirement.

On 2026-09-16 the user was asked to choose between those trust/retention policies.
There is no answer yet. This input does not block independent dead-inventory,
coordinator, permission, migration or executable verification work. Even if

## Deletable birth cardinality prerequisite

## Compressed birth-count roots

The integrated tree now stores only the height bits needed by its highest
retained birth. A one-byte root-depth record identifies the canonical covering
range starting at zero. Ordinary chain heights therefore avoid dozens of
identical leading-zero ancestors. When a new height exceeds that range, the
update joins the original subtree to the new path; when the highest birth is
removed, the component removes redundant ancestors and contracts the root.
Removing the final identity clears the metadata too. The representation depends
only on retained heights and counts, not insertion/removal order.

Every visited parent still equals the sum of its two children. The root must
have the expected children and a nonempty upper half, except the single-height
zero root. Expansion refuses pre-existing rows above that root, and contraction
validates newly reached descendants before publishing any edits. All edits are
staged, then written in sorted key order; SDK cache rollback covers gas failure
halfway through either operation. Metadata loss, malformed depth, late
contraction corruption and stray expansion ancestors all refuse without writes.
Independent prefix-sum, overflow, randomized ordering and full-clear controls
remain in place.

The primitive's worst-case bounds are 260 point reads and 129 writes/deletes per
update; a prefix lookup uses at most 132 point reads and no writes. The measured
zero-to-MaxUint64 expansion uses 194 reads and 129 writes/deletes; its inverse
uses 259 and 129. These transitions consume 527,033 and 400,007 gas in the
component fixture. They restore the exact original two-row zero-height tree,
as do all 64 individual highest-bit transitions. Ordinary height widths use
shorter paths. A query above the root's covered range reads its validated total.
These bounds describe the count component, not an entire transaction or block.

### Repeated-cycle archive growth reproduced

## Scope scan shape is owned evidence

Review of empty-header deletion exposed an existing defect in the internal
scoped-fact worker. Three infusion entries born at height 1 and removed at height
2 still occupy three scan steps in a proof at height 5. Reclaiming one tombstone
at that proof's retention floor preserves the supported economic result but
changes its execution length. The regression reproduced an export refusal,
`archived proof disagrees with historical replay`, immediately after deletion.
Pending proofs can also retain an insertion cursor whose exact replay changes.
The earlier successful scoped-reclamation tests did not cover a reader that
observed several already-absent entries.

The guarded worker now distinguishes version pruning from scan-position
deletion. It may prune old versions at the existing safe floor. It keeps the
tombstone and ordinal while either the snapshot reverse index or a durable
archive owns the whole scope, even when the owner's observation is later than
the tombstone. Both checks use existing exact dependency indices. No reader
inventory scan or replay is added to cleanup, and strict genesis proof equality
is unchanged.

There is a second ownership gap: a reader admitted after the snapshot can see
the old positions without appearing in that snapshot's archives. Until that
lifetime has a bounded ownership design, deletion additionally requires that
independent admission be closed strictly beyond the snapshot seal and that the
current seal still equal it. New independent historical work then cannot start;
inherited work retains its archive coverage. Once the seal advances, candidates
retain their scan positions and the finite pass continues. This is deliberately
conservative even when no later reader actually exists. A fresh closed snapshot
can reconsider unowned candidates. Empty scope headers remain intact.

This restriction is a safety correction, **not production retention readiness**.
A cycle spread across advancing blocks cannot rely on this guard to reclaim
scoped inventory. Per-scope continuation ownership, or another design preserving
exact replay for existing and later readers, remains required before activation.
It must cover both tombstone removal and header deletion/rebirth; accepting a
different step count or silently resetting saved cursors is not a repair.

Regression controls cover completed and partially consumed tombstone scans,
durable ownership after snapshot disposal, and independent readers admitted at
the old boundary or after a later seal. Existing restart controls now explicitly
verify that value pruning resumes through normal/zero-height InitChain and
database reopen while deletion waits for a fresh closed snapshot. Scheduled
deletion completed before the seal advance still restores and continues. No
protobuf, asset movement, event contract, or production caller changes.

## Scope observations across advancing blocks

The immutable reader enrollment sequence can summarize which proofs observed a
scope without retaining a separate lease record for every proof. Each scope now
stores the greatest sequence of a durable proof that scanned its insertion
inventory. This `y` row is one uint64 per retained scope, exposed as the additive
`ServiceHistoryScopeGenesis.last_scan_sequence` field. It is current retention
metadata, not a historical value or a payment certificate. It stays monotonic
when proofs finish, are removed, or a public proof id is reused.

A completed snapshot covers reader births through its fixed `ThroughSequence`.
If a scope's last observer is newer, deletion waits for a later snapshot. If it
is covered, the existing snapshot and durable archive reverse indices determine
whether any owner still needs that scope. Old value versions retain their
existing floor calculation. A new proof that has not reached a scope cannot
have saved that scope's cursor or consumed its tombstone steps, so it does not
pin it. Once the proof reaches the scope, its successful step publishes the
observation with its continuation, preventing deletion before the next covered
snapshot. This removes the blanket prohibition on deletion after the seal
advances, while preserving exact replay.

Observation preparation occurs at the same traced scope-read boundary as the
dependency inventory. A durable interpreter step may scan at most one scope;
it prepares at most one scalar update and publishes after all fallible step
validation. A failed step leaves no observation behind, a gas panic rolls back
the enclosing proof batch, and successful prefixes retain their observations.
Read-only in-memory views have no observation recorder. Missing scope headers
create no metadata. A header first born after the proof's historical height
also creates no observation: it cannot change that earlier empty scan's zero
insertion cutoff. Existing empty headers with old insertion positions do count.

Genesis preserves the scalar and requires it to be within the global reader
chronology. More importantly, exact replay of every live and archived proof
checks that each scope it actually scanned has an observation at least as new
as the proof's original enrollment. Archived replay uses `ProofSequence`, not
the temporary enrollment allocated while reconstructing a retired proof in a
discarded cache. Validation refuses missing/lowered watermarks rather than
repairing them. Future continuation of a pending proof remains a separate
readability check in the discarded cache; it cannot invent observations in the
imported state. Orphan metadata refuses scope creation and export.

This adds no scan over readers or jobs to a live path. A reclaimed candidate
uses one scope observation lookup, a reader-counter bound check, and the existing
indexed owner lookups. A retired later observer conservatively pins its scope
until the next snapshot includes that birth; unrelated scopes remain eligible.
The counter does not authorize removal while any snapshot/archive owner remains.
It also does not remove scope headers, retire financial evidence, establish a
total storage bound, or enable the internal cycle's production caller.

Empty-header reclamation must reuse this ownership check and the published
implicit-absence boundary. A candidate must have no facts or ordinal-count rows
and only its final creation anchor; remaining creation rows belong to the
existing bounded creation cleanup. Deleting a header also removes its original
scope birth and decrements the scope-count tree, so that phase needs its own
finite inventory and authenticated removed-cursor continuation after releasing
the creation pass. Rebirth must occur beyond the old pass's height ceiling and
cannot reuse a cursor still held by a reader. Fixed point-domain headers remain
separate from object-specific scope reclamation. The following phase now implements these requirements; they are not behavior
enabled by the observation counter alone.

Controls cover partial and completed later scans, deletion before a later proof
reaches a scope, unrelated deletion while later work is active, removal after
the observer retires and a new snapshot covers it, failed-step and gas rollback,
forged/missing/out-of-range metadata, monotonic updates, old empty scans followed
by a future scope birth, and byte-exact genesis restoration. The existing normal
and zero-height actual InitChain/database tests again require unobserved scoped
deletion to finish across advancing blocks without a fresh snapshot. The JSON
wire fixture adds only `last_scan_sequence: "0"`; stripping that default recovers
the previous golden hashes.

## Financial maintenance scheduling

`ProcessServiceMaintenance` now interleaves five internal lanes: history,
paid-window prefixes, terminal claims/receipts, retired pools, and archive
release. One call runs at most one working or held lane with the caller's 1..128
work allowance. Each empty lane costs one unit and yields to the next lane in
the same call, with at most five probes total. The next lane
persists across export/import and database restart; a held owner or a lane error
rotates so unrelated cleanup can proceed. Worker-owned finite cursors retain
their existing guards. Gas exhaustion rolls back both child work and lane
rotation, and malformed lane state is refused rather than normalized.
An entirely idle circuit leaves scheduling state unchanged; a smaller allowance
persists its partial rotation. Busy, held and failing workers end the call after
their turn, so skipping empty queues cannot monopolize other workers' turns.

Paid-prefix cleanup now has its missing work selector. A derived index contains
only live, nonfailed, unsettled claims with verified closed windows beyond their
archived prefix. It is keyed by the claim's original enrollment birth, updated
after enrollment and removed before archival unenrollment. Unrelated claim
updates do not rewrite an unchanged entry. The index indicates potential work,
not payment authority: `ArchivePaidServiceWindows` still validates exact payment,
contiguous windows, frozen readers, child ownership, and settlement phase before
removing anything. In particular a verified but unpaid claim remains queued.

A pass freezes the reader-birth ceiling and visits each selected claim at most
once, with at most four claims and sixteen windows per claim per call, within
the shared allowance. Later births wait for the next pass. Large, snapshot-held
and failed claims yield to other candidates; EOF releases the pass frontier.
No live operation scans every claim, window, proof or archive to select a paid
prefix. Genesis derives candidate membership from financial records and births,
while preserving the explicit pass frontier. The on-demand reader invariant
checks both missing entries and extra ones. Additive genesis field 31 carries
paid-prefix progress and field 32 carries the next maintenance lane (0..4).

The coordinator composes existing safety boundaries rather than weakening them.
Paid/terminal cleanup can wait while history owns a frozen reader; subsequent
turns retry after snapshot disposal. Retired pools still wait for all retained
claims and settlement work before any asset drain. Archive release still
respects snapshots, borrowers and unpaid/current-window evidence. Cleanup does
not certify new service, change prices or authorize another payment. Asset
transfers and typed financial deletion/replacement events come from the existing
transactional workers.

This coordinator has no production block-hook caller yet. Archive release already
has an independent EndBlock caller; activation must replace that invocation with
the shared coordinator, not add a second live release budget beside it. Combined
resource bounds, production throughput and downstream acceptance remain release
gates. This integration does not resolve the separate policy question about
replacing unpaid/current-window historical evidence with a trusted checkpoint.

## Indexer ordering

Canonical claim/window/pool deletion requires a typed event identifying the
record kind and complete key. Existing financial replacements and bank transfers
do not express deletion. The event must commit with the removal; failure rolls
both back. A cleanup-only reference deletion must not masquerade as an asset move.

During a financial snapshot, indexers must buffer the latest replacement **or
deletion** per key after the start boundary. On completion they install the frozen
snapshot and apply that overlay in event order. A late old snapshot chunk must
not resurrect a record deleted while the snapshot was being delivered. A new
genesis snapshot supersedes an interrupted stream; a database restart continues
the existing stream. The additive `EventServiceFinancialDelete` schema and reference replay now
implement the exact-key tombstone overlay. The internal terminal transition now emits actual claim/window deletion events
atomically with removal; the reference consumer covers that path. Production
activation and actual external indexer acceptance remain required. Bounded retired
pool deletion is now implemented above as an internal operation; automatic
scheduling remains unfinished. Receipt-only cleanup does not authorize history pruning.
