# v0.22.0 economy client reference

**Reactor replacement, 2026-09-23:** Current reactor output uses flat 1:1 base
power plus owner diversity, with a sticky stake-share cap. This supersedes the
unshipped efficiency query, bands, weights and pending-rate metadata. See the
[replacement progress record](v0.22.0-reactor-replacement-progress.md) for current
acceptance evidence; older test counts below refer to earlier candidates.

**Security policy update, 2026-09-22:** Rank grants supply operational rights only.
Entry-rank changes, rank assignment, permission administration and ownership transfers require explicit
administrative authority (ownership or a direct Admin grant), plus the signing
key's required bits. A configured rank threshold for Admin cannot grant this
power. Guild ownership transfer clears the previous owner's entire direct grant
on that guild, including TokenTransfer. Independent grants on child objects are
not recursively removed. Migration strips newly effective economic bits from
legacy guild and guild-rank grants so formerly inert bits do not silently gain
vault access. Current owners retain owner authority. Pre-existing rank-register
Admin entries are retained as data but confer no administration; explicitly grant
direct Admin to continuing officers. Kick preserves independent direct grants on
the guild and its child objects; revoke those separately when dismissing an admin.

A guild or guild-owned substation used as an allocation source defaults the new
allocation's controller to that guild. Choosing another controller requires source
administration. Guild administrators may delete static/automated source allocations.
Large substation deletions expose `deletion_pending` and
`deletion_migration_substation_id` while bounded GridCascade cleanup runs. Pending
stations reject new connections; the final delete event comes after cleanup.

Query offsets above the maximum page size are rejected with InvalidArgument;
use returned pagination keys to continue large queries. Limit remains capped.
Infusion payloads retain current fuel, power, ratio, commission and defusing
state. No pending efficiency metadata or historical deposit rates are stored.
See the [security remediation report](v0.22.0-security-remediation-2026-09-22.md)
for current validation; older acceptance claims below describe earlier candidates.

**Scope update, 2026-09-21:** The user confirmed removal of the added on-chain
historical billing/audit subsystem while preserving existing elapsed-block
agreement/provider payments, checkpoints, cancellation/refund rules and
GridCascade teardown. Historical financial snapshots, retained service proofs,
service-clock replay and retention scheduling described below are superseded;
normal migration, vault/asset, economic and deletion events remain required.
Runtime and generated-interface removal are implemented. Go checks and all 445 current Python tests pass;
final native chain acceptance remains. Indexer implementation and downstream
testing are handled separately by the user; chain-event correctness remains required. The
[main plan](v0.22.0-economy-plan.md#current-release-gates) is authoritative.

**Retained native vesting accounts:** An associated SDK vesting account with
validator self-stake or related pending records keeps its entire native account,
including liquid assets and non-self stake. Its player's other addresses still
migrate. Vault creation/association does not imply that every signing address was
emptied. Keep retained balances and native staking positions visible separately;
no movement or account-conversion event is emitted for assets that stayed put.
The original SDK vesting schedule, counters and reward settings continue to apply.
Later address rotation/registration keeps this stake native; revocation removes
its Structs capacity authority. These identity-change handlers retain their
existing SDK-spendable coin sweep, so the migration exception does not freeze
future liquid funds at the signing address.

This describes the current v0.22.0 worktree interfaces. The upgrade is not yet
release-ready; see the [plan's release gates](v0.22.0-economy-plan.md#current-release-gates).
Commands below are examples, not a script to run verbatim. Substitute existing
IDs, addresses and your signing key, and supply your network flags. Twelve CLI
command signatures/flags were checked using a fresh build of this worktree.
No live transactions were sent for this documentation check.

## Compatibility with v0.21.0 and the 118b baseline

Combat event health fields are corrected without changing their wire schema.
`targetHealthBefore` records actual health at the start of that target's volley;
it is no longer reconstructed from nominal damage, which overstated health on
overkill. The final projectile row carries resolved target health/destruction,
including explosions triggered by target counters. Intermediate projectile rows
retain pre-volley target health, including blocked volleys. `damage` remains
nominal volley damage, so it need not equal the target's total health loss when
damage exceeds remaining health or counterattack consequences deal more damage.
See the [event evidence](v0.22.0-economy-security-review.md#combat-health-events-must-observe-state).

After billing-history removal, `buf breaking proto --against <baseline>/proto`
passes the configured FILE rules against both archived releases:

- 117b: `accdb07045f10a74feb01095d6db0239f07afda7`.
- 118b: `752d1d6e243db29a4be6a781ad2cbbaf27b09ce0`.

The 2026-09-21 logs and exact baseline revisions are retained in
`build/v022-interface-review/`. Each archived tree has an isolated Buf workspace;
the first attempt inherited the outer workspace and refused duplicate inputs,
then both corrected checks passed. Go and OpenAPI generation also pass after
removal. The retired development-only genesis fields have reserved numbers/names.
No additional historical billing state, query or event is in the release schema.

The subsequent staking restart repair adds `stakingUnbondingId` (genesis tag 45)
to preserve the SDK operation sequence, including completed operations. Keep it
with full app exports; import reconstructs the staking operation-ID/type indices
from staking rows. Legacy exports without this field recover only the live maximum.
This is restart metadata and introduces no billing-history API. Go/OpenAPI
generation and FILE checks against both baselines pass for the added field;
logs are in `build/v022-retained-upgrade-restart/`.

These checks establish protobuf compatibility under the configured rules. They
do not prove that an old client requests the same economic operation, understands
new events or handles the new vault spend sources. Downstream indexer acceptance
is separate user-owned work; chain-side payload and delivery checks remain here.

## Allocation deletion authority

Deleting a dynamic allocation accepts either `SourceAllocation` authority on its
source or `Delete` authority on the allocation. The signing key must hold the bit
for the selected path; an object grant cannot supply a missing signing-key bit.
Guild ownership and explicit rank grants use the same live permission resolver.
The v0.22.0 ante map now preserves the delete-only path, which the prior fixed
source-bit gate incorrectly refused. Creating or resizing allocations still
requires source authority. This message cannot delete static allocations. A successful
CheckTx or broadcast is not proof of handler authorization or delivery.

Deletion also clears the allocation's power attribute with the existing
`EventGrid` zero replacement. The allocation's `EventDelete` comes first in
the transaction's event order; applying the later grid event must not recreate
that allocation. The v0.22.0 migration emits zero replacements for historical
power rows whose allocation no longer exists, without repeating old allocation
deletions or changing source/destination capacity again.

## Allocation controller transfers

`AllocationTransfer` requires `Admin` on the signing key and authority over the
allocation through ownership or a direct administrative grant; rank standing
cannot supply Admin. A target controller must be an existing player or guild with a
canonical owner ID. Connected allocations may change controller without moving
their power, source or destination.

For a player controller, the handoff removes only `AllocationConnection` from
the old controller's direct grant and adds it to the recipient's existing grant.
Other rights survive, including during a self-transfer. Guild controllers use
the live guild-owner resolver; transfers do not create a permission row treating
the guild as a player. An allocation's existing direct and rank grants are not
cleared by a controller transfer. Independent direct child-object grants remain
until explicitly revoked, including grants originally made using rank authority.
Authority supplied by current membership, rank or ownership ends when that
relationship ends; no new grant-provenance or cascading-cleanup system is added.

`EventAllocation` reports the new controller; permission events report any
changed player grants. A failed later message rolls back the earlier handoff and
its events. Previous implicit ownership alone cannot authorize taking the
allocation back in a second message.

## Vaults and signing

An owner ID names a player (`1-N`) or guild (`0-N`). A vault address is a bank and
staking account controlled through Structs permissions. It is not a keyring key
or an address that should be registered as a player signing key.

```sh
structsd query structs vault "$OWNER_ID" -o json
structsd query bank balance "$VAULT_ADDRESS" ualpha -o json
structsd tx structs vault-send "$OWNER_ID" "$RECIPIENT_OWNER_ID" 1000000ualpha --from "$KEY"
```

The vault query returns `ownerId`, `address` and `provisioned`. It can return the
deterministic address before provisioning and never creates accounts itself.
Provisioning is not a statement about the current balance or the caller's rights.
REST uses `GET /structs/vault/{ownerId}`. Read balances through the bank module;
paginate when requesting all denominations.

The player query's existing `playerInventory.rocks` field now reports **spendable
ualpha in the player vault**. Locked coins are excluded. It no longer reports the
primary signing address's balance and does not aggregate signing-key balances,
delegated stake or other denominations. Querying inventory does not provision a
vault; an unfunded, unprovisioned vault reports zero. Read retained signing-key
balances and native staking positions separately.

`MsgVaultSend` takes owner IDs for both ends and a coin list for `amount`.
The signing key needs token-transfer permission and authority over the source
owner. Guild membership alone does not authorize a treasury spend. An authorized
transaction provisions missing vault accounts; a failed transaction rolls back
that provisioning and its transfers. Bank spendability, vesting and applicable
guild-token restrictions still apply.

For a player's vault-to-signing-address transfer, use the existing `player-send`
with the vault as `from-address` and the registered key as the destination. This
can fund the signing account for transactions that require native fees. The
vault does not sign the transaction.

## Guild creation and issuance

```sh
structsd tx structs guild-create "$REACTOR_ID" "$ENDPOINT" "$ENTRY_SUBSTATION_ID" --from "$KEY"
structsd tx structs guild-bank-mint 1000000 1000000 --guild-id "$GUILD_ID" --from "$KEY"
```

Creation spends 2,000,000 ualpha from the founder's player vault: 1,000,000 is
burned and 1,000,000 becomes guild-token collateral. It issues 1,000,000 base
units (one token) of `uguild.<guild-id>` into the new guild vault. The selected
primary reactor must exist; the founder need not own or control it. Other
founding and entry-substation eligibility checks still apply.

Later `GuildBankMint` spends Alpha from the **guild vault**, moves collateral to
the separate collateral pool and issues tokens into the guild vault. There is
no recipient field or override. Distribute treasury tokens using `VaultSend`.
Mint amounts are integer base units. `--guild-id` is needed when selecting a guild
other than the signer's current guild, including ownership without membership.
Mint authority and token-transfer authority are both required.

## Rank sales and admission

Read the guild and player before quoting. Relevant guild fields are `entryRank`,
`rankPurchaseBasePrice`, `rankPurchaseStepIncrease`, `rankPurchaseMinimumRank`
and `joinByRankPurchaseEnabled`. Lower numeric ranks are better. Minimum rank zero
disables sales; enabled admission also requires an enabled sale range.

For entry rank E, calculate progress as `max(E - currentRank, 0)`. For a valid
target rank, target progress is `E - targetRank`. With base price B and step
increase S, `T(n) = B*n + S*n*(n-1)/2`; charge the difference between target and
current T. Admission starts from zero progress. Compute using exact integers,
not floating-point numbers. Prices are base guild-token units, not whole tokens.

For a guild whose entry rank is 101, this configuration prices the first two
steps at 10 and 15 whole tokens:

```sh
structsd tx structs guild-update-rank-purchase "$GUILD_ID" 10000000 5000000 1 true --from "$OWNER_KEY"
# Existing member at rank 101 purchases rank 99 for at most 25 tokens:
structsd tx structs guild-rank-purchase "$GUILD_ID" 99 25000000 101 --from "$KEY"
# A guildless player requests the separate purchase-admission path:
structsd tx structs guild-membership-join-by-rank-purchase "$GUILD_ID" 99 25000000 --from "$KEY"
```

Configuration requires guild admin authority. Purchase and admission both require
the signing key's membership and token-transfer permissions, including free
purchases. Payment goes from the player's vault to the target guild vault, in
that guild's token only. The response reports `price`, `denom` and `rank`.

Member purchase requires `expectedRank`. Admission uses `expectedGuildId`, empty
for an expected guildless player; supply `--expected-guild-id` when leaving another
guild. Stale expectations or a price above `maxPrice` reject without payment.
These guards do not pin every guild setting: refresh the quote and intended
membership/rank outcome before signing.

An ordinary rank purchase cannot admit a non-member. The separate admission
transaction requires the guild's explicit purchase-admission setting and checks
applicable leave eligibility. It connects to the guild's ordinary entry
substation. It does not redelegate reactor stake. Existing invite/request/direct
join routes remain available under their configured rules; infusion-gated direct
joining may redelegate and therefore requires token-migration authority when it
moves stake. Purchases have no expiry; demotion changes the rank from which the
next purchase is priced. There is no lifetime spending credit.

## Generator fuel

`struct-generator-infuse` burns fuel from the signing player's vault. Fund that
vault before submitting; an empty vault does not fall back to the primary key's
balance. The existing infusion permission and generator eligibility checks still
apply, and only a single Alpha denomination is accepted. Generator infusions are
recorded against the vault address. Existing generator positions remain at their
recorded addresses; this change does not recreate or double-credit their fuel.

The generator's `EventAlphaInfuseDetail` retains `primaryAddress` as identity
context and adds `vaultAddress` as the fuel source. Use bank events for asset
accounting: the same legacy Alpha event type also appears in reactor unbonding
bookkeeping and is not, by itself, proof of a burn or a new deposit.

## Reactor positions

```sh
structsd query structs reactor-stake-share "$REACTOR_ID" -o json
structsd query structs owner-reactor-diversity "$OWNER_ID" -o json
structsd query structs infusion "$REACTOR_ID" "$VAULT_ADDRESS" -o json
structsd tx structs reactor-infuse "$VALIDATOR_ADDRESS" 1000000ualpha --from "$KEY"
structsd tx structs reactor-infuse "$VALIDATOR_ADDRESS" 1000000ualpha --owner-id "$GUILD_ID" --from "$KEY"
```

Reactor positional address arguments are validator operator addresses. Omitting
`--delegator-address` selects the signer's player vault; `--owner-id` selects a
player or guild vault. An explicit `--delegator-address` with an owner
selector must match that vault; without the selector, an explicit address is
resolved through its live asset owner. The same selectors apply to defuse,
cancel-defusion and begin-migration. Each operation requires its own asset bit
and authority over the selected owner.

The v0.22 CLI removes the former leading delegator positional argument for all
four operations. Existing CLI callers move that address to `--delegator-address`;
callers selecting a default vault omit it entirely. An explicit empty address is
not accepted by the SDK address parser. Protobuf message fields and their meaning
are unchanged by this CLI correction.

The stake-share query reports `validatorTokens`, `stakeDenominator`, `capBps`
and `capActive`, plus separate `externalDepositHeadroom` and
`bondedRedelegationHeadroom`. External deposits enlarge the denominator; transfers
from another bonded validator do not. Empty headroom means the cap is inactive
or configured to 100%, rather than zero available stake. REST uses
`GET /structs/reactor/{reactorId}/stake-share`. Defaults are a 30% cap activated
at ten bonded validators, sticky after activation. Existing above-cap positions
remain, but further inflows must satisfy the cap. Cancellation is an inflow.
A required guild-join migration that cannot complete rejects the entire join.

The query also reports `slashRevision`, `reconciledSlashRevision` and
`commissionRepairPending`. A pending repair disables commission source admission
until its accounting commits; a completed repair does not override validator
health or other capacity checks. Manual restart does not make a healthy reactor
pending. Indexers must consume `EventReactorCommissionRevision` and the
`EventReactorCommissionRevisionReset` replacement marker, including an empty
replacement after genesis rebuild. Revisions are exact uint64 values and can
restart from zero following that reset. See the [event contract](v0.22.0-economy-events.md#slash-repair-eligibility-visibility)
for block ordering, higher-height imports and SDK metadata handling.

An infusion exposes current `fuel`, `power`, `ratio`, `commission` and
`defusing`. Eligible bonded, unjailed backing produces 1:1 base power before the
existing commission split. There is no deposit-rate blend or grandfathered
weight. Cancellation recalculates backing and the current owner portfolio.

The owner-diversity query uses `GET /structs/owner/{ownerId}/reactor-diversity`.
Its `stored` summary contains exact integer strings `power` and `squaredPower`,
plus uint64 `appliedBonus`. It aggregates the owner's delegator shares per reactor,
including multiple owned addresses on the same reactor. The current defaults
are `maxBonusBps=5000` and `targetExtraReactors=9`. `storedCapacity` includes the
applied bonus and other primary contributions; do not add it again in a client.

`liveBonus` is the formula result from current native backing and eligibility,
or an empty string if its bounded inventory is incomplete. `usableBonus` is
limited by both live entitlement and the already-applied bonus. Read
`livePortfolioComplete`, `infusionInventoryComplete`, `initialized` and
`usablePrimaryCapacity` alongside these values. Reading does not credit newly
unreconciled stake. These fields distinguish stored accounting from conservative
usable power while repairs are pending; secondary supply remains separate.

Concentrated deposits can reduce total owner power despite adding base stake.
This is accepted gameplay: preview it in the interface, and expect ordinary
GridCascade when capacity falls. Bonus changes are published through
`EventOwnerReactorDiversity`, including zero transitions; genesis import emits a
one-time `EventOwnerReactorDiversityReset` before reconstructed summaries.

A validator leaving or returning to the bonded set queues
stored-power reconciliation. Shutdown, restoration and slash work share the
128-position-per-block budget. Live eligibility may reject power immediately
while its stored infusion/grid values are still positive; use those events to
track accounting progress, not as a complete gameplay-readiness signal. Large
reactors can recover over several blocks. The validator's bonded event alone
does not mean every previously zeroed position is producing again. Brownout teardown already completed is
not reversed. Explicit paid `reactor-restart` schedules the same bounded worker;
transaction success means the repair is queued, not that every infusion has
recovered. Repeated manual requests preserve an existing cursor. Track committed
infusion/grid and owner-diversity events over subsequent blocks.

## Indexer integration and schemas

Consume vault associations, bank movements and resulting object/infusion events
as described in the [event reference](v0.22.0-economy-events.md). Upgrade events
can appear at block level without a user transaction. Successful rank purchases
emit `structs.structs.EventGuildRankPurchase`, including whether they admitted
the player. Failed transaction batches must not be treated as completed purchases
or movements. Downstream ingestion implementation and testing are user-owned
work outside this task; accurate chain events remain required.

Wire schemas are defined in `proto/structs/structs/{tx,query,guild,infusion,events}.proto`;
the generated HTTP reference is [OpenAPI](../static/openapi.yml).
New transaction type URLs are `/structs.structs.MsgVaultSend`,
`/structs.structs.MsgGuildRankPurchase`,
`/structs.structs.MsgGuildMembershipJoinByRankPurchase` and
`/structs.structs.MsgGuildUpdateRankPurchase`.

### Planetary defenses during pending power repair

Planetary cannon and jamming counters describe installed online structs awaiting
any deferred cleanup. Combat also checks the owner's current backed power, so
positive stored counters do not guarantee that a cannon fires or a satellite
intercepts after an outage. Healthy independent supply still supports those
defenses. No counter is erased merely to evaluate an attack.

Use the delivered `EventAttack` outcome for actual cannon damage and interception.
`evadedByPlanetaryDefenses` describes planetary interception; the separate
`evaded` field describes unit evasion and remains false for interception alone.
There is no new wire schema or synthetic defense-removal event for this read-time
gate. Normal teardown continues to emit the actual subsequent state changes.

### Permission cleanup in genesis

`GenesisState.permissionCleanupQueue` (protobuf field 41) records deleted objects
with permission rows still awaiting bounded cleanup. Preserve it alongside
`permissionList` and `guildRankPermissionList` when handling a v0.22 export.
Dropping it retains the permission rows but loses their pending cleanup work.
Entries must be unique canonical allocation, agreement, provider or substation
IDs absent from the corresponding live-object lists. Import rejects live targets.
This additive genesis field does not change transaction signatures or permission
clear event schemas. Absent legacy fields decode to an empty queue.

Permission cleanup IDs must also be below the corresponding exported next-ID
counter (`allocationCount` for allocations and agreements, `providerCount` or
`substationCount` otherwise). Preserve every exported entity counter even if the
highest-numbered object was deleted. Import retains the greater of that counter,
existing hook-allocated state and surviving-object requirements; it must not
reuse deleted IDs merely because they no longer occur in an object list.

### Owner-filtered planet pages

`PlanetAllByPlayer` now applies page limits and offsets to the named owner's
planets, using an owner index. Unrelated planets no longer produce empty pages or
consume offsets. Response types and count suppression are unchanged. Restart
in-progress pagination after the upgrade rather than treating an offset captured
under the former global-page behavior as an owner-relative offset. The v0.22
migration backfills the derived index, and genesis import rebuilds it.

### Object permission pagination

`permission-by-object` now paginates only keys under the requested object's
`objectId@` prefix. Offsets count that object's grants, and returned cursor keys
are relative to that prefix. Restart pagination after upgrading; do not reuse
pre-upgrade cursors, which were relative to the entire permission store.
Returned permission IDs remain complete `objectId@playerId` strings. Page limits
and suppression of total counts remain unchanged. `permission-by-player` uses the separate player index described below.

### Player permission pagination

`permission-by-player` now uses a player-scoped index. Offsets count only that
player's direct permission rows; restart pagination after the upgrade instead of
reusing old cursors from global pagination. Returned IDs, permission values,
page limits and disabled total counts are unchanged. This lists direct grants,
not authority inherited from guild ownership or rank. Genesis rebuilds the index
from permission records; there is no additional exported wire field.

### Guild-rank permission pages

For `guild-rank-permission-by-object`, pagination limits and offsets count guild
registers, not individual permission records. A page with limit 1 can return
several records for the same guild: each nonzero bit carries its own rank
threshold. Follow `pagination.nextKey` until it is empty; do not infer completion
from the number of returned records. Reverse pagination reverses guild order;
permission bits within each guild remain in ascending bit order. Total counts
remain disabled. The object-and-guild query reads one register directly.

## Substation supply validation and allocation complexity

Positive stored grid `capacity - load` is no longer sufficient to predict an
accepted allocation or agreement. New allocations from substations, dynamic
allocation increases and provider agreement headroom checks validate the complete
incoming allocation ancestry under one shared allowance of 2,048 visited objects
and raw incoming-index rows. Unsupported ancestry returns `unsupported_supply`
on allocation operations or zero available capacity at the provider's existing
capacity check. Cycles, missing/mismatched indexed allocations, an overloaded
ancestor or an incomplete proof can all cause refusal. Validation does not change
stored grid attributes, so indexers must not interpret a refused admission as a
capacity update event.

A healthy but sufficiently complex topology may exceed this limit. Simplifying
its dependency graph can restore admission; waiting for the cascade alone does
not resolve a complexity refusal. This is a protocol constraint for v0.22.0, not
an adjustable query pagination size. Ordinary stored-capacity queries retain
their accounting meaning and do not expose a separate complete supply proof.
Player online/readiness checks now exclude an unsupported secondary share, while
raw connection-capacity queries retain their stored accounting value until the
cascade updates it. Independent usable primary power remains available. Reactor-root
freshness and the complete gameplay-path audit remain unfinished release
requirements; this must not be advertised as complete immediate shutdown enforcement.

After economy activation, player readiness also discounts primary reactor power
whose validator is jailed or no longer bonded, whose live delegation no longer
backs the stored contribution, or whose address no longer belongs to that owner.
Slashes preserve the position's entry-rate blend when calculating the remaining
usable share. A manual restart request by itself does not disable healthy power.
The ownership inventory has a 2,048-unit allowance covering raw index rows and
existing infusion caches; an incomplete inventory makes primary power unusable
for readiness. Stored capacity queries and events continue to represent settled
accounting, so clients cannot infer immediate readiness from raw capacity alone.

New dynamic allocations and dynamic increases from a player also use that live
primary capacity discount. A request above usable headroom returns the existing
capacity error. A new automated player allocation returns `unsupported_supply`
while its full stored capacity is unavailable. Existing dynamic allocations can
still be reduced during repair, and remaining backed capacity stays allocatable.
Automatic resizing and stored grid/event accounting remain on their settlement
paths; a refusal itself does not publish a capacity change.

Substation ancestry also applies the primary discount to player sources. An
existing incoming allocation becomes unsupported when that player's total
allocation load exceeds its usable primary capacity, even while its stored
power is unchanged. An allocation that still fits after a partial slash stays
usable. Player-root infusion rows and cached inventory checks consume the same
2,048-unit ancestry allowance as nodes and incoming allocation rows. Reactor
commission and generator roots still need their separate eligibility review.

Reactor commission sources now require a currently bonded, unjailed validator
after economy activation. Ineligible reactor sources cannot create allocations
or increase dynamic allocations and make downstream ancestry unsupported even
before stored commission totals are updated. A queued manual restart does not
disable an otherwise eligible source. Positive slashes additionally require the
latest issued revision to be certified after reconciliation before commission
admission resumes. Generator eligibility and combined gameplay behavior require separate checks.
Billing continues by elapsed blocks until ordinary teardown.


Generator fuel may remain stored while the generator is offline. After economy
activation, usable owner power excludes contributions from offline, destroyed,
missing or unsupported generator sources; stored fuel and grid totals are not
changed by that readiness check. Independent healthy supply remains available.
Reactivating a generator still requires the ordinary activation readiness and
charge checks. Generator power enters allocations through its infusion owner;
a direct struct-source allocation does not establish supported supply.

Guild-owned allocations now use the same live infusion-backing checks as player
allocations. New allocations, dynamic increases and automated allocations cannot
use a guild vault's stale reactor output, and downstream player readiness also
checks guild roots. Load reduction remains possible. These checks do not pause elapsed-block agreement billing.

Active generator shutdown, restoration and destruction now run through bounded
jobs. The additive `Infusion.generatorDisabled` field distinguishes preserved
burned fuel from currently credited output: when true, power is zero even though
fuel and ratio remain nonzero. Restoration retains that ratio; destruction never
refunds burned fuel. A successful top-up after activation can restore an existing
disabled position before the worker reaches it. The worker does not credit it a
second time.

Consume normal infusion/grid replacements and infusion deletion events across
all affected blocks. Do not assume the initiating transaction updates every
donor. Genesis includes `generatorPowerQueue` IDs and disabled flags so partial
work survives restart; private insertion cursors are rebuilt. Zero-height
BeginBlock snapshots describe the imported state, followed by EndBlock progress.
Both export modes have real-app continuation coverage. Complete ownership lifecycle, production limits and ordinary GridCascade
settlement remain release gates.


## Agreement and provider payments

Agreement/provider payments use the ordinary elapsed-block model. Opening,
capacity changes and teardown checkpoint the provider before changing aggregate
load. Withdrawals checkpoint before moving available earnings to the owner vault.
Cancellation and expiry use the established refund and penalty formulas;
GridCascade tears down affected agreements through those same settlement paths.
Capacity rescaling and individual payments retain their existing integer
rounding. Remainders stay in collateral until provider deletion drains the pools.

There is no additional historical-billing query, financial claim, service clock,
or on-chain audit snapshot. Current contract records, provider checkpoint/load,
normal bank events and object replacement/deletion events are the interface.
Consumers may retain transaction and block receipts off-chain. An outage does
not pause or retrospectively reprice the agreement before actual teardown.


## Structured Go error codes are not the delivered ABCI codes

The native C5 range check exposed an inherited encoding distinction. A
`CombatTargetingError` has `Code() == 1400` and `Unwrap() == ErrCombatTargeting`,
but `cosmossdk.io/errors v1.0.2`'s ABCI encoder looks for `ABCICode()`/`Codespace()`
and traverses `Cause()`. It does not traverse this type's `Unwrap()` or call its
`Code()`. Consequently the delivered range error is `code: 1`,
`codespace: "undefined"`, with the detailed `out_of_range` message in `raw_log`.
Clients must not infer the wire code from `StructuredError.Code()`.

Native transaction
`CBFF094184DDE0C64F21D42DB36708ABE0A61FF8D85B966A4EDCCA511B08A8E9`
at height 71966 is retained in
`/private/tmp/structs-native-command-fom65a21/diagnostic-txs.json`.
The small SDK probe `/tmp/structs-command-error-probe.go` reproduces this for both
the direct and wrapped structured error; its registered underlying cause encodes
as `structs/1400` instead (`/tmp/structs-command-error-probe.log`). The v0.21.0 tag
has the same `Code`/`Unwrap` methods, so this is inherited behavior, not a new
economy-migration failure.

C5 pins the actual envelope and exact identities/reason and rejects generic,
unrelated or panic errors. Production error encoding is unchanged by this test
repair. The final interface review must account for this distinction; changing
these interfaces later changes observable transaction error codes and requires
client compatibility review.
